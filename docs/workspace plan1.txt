# MASTER PROMPT — Notion 스타일 통합업무관리 시스템 단계별 개발 지시서

너는 고급 풀스택 개발자이자 제품 설계자다.
지금부터 “Notion 카드형 업무관리 시스템을 오마주한 통합업무관리 웹앱”을 개발한다.

중요한 원칙은 다음과 같다.

* Notion을 그대로 복제하지 말고, **카드형 업무관리 UX에서 영감을 받은 독자적인 디자인**으로 구현한다.
* 한 번에 전체 기능을 구현하지 않는다.
* 반드시 Phase 단위로 나누어 진행한다.
* 각 Phase 완료 후에는 반드시 자체검수, 무결성 검토, 빌드 테스트, Git 커밋을 진행한다.
* 각 Phase 완료 후에는 나에게 “다음 Phase 진행 승인”을 요청하고, 내가 허락하기 전까지 다음 Phase를 진행하지 않는다.
* 모르는 정보가 있으면 임의로 크게 확장하지 말고, 현재 코드베이스를 먼저 분석한 뒤 보수적으로 구현한다.
* 기존 프로젝트가 있다면 기존 구조와 기술스택을 최대한 유지한다.
* 기존 프로젝트가 없다면 아래 기본 기술스택을 기준으로 새 프로젝트를 구성한다.

---

## 0. 기본 개발 목표

개발할 시스템은 클라이언트로부터 업무를 수주한 뒤, 중간관리자, PM, 실무 직원이 하나의 카드형 업무관리 화면에서 일정, 승인, 반려, 업무 순서, 야근/추가일정 신청, 직원별 공정표를 관리할 수 있는 웹앱이다.

핵심 목표는 다음과 같다.

1. 클라이언트에게 업무 수주
2. 수주된 프로젝트를 중간관리자가 담당 PM에게 전달
3. 담당 PM 또는 하위 직원이 업무일정 작성
4. 중간관리자가 일정 확인 후 승인 또는 반려
5. 승인된 일정은 개별 담당자에게 전송
6. 반려된 일정은 PM 또는 하위 직원이 재설정
7. 일정은 Notion 스타일 카드형 UI로 배치
8. 각 카드는 프로젝트 상태창 역할 수행
9. 배정받은 업무 진행도 표시
10. 일정 종료 시 완료 처리 가능
11. 업무 추가 요청 가능
12. 업무 추가는 담당 직원 직접 등록 또는 PM 신청 후 중간관리자 승인 방식 지원
13. 카드 이동 시 업무 순서 자동 변경
14. 업무 순서 변경 시 관련자에게 알림 생성
15. 야근 또는 추가일정 필요 시 카드 내부 버튼으로 신청
16. 신청 알림은 PM과 중간관리자에게 전달
17. PM이 승인하지 않아도 중간관리자는 신청 알림을 미리 확인 가능
18. 직원별 전체 공정표를 표 형태로 제공
19. 일별, 주별, 월별 보기 지원
20. 부서별 필터링 지원
21. 역할별 권한 분리
22. 모든 주요 변경사항은 기록으로 남김

## 1. 권장 기술스택

기존 프로젝트가 있다면 기존 스택을 우선한다.

기존 프로젝트가 없거나 신규 프로젝트라면 다음 스택을 사용한다.

* Frontend: Next.js 또는 React
* Language: TypeScript
* Styling: Tailwind CSS
* State: Zustand 또는 React Context
* Database: 우선 로컬 개발용 Mock JSON 또는 SQLite
* 추후 확장 가능 구조: Supabase, PostgreSQL, Prisma 적용 가능하게 설계
* Drag & Drop: dnd-kit
* Date Handling: date-fns
* Icons: lucide-react
* Charts / Timeline: 직접 구현 또는 lightweight 라이브러리
* Git: Phase별 커밋 필수

단, 기존 코드베이스가 이미 다른 프레임워크를 사용하고 있다면 무리하게 변경하지 말고 기존 구조를 유지한다.

## 2. 사용자 역할 정의

시스템에는 다음 역할이 존재한다.

### 2-1. 클라이언트

* 업무를 요청하는 외부 주체
* 직접 로그인 기능은 Phase 후반 또는 별도 Phase에서 구현
* 초기에는 프로젝트 등록 시 “클라이언트명” 필드로 관리

### 2-2. 중간관리자

* 수주 프로젝트를 확인
* PM에게 프로젝트 배정
* PM 또는 실무자가 작성한 일정 승인/반려
* 업무 추가 요청 승인/반려
* 야근/추가일정 신청 확인 및 승인/반려
* 전체 공정표 확인
* 부서별 업무 현황 확인
* 전체 업무 우선순위 조정 가능

### 2-3. PM

* 중간관리자로부터 프로젝트를 전달받음
* 프로젝트 세부 업무 카드 생성
* 일정 초안 작성
* 담당자 배정
* 업무 추가 신청
* 야근/추가일정 신청 검토
* 승인된 일정에 따라 팀원 업무 관리

### 2-4. 실무 직원

* 배정받은 카드 확인
* 진행률 업데이트
* 완료 처리 요청 또는 완료 처리
* 업무 추가 제안
* 야근/추가일정 신청
* 자신의 일별/주별/월별 업무 공정표 확인

### 2-5. 관리자

* 사용자, 부서, 권한 관리
* 전체 로그 확인
* 시스템 설정 관리

## 6. 핵심 업무 흐름

### 6-1. 수주 → PM 배정

1. 클라이언트 업무 수주
2. 수주 프로젝트 등록
3. 프로젝트 상태: INTAKE_RECEIVED
4. 중간관리자가 확인
5. PM 배정
6. 프로젝트 상태: PM_ASSIGNED
7. PM에게 알림 생성

### 6-2. PM 일정 작성 → 중간관리자 승인

1. PM이 프로젝트 업무 카드를 생성
2. 담당자 및 일정 배정
3. 일정 초안 작성
4. PM이 “일정 승인 요청” 클릭
5. ApprovalRequest 생성
6. 프로젝트 상태: SCHEDULE_PENDING_APPROVAL
7. 중간관리자에게 알림 생성
8. 중간관리자가 승인 또는 반려

승인 시:

1. SchedulePlan 상태 APPROVED
2. Project 상태 SCHEDULE_APPROVED 또는 IN_PROGRESS
3. 개별 담당자에게 알림 생성
4. 각 직원의 공정표에 업무 반영

반려 시:

1. SchedulePlan 상태 REJECTED
2. Project 상태 SCHEDULE_REJECTED
3. 반려 사유 기록
4. PM 또는 하위 직원이 일정 재작성
5. 다시 승인 요청

### 6-3. 업무 카드 진행

1. 직원은 본인에게 배정된 카드 확인
2. 진행 시작 시 카드 상태 IN_PROGRESS
3. 진행률 업데이트
4. 완료 시 DONE 처리
5. 완료 기록 생성
6. 관련 PM과 중간관리자에게 알림 생성

### 6-4. 업무 추가

두 가지 방식이 필요하다.

방식 A — 담당 직원이 직접 추가:

1. 직원이 카드 또는 프로젝트 화면에서 “업무 추가” 클릭
2. 추가 업무명, 사유, 예상 일정 입력
3. ApprovalRequest type: ADDITIONAL_TASK 생성
4. PM과 중간관리자에게 알림 생성
5. 중간관리자 승인 시 새 TaskCard 생성
6. 반려 시 사유 기록

방식 B — PM이 신청:

1. PM이 추가 업무 카드 초안 생성
2. 중간관리자 승인 요청
3. 승인 시 공식 카드 생성
4. 담당 직원에게 알림 생성

### 6-5. 업무 순서 변경

1. 카드 보드에서 카드를 드래그하여 순서 변경
2. orderIndex 자동 업데이트
3. AuditLog 생성
4. 관련 담당자에게 Notification 생성
5. 알림 내용: “업무 순서가 변경되었습니다.”
6. 직원별 공정표에도 변경 순서 반영

### 6-6. 야근 또는 추가일정 신청

1. 담당 직원이 해당 업무 카드에서 “야근/추가일정 신청” 클릭
2. 신청 사유, 필요 시간, 요청 일정 입력
3. ApprovalRequest type: OVERTIME_REQUEST 또는 DEADLINE_EXTENSION 생성
4. PM에게 알림 생성
5. 중간관리자에게도 동시에 사전 알림 생성
6. PM이 아직 승인하지 않아도 중간관리자는 해당 신청을 확인 가능
7. 승인/반려 이력 기록
8. 승인 시 업무 일정 또는 별도 표시 업데이트

## 7. 디자인 방향

Notion을 직접 복제하지 않는다.
단, 아래 UX 감성은 참고한다.

* 미니멀한 카드형 레이아웃
* 넓은 여백
* 부드러운 회색 계열 배경
* 상태별 컬럼
* 카드 내부에 핵심 정보만 압축 표시
* 클릭 시 상세 패널 또는 모달 표시
* 드래그 앤 드롭 중심 UX
* 불필요한 장식 최소화
* 실무자가 피로하지 않은 화면

금지:

* Notion 로고 사용 금지
* Notion과 동일한 UI 복제 금지
* Notion 고유 아이콘/브랜드 요소 사용 금지
* 과도한 애니메이션 금지
* 한 화면에 너무 많은 텍스트 노출 금지

## 9. Git 작업 규칙

각 Phase 완료 후 반드시 다음을 수행한다.

```bash
git status
npm run lint
npm run build
```

프로젝트에 test 스크립트가 있다면 다음도 수행한다.

```bash
npm run test
```

오류가 발생하면 다음 Phase로 넘어가지 말고 해당 Phase 안에서 수정한다.

커밋 전 확인:

```bash
git diff
git status
```

커밋:

```bash
git add .
git commit -m "phase-X: ..."
```

원격 push는 내가 명시적으로 승인하기 전까지 하지 않는다.

## 10. 무결성 검토 기준

각 Phase마다 아래 항목을 반드시 검토한다.

### 10-1. 데이터 무결성

* Project와 TaskCard의 관계가 깨지지 않는가?
* TaskCard의 assigneeId가 실제 User에 존재하는가?
* departmentId가 실제 Department에 존재하는가?
* ApprovalRequest가 관련 Project 또는 Task와 연결되는가?
* Notification이 실제 User에게 연결되는가?
* AuditLog가 실제 변경사항을 설명하는가?

### 10-2. 상태 무결성

* 승인 전 업무가 완료 처리되지 않는가?
* 반려된 일정이 승인된 것처럼 표시되지 않는가?
* 완료된 카드가 무분별하게 이동되지 않는가?
* Hold 상태 업무가 공정표에서 구분되는가?
* 순서 변경 후 orderIndex가 중복되지 않는가?

### 10-3. 권한 무결성

* 직원이 타인의 업무를 무단 수정할 수 없는가?
* PM이 중간관리자 승인 권한을 갖지 않는가?
* 중간관리자가 전체 승인 요청을 볼 수 있는가?
* PM 승인 전이라도 중간관리자가 야근/추가일정 신청을 미리 볼 수 있는가?
* 직원은 본인 중심의 공정표만 보는가?

### 10-4. UI 무결성

* 카드가 너무 복잡하지 않은가?
* 표 화면이 한눈에 들어오는가?
* 모바일에서 주요 기능이 깨지지 않는가?
* 승인/반려 버튼이 명확한가?
* 알림이 누락되지 않는가?

## 11. 절대 금지사항

* 전체 기능을 한 번에 구현하지 마라.
* Phase 승인 없이 다음 Phase로 넘어가지 마라.
* 사용자의 승인 없이 GitHub 원격 저장소에 push하지 마라.
* 기존 코드를 분석하지 않고 구조를 새로 갈아엎지 마라.
* Notion UI를 그대로 복제하지 마라.
* 브랜드 로고, 고유 아이콘, 고유 디자인을 모방하지 마라.
* Mock 데이터만 바꾸고 실제 UI 연결을 하지 않는 방식으로 끝내지 마라.
* 빌드 오류가 있는 상태로 완료 보고하지 마라.
* 자체검수 없이 완료 보고하지 마라.
* 알림, 승인, 로그 흐름을 생략하지 마라.
* 상태값을 임의로 추가해 혼란스럽게 만들지 마라.
* 불필요하게 거대한 DB 설계로 시작하지 마라.
* 추측으로 기능을 확장하지 마라.
