# WORKSPACE PLAN 8 — 업무팀 평가방식 통합, QC 오류율 기반 성과평가, 프로젝트 규모/작업량 보정 프롬프트

이 프롬프트는 기존 `workspace plan1.txt`, `workspace plan2.txt`, `workspace plan3.txt`, `workspace plan4.txt`, `workspace plan5.txt`, `workspace plan6.txt`, `workspace plan7.txt` 이후에 추가되는 여덟 번째 보강 지시사항이다.

이번 Plan 8의 목적은 사용자가 제공한 `업무팀 평가방식(1).xlsx`의 평가 계획안을 현재 Workspace 시스템에 충돌 없이 녹여 넣는 것이다.

중요한 점은 Plan 8의 평가는 Plan 6의 `HealthScore`와 다르다는 것이다.

- `HealthScore`: 현재 업무 카드가 정상적으로 진행 중인지 판단하는 운영/리스크 지표
- `PerformanceEvaluation`: 일정 기간 동안 작업자의 품질, 작업량, 프로젝트 규모를 기준으로 산정하는 평가 지표

두 지표는 서로 연결될 수는 있지만, 절대 같은 값으로 취급하지 않는다.

## 0. 평가방식 Excel에서 확인한 핵심 기준

업로드된 `업무팀 평가방식(1).xlsx`의 주요 내용은 다음과 같다.

### 0-1. 평가방식 도입 목적

기존에는 단순 오류 건수만으로 업무 품질을 판단하기 어려웠고, 프로젝트 규모 및 작업량 차이로 인해 동일 기준 평가에 한계가 있었다.

따라서 평가방식은 다음 요소를 함께 반영한다.

- 작업 품질
- QC 오류율
- 수행 프로젝트 규모
- 실제 작업량
- 프로젝트별 특수성

또한 프로젝트별 평가 기준 차이를 줄이기 위해, PM 개인 평가보다는 QC팀 기준 중심으로 평가를 일원화하는 방향으로 구성한다.

### 0-2. 평가 흐름

기본 흐름은 다음과 같다.

1. 작업자가 도면 기준으로 산출 작업을 완료한다.
2. `제출자료 검토사항` 및 `최종자료 검토사항` 단계에서 오류사항을 정리한다.
3. 프로젝트 완료 시 PM은 프로젝트 특성 및 진행 여건에 대한 종합의견을 작성한다.
4. PM 의견은 직접 평가점수로 반영하지 않고, QC팀이 프로젝트 상황을 이해하기 위한 참고자료로 사용한다.
5. QC팀은 PM 의견과 오류 리스트를 함께 검토한다.
6. QC팀은 오류 중요도에 따라 가중치를 부여한다.
7. 시스템은 QC팀이 확정한 가중치 기준으로 오류율과 평가점수를 계산한다.

### 0-3. 품질 평가 방식

기본 품질 평가는 단순 오류 건수가 아니라 작업량 대비 오류 비율을 기준으로 산정한다.

```text
오류율 = (오류건수 ÷ 작업량) × 100
```

단, Plan 8에서는 단순 오류건수 대신 QC 가중치를 반영한 `가중 오류건수`를 기본 계산에 사용할 수 있도록 설계한다.

```text
가중 오류건수 = SUM(오류별 가중치)
가중 오류율 = (가중 오류건수 ÷ 작업량) × 100
```

### 0-4. 오류율 구간별 점수 예시

Excel 기준의 점수 구간은 다음과 같다.

```text
0~10%: 100점
10~20%: 80점
20~30%: 60점
30~40%: 40점
40~50%: 20점
50~100%: 0점
```

구간 경계가 겹치지 않도록 실제 구현에서는 다음처럼 처리한다.

```text
0 <= errorRate <= 10: 100
10 < errorRate <= 20: 80
20 < errorRate <= 30: 60
30 < errorRate <= 40: 40
40 < errorRate <= 50: 20
50 < errorRate <= 100: 0
100 < errorRate: 0
```

### 0-5. QC 오류 가중치 기준

QC팀은 오류의 중요도 및 영향도에 따라 항목별 가중치를 설정할 수 있다.

가중치 범위:

```text
10% ~ 100%
```

예시:

```text
가중치 100% → 오류 1건 즉시 반영
가중치 50% → 동일 수준 오류 2건 누적 시 1건 반영
가중치 25% → 동일 수준 오류 4건 누적 시 1건 반영
```

이 기준은 단순 오탈자 수준의 오류와 실제 품질 영향 오류를 구분하기 위한 장치다.

### 0-6. 프로젝트 규모 반영 기준

프로젝트 규모는 1차 운영안에서 건물 규모 기준으로 단순화한다.

기준 면적:

```text
50,000 Py = 규모 가중치 1
```

계산 방식:

```text
면적 가중치 = 프로젝트 연면적 ÷ 50,000 Py
```

예시:

```text
25,000 Py → 0.5
50,000 Py → 1.0
100,000 Py → 2.0
```

이 규모 가중치는 단순 프로젝트 개수만으로 평가할 때 발생하는 불공정성을 줄이기 위한 보정값이다.

## 1. Plan 8의 절대 원칙

Antigravity는 다음 원칙을 반드시 지켜라.

- Plan 8은 Plan 1~7을 대체하지 않는다.
- Plan 8은 기존 Workspace에 성과평가 기능을 충돌 없이 추가하는 확장 계획이다.
- 평가 기능은 초기 MVP에 포함하지 않는다.
- Plan 4의 MVP 제한 원칙을 유지한다.
- Plan 7의 데이터 사전, status taxonomy, 권한 스코프 함수 설계를 먼저 따른다.
- 평가 점수는 업무 진행률, HealthScore, 프로젝트 완료율과 혼동하지 않는다.
- QC 오류율은 작업자의 실제 성과평가 지표다.
- HealthScore는 업무 카드의 현재 리스크/건강도 지표다.
- PM 의견은 평가 참고자료이며, PM이 직접 점수를 임의로 주는 방식으로 구현하지 않는다.
- QC팀 또는 QC 권한 사용자가 오류 중요도와 가중치를 확정한다.
- 평가 결과는 권한 있는 사용자에게만 노출한다.
- 평가 계산식은 하드코딩하지 말고 EvaluationPolicy로 분리한다.
- 평가 데이터는 AuditLog, VersionSnapshot, 권한 스코프, 검색/필터와 연결되어야 한다.
- 사용자 승인 없이 Phase 41 이후로 넘어가지 않는다.
- 사용자 승인 없이 GitHub 원격 push를 하지 않는다.

## 2. 기존 Plan과의 충돌 방지 기준

### 2-1. Plan 1과의 연결

Plan 1은 기본 업무 흐름을 정의한다.

```text
수주 → PM 배정 → 일정 작성 → 승인/반려 → 카드형 업무진행 → 완료
```

Plan 8의 평가는 이 흐름을 방해하지 않는다.

평가 데이터는 다음 시점 이후 생성된다.

```text
TaskCard 완료 요청
PM 검토
중간관리자 최종 완료 승인
QC 검토
평가 반영
```

평가는 업무를 진행시키는 기능이 아니라 완료 이후 품질 검토와 성과 산정을 위한 기능이다.

### 2-2. Plan 2와의 연결

Plan 2의 다음 기능과 연결한다.

- 선후행 업무
- 일정 충돌
- 변경요청
- 체크리스트
- 산출물 관리
- 알림 우선순위
- 실제 DB/로그인 확장

평가 계산 시 다음 데이터를 참고할 수 있다.

- 완료된 TaskCard
- 작업자의 체크리스트 완료 여부
- 산출물 등록 여부
- 변경요청 발생 여부
- QC 오류 리스트
- 프로젝트 특수성 메모

단, 체크리스트 미완료나 산출물 누락은 품질 평가 자체에 직접 점수화하지 않고, QC 검토 참고자료로만 우선 사용한다.

### 2-3. Plan 3과의 연결

Plan 3의 인사카드 기반 권한을 평가 권한에도 적용한다.

PersonnelCard에 평가 관련 권한을 추가 고려한다.

```text
canViewEvaluation
canManageEvaluation
canReviewQcIssues
canLockEvaluation
canExportEvaluationReport
```

역할별 노출 원칙:

- 최고관리자: 전체 평가 조회 가능
- 중간관리자: 본인 부서 평가 조회 가능
- PM: 본인 프로젝트의 QC 오류 및 PM 의견 조회 가능, 최종 평가점수 전체 조회는 제한 가능
- 작업자: 본인 평가 결과와 본인 오류 내역만 제한적으로 조회 가능
- QC 담당자: QC 오류 등록, 가중치 부여, 평가 산정 가능
- 관리자: 평가 정책 관리 가능

### 2-4. Plan 4와의 연결

Plan 4의 운영 안정화 기준과 연결한다.

- 평가 결과는 기간별로 Lock 가능해야 한다.
- 평가 확정 후 수정은 권한 있는 사용자만 가능하다.
- 평가 수정은 VersionSnapshot과 AuditLog를 남긴다.
- 평가 결과 삭제는 실제 삭제가 아니라 soft delete 처리한다.
- 평가정책 변경 시 기존 평가 결과에 소급 적용할지 여부를 명시해야 한다.

### 2-5. Plan 5와의 연결

Plan 5의 VN 월별 스케줄표 기반 데이터는 작업량 산정의 근거로 사용할 수 있다.

연결 가능 데이터:

- ScheduleAssignment
- TaskCard
- PersonnelCard
- Project
- PersonalSchedule

작업량 산정 기준 후보:

```text
1. 완료된 TaskCard 수
2. ScheduleAssignment 일수
3. 투입일수 × 기준 근무시간
4. 프로젝트 규모 가중치
5. Scope 난이도 가중치
```

초기에는 단순하게 시작한다.

```text
초기 작업량 = 완료된 업무 카드 수 또는 ScheduleAssignment 기반 투입일수
확장 작업량 = 프로젝트 규모 가중치 × 참여 비율 × Scope 난이도 가중치
```

### 2-6. Plan 6과의 연결

Plan 6의 HealthScore와 Plan 8의 평가점수는 분리한다.

```text
HealthScore
- 현재 업무가 잘 진행되고 있는지 보는 리스크 지표
- 업무 운영용
- PM/중간관리자가 조기 대응하기 위한 지표

EvaluationScore
- 일정 기간 동안의 작업 품질과 작업량을 보는 성과평가 지표
- 완료 후 평가용
- QC 검토와 오류율 기반
```

보드 카드에 평가점수를 직접 노출하지 않는다.

단, 카드 상세 패널의 QC/평가 탭에서 권한 있는 사용자에게만 평가 관련 정보를 표시할 수 있다.

### 2-7. Plan 7과의 연결

Plan 7의 통합 데이터 사전에 평가 관련 엔티티를 추가한다.

Data Dictionary에는 다음 항목을 추가해야 한다.

- EvaluationPeriod
- EvaluationPolicy
- EvaluationTarget
- QcIssue
- QcIssueWeight
- ProjectScaleFactor
- WorkloadUnit
- PerformanceEvaluationResult
- EvaluationAppeal
- EvaluationLock
- EvaluationReport

## 3. 평가 전용 역할 및 권한

기존 역할에 QC 관련 역할을 추가하거나, PersonnelCard 권한 플래그로 관리한다.

### 3-1. 추가 역할 후보

```text
QC_REVIEWER
QC_MANAGER
EVALUATION_ADMIN
```

단, 초기 구현에서는 역할을 과도하게 늘리지 말고 PersonnelCard의 권한 플래그로 처리할 수 있다.

### 3-2. 권장 권한 플래그

```text
canCreateQcIssue
canEditQcIssue
canApproveQcIssueWeight
canCalculateEvaluation
canViewEvaluationResult
canViewDepartmentEvaluation
canViewAllEvaluation
canLockEvaluation
canUnlockEvaluation
canSubmitEvaluationAppeal
canReviewEvaluationAppeal
```

### 3-3. 권한 원칙

- 작업자는 본인 평가 결과만 볼 수 있다.
- 작업자는 평가 확정 전 계산식이나 타인 비교표를 볼 수 없다.
- PM은 본인 프로젝트의 PM 종합의견을 작성할 수 있다.
- PM은 QC 가중치를 확정할 수 없다.
- 중간관리자는 본인 부서 평가 현황을 볼 수 있다.
- 최고관리자는 전체 평가 현황을 볼 수 있다.
- QC 권한자는 오류와 가중치를 관리할 수 있다.
- 평가 확정 후 수정은 평가 관리자 또는 최고관리자만 가능하다.

## 4. 평가 데이터 모델

### 4-1. EvaluationPeriod

평가 기간을 정의한다.

```ts
EvaluationPeriod {
  id: string
  title: string
  startDate: string
  endDate: string
  departmentId?: string
  status: "DRAFT" | "COLLECTING" | "QC_REVIEW" | "CALCULATED" | "LOCKED" | "ARCHIVED"
  createdBy: string
  createdAt: string
  updatedAt: string
}
```

### 4-2. EvaluationPolicy

평가 계산 정책을 정의한다.

```ts
EvaluationPolicy {
  id: string
  title: string
  effectiveFrom: string
  effectiveTo?: string
  baseAreaPy: number
  useWeightedQcIssue: boolean
  qualityScoreWeight?: number
  workloadScoreWeight?: number
  useWorkloadAdjustment: boolean
  useProjectScaleAdjustment: boolean
  errorRateBands: ErrorRateBand[]
  createdBy: string
  createdAt: string
  updatedAt: string
}
```

주의:

- `qualityScoreWeight`, `workloadScoreWeight`는 사용자가 최종 평가비율을 확정하기 전까지 하드코딩하지 않는다.
- 초기에는 품질점수와 작업량지수를 별도로 보여주고, 최종 종합점수는 정책 설정 후 계산한다.

### 4-3. ErrorRateBand

```ts
ErrorRateBand {
  id: string
  minExclusive?: number
  minInclusive?: number
  maxInclusive: number
  score: number
  label: string
}
```

기본 예시:

```ts
[
  { label: "0~10%", minInclusive: 0, maxInclusive: 10, score: 100 },
  { label: "10~20%", minExclusive: 10, maxInclusive: 20, score: 80 },
  { label: "20~30%", minExclusive: 20, maxInclusive: 30, score: 60 },
  { label: "30~40%", minExclusive: 30, maxInclusive: 40, score: 40 },
  { label: "40~50%", minExclusive: 40, maxInclusive: 50, score: 20 },
  { label: "50~100%", minExclusive: 50, maxInclusive: 100, score: 0 }
]
```

### 4-4. EvaluationTarget

평가 대상자를 정의한다.

```ts
EvaluationTarget {
  id: string
  evaluationPeriodId: string
  userId: string
  personnelCardId: string
  departmentId: string
  roleAtPeriod: string
  teamName?: string
  groupName?: string
  included: boolean
  excludeReason?: string
}
```

### 4-5. QcIssue

QC 오류를 정의한다.

```ts
QcIssue {
  id: string
  evaluationPeriodId: string
  projectId: string
  taskId?: string
  scheduleAssignmentId?: string
  assigneeId: string
  reportedBy: string
  reviewedBy?: string
  issueStage: "SUBMISSION_REVIEW" | "FINAL_REVIEW" | "DELIVERY_REVIEW" | "POST_DELIVERY"
  issueType: string
  title: string
  description: string
  severity: "LOW" | "MEDIUM" | "HIGH" | "CRITICAL"
  weightPercent: number
  weightedErrorCount: number
  sourceFileId?: string
  sourceAttachmentId?: string
  status: "DRAFT" | "REVIEWED" | "CONFIRMED" | "REJECTED" | "VOID"
  pmCommentId?: string
  qcComment?: string
  createdAt: string
  updatedAt: string
}
```

계산 규칙:

```text
weightedErrorCount = weightPercent / 100
```

예시:

```text
100% = 1.0
50% = 0.5
25% = 0.25
10% = 0.1
```

### 4-6. ProjectEvaluationContext

PM의 프로젝트 종합의견을 저장한다.

```ts
ProjectEvaluationContext {
  id: string
  evaluationPeriodId: string
  projectId: string
  pmId: string
  departmentId: string
  projectConditionSummary: string
  scheduleDifficultyComment?: string
  scopeDifficultyComment?: string
  clientChangeComment?: string
  resourceIssueComment?: string
  specialNotes?: string
  createdAt: string
  updatedAt: string
}
```

중요:

- PM 의견은 평가점수 직접 계산에 반영하지 않는다.
- PM 의견은 QC팀이 오류와 가중치를 판단할 때 참고하는 컨텍스트다.
- PM 의견을 평가점수로 반영하려면 별도 정책 승인 후 확장 Phase에서 처리한다.

### 4-7. ProjectScaleFactor

프로젝트 규모 가중치를 정의한다.

```ts
ProjectScaleFactor {
  id: string
  projectId: string
  grossAreaPy?: number
  baseAreaPy: number
  areaWeight: number
  source: "PROJECT_LIST" | "MANUAL" | "IMPORTED_EXCEL" | "UNKNOWN"
  createdAt: string
  updatedAt: string
}
```

계산식:

```text
areaWeight = grossAreaPy / baseAreaPy
baseAreaPy = 50000
```

### 4-8. WorkloadUnit

작업량을 정의한다.

```ts
WorkloadUnit {
  id: string
  evaluationPeriodId: string
  userId: string
  projectId?: string
  taskId?: string
  scheduleAssignmentId?: string
  workloadType: "TASK_CARD" | "SCHEDULE_DAY" | "PROJECT_SCALE" | "MANUAL"
  baseWorkload: number
  projectScaleWeight?: number
  scopeWeight?: number
  finalWorkload: number
  source: "TASK_CARD" | "SCHEDULE_ASSIGNMENT" | "MANUAL" | "IMPORTED_EXCEL"
  createdAt: string
}
```

초기 계산 후보:

```text
baseWorkload = 완료된 TaskCard 수 또는 투입일수
finalWorkload = baseWorkload × projectScaleWeight × scopeWeight
```

단, `scopeWeight`는 사용자 승인 전까지 기본값 1로 둔다.

### 4-9. PerformanceEvaluationResult

평가 결과를 저장한다.

```ts
PerformanceEvaluationResult {
  id: string
  evaluationPeriodId: string
  userId: string
  departmentId: string
  totalWorkload: number
  totalRawErrorCount: number
  totalWeightedErrorCount: number
  rawErrorRate: number
  weightedErrorRate: number
  qualityScore: number
  workloadIndex?: number
  workloadScore?: number
  finalScore?: number
  grade?: string
  status: "DRAFT" | "CALCULATED" | "REVIEWING" | "CONFIRMED" | "LOCKED"
  calculatedAt?: string
  confirmedBy?: string
  confirmedAt?: string
}
```

기본 계산식:

```text
rawErrorRate = (totalRawErrorCount / totalWorkload) × 100
weightedErrorRate = (totalWeightedErrorCount / totalWorkload) × 100
qualityScore = scoreByErrorRateBand(weightedErrorRate)
```

작업량 반영은 정책 확정 후 계산한다.

```text
finalScore = qualityScore × qualityScoreWeight + workloadScore × workloadScoreWeight
```

단, `qualityScoreWeight`와 `workloadScoreWeight`가 설정되지 않은 경우 `finalScore`를 계산하지 않고 품질점수와 작업량지수를 별도로 표시한다.

### 4-10. EvaluationAppeal

평가 이의신청을 정의한다.

```ts
EvaluationAppeal {
  id: string
  evaluationPeriodId: string
  userId: string
  evaluationResultId: string
  targetIssueId?: string
  reason: string
  requestedBy: string
  status: "PENDING" | "ACCEPTED" | "REJECTED" | "CANCELLED"
  reviewedBy?: string
  reviewComment?: string
  createdAt: string
  updatedAt: string
}
```

## 5. 평가 계산 로직

### 5-1. 기본 품질평가 계산

```text
1. 평가 기간에 포함된 작업자를 찾는다.
2. 작업자의 완료 업무 또는 투입 일수를 기준으로 totalWorkload를 계산한다.
3. 작업자에게 귀속된 QC 오류를 찾는다.
4. 오류별 weightPercent를 weightedErrorCount로 변환한다.
5. totalWeightedErrorCount를 합산한다.
6. weightedErrorRate = (totalWeightedErrorCount / totalWorkload) × 100
7. weightedErrorRate 구간에 따라 qualityScore를 계산한다.
```

### 5-2. 작업량 산정 기준

작업량은 다음 순서로 확장한다.

#### 1차 MVP 평가 샘플

```text
totalWorkload = 완료된 TaskCard 수
```

또는 VN Excel seed가 연결된 경우:

```text
totalWorkload = ScheduleAssignment 투입일수
```

#### 2차 확장

```text
totalWorkload = ScheduleAssignment 투입일수 × 프로젝트 규모 가중치
```

#### 3차 확장

```text
totalWorkload = ScheduleAssignment 투입일수 × 프로젝트 규모 가중치 × Scope 난이도 가중치
```

단, Scope 난이도 가중치는 아직 확정되지 않았으므로 기본값 1로 둔다.

### 5-3. 프로젝트 규모 가중치

```text
projectScaleWeight = projectGrossAreaPy / 50000
```

프로젝트 연면적이 없으면 다음 중 하나로 처리한다.

```text
UNKNOWN
MANUAL_REQUIRED
DEFAULT_1
```

기본 운영안:

- 면적이 있으면 계산
- 면적이 없으면 `DEFAULT_1`로 표시하되, 평가 리포트에 `면적 정보 없음` 경고를 표시한다.
- 평가 확정 전 중간관리자 또는 평가관리자가 면적을 수동 입력할 수 있게 설계한다.

### 5-4. 오류 가중치 계산

```text
weightedErrorCount = weightPercent / 100
```

예시:

```text
100% 오류 1건 = 1.0
50% 오류 1건 = 0.5
25% 오류 1건 = 0.25
10% 오류 1건 = 0.1
```

### 5-5. 0 나누기 방지

작업량이 0인 경우 오류율을 계산하지 않는다.

처리 방식:

```text
totalWorkload = 0 → evaluationStatus = REVIEW_REQUIRED
qualityScore = null
warning = "작업량이 없어 오류율을 계산할 수 없습니다."
```

# PHASE EXECUTION CONTROL ADDENDUM — 단계별 진행 강제 규칙

이 추가 지시사항은 workspace plan1~8 전체에 공통 적용되는 Phase 진행 통제 규칙이다.

Antigravity는 모든 작업에서 아래 규칙을 반드시 지켜야 한다.

---

## 1. Phase Lock 원칙

현재 진행 중인 Phase 외의 기능을 구현하지 마라.

예시:

- Phase 0에서는 분석만 한다.
- Phase 1에서는 데이터 모델, 타입, Mock 데이터, 권한 기본 구조만 만든다.
- Phase 2에서는 기본 레이아웃과 대시보드만 만든다.
- Phase 3에서는 수주 프로젝트 등록과 PM 배정만 만든다.
- Phase 4에서는 일정 작성과 승인/반려만 만든다.
- Phase 5에서는 카드형 보드와 드래그 순서 변경만 만든다.
- 이후 Phase도 각 Phase에 명시된 범위만 구현한다.

현재 Phase에서 다음 Phase 기능이 필요해 보이더라도, 임의로 구현하지 말고 “다음 Phase 후보 작업”으로만 기록하라.
