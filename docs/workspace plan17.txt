# WORKSPACE PLAN 17 — 수주 프로젝트/개발팀 업무 리스트 분리, 프로젝트 보드 흐름, PM 업무 하달, 작업자 일정 조정 워크플로우 정밀 구현 프롬프트

이 프롬프트는 기존 `workspace plan1.txt`부터 `workspace plan16.txt` 이후에 추가되는 열일곱 번째 보강 지시사항이다.

Plan 17의 목적은 단순 문구 변경이 아니다. 현재 화면에서 확인된 수주 프로젝트 관리, 개발팀 내부 업무 관리, 프로젝트 보드 컬럼 순서, 신규 항목의 착수 전 자동 진입, PM의 작업 하달, 작업자의 일정 요청/세부일정 조정까지 이어지는 **운영 가능한 업무 흐름**을 실제 코드와 데이터 구조에 연결하는 것이다.

현재 별도 흐름에서 디자인 개선이 진행 중일 수 있다. 따라서 Plan 17은 시각 디자인 개선이 아니라 **기능, 상태 전이, 데이터 정합성, 권한, 승인, 일정, 알림, JSON handoff, QA 증빙**을 중심으로 진행한다. 단, 사용자가 지정한 탭 이름, 탭 순서, 컬럼 순서처럼 기능 이해에 직접 영향을 주는 UI 문구/배치는 Plan 17 범위에 포함한다.

## 0. 현재 스크린샷 기준 문제

사용자가 제공한 2026-07-08 화면 기준으로 다음 문제가 확인된다.

1. `/projects/intake` 화면의 제목과 관리 범위가 `수주 프로젝트 관리` 하나로만 보인다.
2. 이 화면에는 내부 개발팀 업무를 별도 리스트로 생성/관리하는 탭이 없다.
3. 프로젝트 보드의 상단 탭 순서가 `외부 수주 프로젝트` 다음 `개발팀 작업`이다.
4. 사용자는 `개발팀 작업` 탭이 `외부 수주 프로젝트`보다 앞에 오기를 원한다.
5. 프로젝트 보드 컬럼이 `착수 전`, `진행 중`, `수정(Revision)`, `완료` 순서로 보인다.
6. 사용자는 `수정` 컬럼이 `완료` 카드 우측에 배치되기를 원한다.
7. 신규 수주 프로젝트 또는 신규 개발팀 업무 리스트가 생성되면 자동으로 `착수 전` 컬럼에 추가되어야 한다.
8. `착수 전` 항목을 `진행 중`으로 드래그하면 단순 status 변경이 아니라, PM이 작업자를 지정하고 개별 업무를 하달하며 일정을 조정할 수 있는 workflow가 시작되어야 한다.
9. 작업자는 일정 하달을 받은 뒤 추가 일정 요청, 일정 연장 요청, 세부 작업일정 조정을 할 수 있어야 한다.
10. 현재 문서상 Plan 15/16에는 개발팀 작업, 수정 컬럼, JSON handoff, 인사카드/조직 구조가 언급되어 있으나, 실제 화면/코드 반영 여부는 항목별로 다시 검증해야 한다.

## 1. Plan 17 핵심 목표

Antigravity는 Plan 17에서 다음 목표를 달성해야 한다.

1. `/projects/intake`에 두 개의 상위 관리 탭을 만든다.
   - `수주 프로젝트 관리`
   - `개발팀 업무 리스트 관리`
2. `수주 프로젝트 관리`는 외부 수주 프로젝트(`CLIENT_ORDER`)만 생성/관리한다.
3. `개발팀 업무 리스트 관리`는 내부 개발팀 업무(`INTERNAL_DEVELOPMENT`)만 생성/관리한다.
4. 두 유형 모두 생성 직후 프로젝트 보드의 `착수 전` 컬럼에 자동으로 보인다.
5. 프로젝트 보드 상단 탭 순서를 다음과 같이 변경한다.
   - `개발팀 작업`
   - `외부 수주 프로젝트`
6. 프로젝트 보드 컬럼 순서를 다음과 같이 변경한다.
   - `착수 전`
   - `진행 중`
   - `완료`
   - `수정`
7. `수정`은 완료된 외부 수주 프로젝트 또는 완료된 내부 개발 업무에 후속 수정/재작업 요청이 있을 때만 진입하는 별도 workflow로 유지한다.
8. `착수 전`에서 `진행 중`으로 이동할 때 PM 업무 하달 workflow를 강제한다.
9. PM은 프로젝트/개발업무 단위에서 작업자를 지정하고 TaskCard를 생성하며 작업 기간을 조정할 수 있어야 한다.
10. 작업자는 하달받은 업무에 대해 추가 일정 요청, 일정 연장 요청, 세부 작업일정 조정을 신청할 수 있어야 한다.
11. PM/부서장 승인 전에는 원본 일정과 업무가 임의로 변경되지 않아야 한다.
12. 승인/반려/하달/일정변경/수정요청은 AuditLog와 Notification에 기록되어야 한다.
13. JSON export/import와 `/json` handoff에 신규 데이터 구조를 포함해야 한다.
14. QA Evidence Matrix와 Master Report를 실제 결과에 맞게 정정해야 한다.

## 2. Plan 1~16과의 연결성

### 2-1. Plan 1 기본 흐름 유지

기존 수주 프로젝트 흐름은 유지한다.

```text
수주 등록
-> PM 배정
-> 일정 초안 작성
-> 승인/반려
-> 작업 진행
-> 완료
```

Plan 17은 이 흐름 중 `수주 등록`, `착수 전`, `진행 중 전환`, `PM 작업 하달`, `작업자 일정 조정`을 더 정확하게 연결한다.

### 2-2. Plan 15/16 개발팀 작업과의 연결

Plan 15/16의 `개발팀 작업`은 외부 수주 프로젝트가 아니다.

```text
외부 수주 프로젝트 = CLIENT_ORDER
개발팀 업무 리스트 = INTERNAL_DEVELOPMENT
```

두 유형은 같은 보드/일정/결재 엔진을 사용할 수 있지만, 수주 실적과 납품일 계산은 섞지 않는다.

### 2-3. Plan 14 수정/사후 추가업무와의 연결

다음 둘은 반드시 구분한다.

```text
RevisionRequest:
- 완료된 작업물에 대한 수정/재작업 요청
- 외부 클라이언트 요청 또는 내부 검수 후 수정 요청
- 보드의 수정 컬럼으로 이동

PostDeliveryWorkRequest:
- 납품 후 내부 판단 또는 작업자/PM 판단으로 추가 업무 필요
- 사후 추가업무 및 재오픈 workflow
```

Plan 17에서 `수정` 컬럼은 `완료` 오른쪽에 둔다. 의미상 완료 이후 발생하는 후속 재작업 흐름이기 때문이다.

### 2-4. Plan 11 일정/충돌/작업자 요청과의 연결

작업자가 하달받은 일정에 대해 추가 일정 또는 세부일정 조정을 요청하는 흐름은 Plan 11의 일정 연장, 야근, 충돌 관리, 승인 workflow와 연결해야 한다.

### 2-5. Plan 13/15/16 JSON handoff와의 연결

신규 수주 프로젝트, 개발팀 업무, PM 업무 하달, TaskCard, TaskWorkSegment, ScheduleAdjustmentRequest, RevisionRequest, ApprovalRequest는 JSON export/import 대상에 포함되어야 한다.

정적 GitHub Pages 환경에서는 브라우저가 repo 파일을 직접 수정할 수 없으므로, 저장은 JSON 다운로드/수동 반영/handoff 구조로 안내한다.

## 4. 권장 데이터 모델

기존 타입을 훼손하지 말고 확장한다.

### 4-1. ProjectSourceType

```ts
type ProjectSourceType = "CLIENT_ORDER" | "INTERNAL_DEVELOPMENT";
```

규칙:

```text
CLIENT_ORDER:
- 수주 프로젝트 관리 탭에서 생성
- deliveryDate 기준
- 수주 실적에 포함

INTERNAL_DEVELOPMENT:
- 개발팀 업무 리스트 관리 탭에서 생성
- targetDate 또는 targetReleaseDate 기준
- 수주 실적에서 제외
- 개발팀 내부 backlog/work item 성격
```

### 4-2. Project status와 board column 분리

Project.status를 무조건 보드 컬럼으로 오해하지 않는다.

```ts
type ProjectBoardColumn =
  | "PRE_WORK"
  | "IN_PROGRESS"
  | "COMPLETED"
  | "REVISION";
```

권장 selector:

```ts
getProjectBoardColumn(project, revisionRequests, today)
```

규칙:

```text
신규 생성:
- status: INTAKE_RECEIVED 또는 PM_ASSIGNED
- board column: PRE_WORK

PM 업무 하달 완료 후 진행 시작:
- status: IN_PROGRESS
- board column: IN_PROGRESS

완료:
- status: COMPLETED
- board column: COMPLETED

활성 RevisionRequest 존재:
- board column: REVISION
- 단, 완료 컬럼 오른쪽에 표시
```

### 4-3. PM 업무 하달 데이터

기존 TaskCard를 우선 사용한다. 필요하면 lightweight dispatch metadata를 추가한다.

```ts
interface WorkDispatchPlan {
  id: string
  projectId: string
  sourceType: "CLIENT_ORDER" | "INTERNAL_DEVELOPMENT"
  pmId: string
  status: "DRAFT" | "DISPATCHED" | "PARTIALLY_DISPATCHED" | "CANCELLED"
  taskIds: string[]
  createdAt: string
  updatedAt: string
}
```

TaskCard 생성 시 최소 필드:

```ts
TaskCard {
  projectId
  title
  description
  scopeName?
  status: "TODO" | "READY" | "IN_PROGRESS"
  assigneeId
  pmId
  managerId
  departmentId
  startDate
  dueDate
  priority
  orderIndex
  approvalStatus
  sourceType: "PM_DISPATCH" | "INTERNAL_DEVELOPMENT_DISPATCH" | "CLIENT_ORDER_DISPATCH"
}
```

### 4-4. 작업자 일정 조정 요청

기존 ApprovalRequest를 최대한 활용하되, 세부 일정 조정 payload가 부족하면 아래 구조를 추가한다.

```ts
type ScheduleAdjustmentType =
  | "ADDITIONAL_TIME"
  | "DEADLINE_EXTENSION"
  | "WORK_SEGMENT_CHANGE"
  | "REASSIGNMENT_REQUEST"
  | "MANPOWER_SUPPORT";

interface ScheduleAdjustmentRequest {
  id: string
  projectId: string
  taskId: string
  requestedBy: string
  pmId?: string
  managerId?: string
  type: ScheduleAdjustmentType
  reason: string
  currentStartDate?: string
  currentDueDate?: string
  requestedStartDate?: string
  requestedDueDate?: string
  requestedSegments?: Array<{
    startDate: string
    endDate: string
    description: string
    estimatedHours?: number
  }>
  status: "PENDING_PM" | "PENDING_MANAGER" | "APPROVED" | "REJECTED" | "CANCELLED" | "APPLIED"
  approvalRequestId?: string
  createdAt: string
  updatedAt: string
}
```

승인 전에는 TaskCard와 TaskWorkSegment 원본을 변경하지 않는다. 승인 후에만 적용한다.

## 5. 기능 완료의 정의

Plan 17에서 완료는 단순 렌더링이 아니다. 아래가 모두 되어야 한다.

1. 신규 수주 프로젝트 생성 시 `/projects`의 외부 수주 보드 `착수 전`에 나타난다.
2. 신규 개발팀 업무 생성 시 `/projects`의 개발팀 작업 보드 `착수 전`에 나타난다.
3. 보드 탭 순서는 `개발팀 작업`, `외부 수주 프로젝트`다.
4. 보드 컬럼 순서는 `착수 전`, `진행 중`, `완료`, `수정`이다.
5. PM 또는 권한자가 `착수 전` 카드를 `진행 중`으로 드래그하면 PM 업무 하달 workflow가 열린다.
6. PM 미배정 상태에서는 진행 중 이동이 차단되거나 PM 배정 workflow로 안내된다.
7. PM은 하나 이상의 TaskCard를 만들고 작업자를 지정해야 진행 전환을 완료할 수 있다.
8. 작업자에게 할당된 TaskCard와 일정이 작업자 화면/일정표에 보인다.
9. 작업자는 할당된 업무에서 추가 일정/일정 연장/세부일정 조정 요청을 만들 수 있다.
10. 요청 승인 전에는 원본 일정이 변경되지 않는다.
11. 승인 후 TaskCard/TaskWorkSegment/PersonalSchedule 또는 관련 schedule data가 반영된다.
12. 주요 action은 Notification과 AuditLog를 남긴다.
13. JSON export/import에 신규 데이터가 포함된다.
14. lint/build가 통과한다.
15. QA Evidence Matrix와 Master Report가 실제 결과에 맞게 갱신된다.

## 6. 전역 작업 규칙

각 Phase는 반드시 다음 순서로 진행한다.

```text
분석
-> 구현
-> 자체검수
-> npm.cmd run lint
-> npm.cmd run build
-> 완료보고
-> 사용자 승인 요청
```

사용자가 승인하기 전까지 다음 Phase를 시작하지 마라.

완료 보고에는 반드시 다음을 포함한다.

```text
1. 수정한 파일
2. 구현/수정한 기능
3. 실제 확인한 사용자 시나리오
4. lint/build 결과
5. 남은 리스크
6. Git 상태
7. 다음 Phase 승인 요청
```

원격 GitHub push는 사용자 승인 전까지 절대 하지 마라.
