# WORKSPACE PLAN 9 — 최종 통합 리포트 검증, Phase 진행 통제, QA/배포 증빙 강화 프롬프트

이 프롬프트는 기존 `workspace plan1.txt`, `workspace plan2.txt`, `workspace plan3.txt`, `workspace plan4.txt`, `workspace plan5.txt`, `workspace plan6.txt`, `workspace plan7.txt`, `workspace plan8.txt` 이후에 추가되는 아홉 번째 보강 지시사항이다.

이번 Plan 9의 목적은 신규 기능을 추가하는 것이 아니라, 현재 Workspace 프로젝트가 Plan 1~8 요구사항을 실제로 어느 범위까지 반영했는지 **보고서, 검증 증빙, QA 체크리스트, 배포 안정성, Phase 진행 통제 기준**으로 정리하는 것이다.

사용자가 제공한 기존 통합 리포트는 주요 기능 요약으로는 적절하나, 다음 항목이 상대적으로 약하다.

- MVP 구현 범위와 확장 범위 구분
- 실제 데이터 저장 방식 / 로그인 / DB 전환 계획
- 검색 / 필터 / SavedView 반영 여부
- VN Excel 스케줄 데이터 검증 결과
- Data Dictionary / Status Taxonomy / Permission Scope 검증 결과
- 부재중 / 대리승인 / 업무 재배정 등 운영 예외처리
- Change Request / VersionSnapshot / 변경 전후 비교
- Soft Delete / Archive / Backup 정책
- GitHub Pages 배포 안정성 검증
- Lint / Build / Test / 커밋 해시 / 배포 URL 증빙
- Phase 범위 통제 규칙

Plan 9는 위 항목을 Antigravity가 단계별로 검토하고, 최종적으로 `Workspace 프로젝트 통합 리포트`를 보완하도록 지시한다.

---

## 0. Plan 9의 핵심 목적

Antigravity는 Plan 1~8을 모두 읽은 뒤, 다음 기준에 따라 최종 리포트와 검증 체계를 보완해야 한다.

1. 이미 구현된 기능과 설계만 반영된 기능을 구분한다.
2. MVP 범위와 확장 범위를 명확히 구분한다.
3. “완료”라는 표현은 실제 증빙이 있을 때만 사용한다.
4. Lint / Build / Test 통과 여부는 실제 실행 결과와 함께 보고한다.
5. Git 커밋 해시는 실제 커밋 후에만 보고한다.
6. GitHub Pages 배포 완료는 실제 URL 검증 후에만 보고한다.
7. 기존 리포트의 과장 표현을 보수적인 표현으로 수정한다.
8. Plan 1~8의 누락 항목을 리포트에 추가한다.
9. Phase 단위 작업 통제를 강화한다.
10. 원격 push는 사용자 승인 전까지 절대 진행하지 않는다.

---

## 1. 절대 원칙

Antigravity는 다음 원칙을 반드시 지켜라.

- Plan 9는 Plan 1~8을 대체하지 않는다.
- Plan 9는 Plan 1~8의 최종 검증 및 리포트 보강 지시사항이다.
- Plan 4의 MVP 제한 원칙을 유지한다.
- Plan 7의 데이터 사전, 권한 스코프, 테스트 매트릭스 원칙을 유지한다.
- Plan 8의 평가 모듈은 HealthScore와 EvaluationScore를 분리한다.
- 실제 검증 없이 “완벽히 통과”, “모두 적용”, “프로덕션 준비 완료”라고 쓰지 않는다.
- 증빙이 없는 항목은 “설계 반영”, “구현 예정”, “검증 필요”로 표기한다.
- Phase별 승인 없이 다음 Phase로 넘어가지 않는다.
- 사용자 승인 없이 GitHub 원격 push를 하지 않는다.
- 사용자 승인 없이 기존 리포트 파일을 덮어쓰지 않는다.
- 기존 리포트를 수정할 경우 원본 백업 또는 별도 파일로 생성한다.

## 2. 기존 통합 리포트의 수정 기준

사용자가 제공한 기존 리포트에는 다음 문장이 포함될 수 있다.

```text
지금까지의 모든 기능은 수차례의 Lint 검증 및 Next.js 정적 빌드(Export) 무결성 테스트를 완벽히 통과하였으며, 코드는 모두 origin/main (GitHub)에 동기화되어 실제 프로덕션 서버 및 GitHub Pages에 즉시 배포될 준비가 되어 있습니다.
```

이 문장은 실제 증빙이 없으면 너무 단정적이다.

### 2-1. 증빙이 없는 경우 수정 문구

실제 lint/build/test/push/deploy 증빙이 없다면 다음처럼 수정하라.

```text
현재 구현 범위는 주요 기능 단위 검증을 진행할 수 있는 구조로 정리되었으며, 최종 배포 전에는 lint/build 결과, Git 커밋 해시, GitHub Pages 배포 URL, 주요 화면별 QA 결과를 별도 체크리스트로 확인해야 합니다.
```

### 2-2. 증빙이 있는 경우 포함해야 할 정보

실제로 검증이 완료된 경우에는 다음 정보를 리포트에 반드시 포함하라.

```text
- 최종 커밋 해시
- 브랜치명
- 실행한 명령어
- lint 결과
- build 결과
- test 결과
- GitHub Pages URL
- GitHub Pages 검증 일시
- 검증한 주요 화면 목록
- 남은 리스크
```

### 2-3. 금지 표현

증빙 없이 다음 표현을 사용하지 마라.

```text
완벽히 통과
모두 반영 완료
프로덕션 준비 완료
즉시 배포 가능
문제 없음
리스크 없음
```

대신 다음 표현을 사용하라.

```text
검증 완료
검증 필요
설계 반영
구현 완료
추후 확장
배포 전 확인 필요
일부 리스크 존재
```

## 4. Phase 진행 통제 규칙

Plan 9부터는 모든 Phase 진행 시 아래 규칙을 추가로 적용한다.

### 4-1. Phase Lock 원칙

현재 진행 중인 Phase 외의 기능을 구현하지 마라.

예시:

```text
Phase 47에서는 리포트 누락 분석만 한다.
Phase 48에서는 리포트 보강 문서 초안만 작성한다.
Phase 49에서는 QA 체크리스트와 증빙 구조만 만든다.
Phase 50에서는 실제 lint/build/deploy 검증만 수행한다.
Phase 51에서는 최종 리포트를 정리한다.
Phase 52에서는 Plan 1~9 전체 최종 승인 요청만 한다.
```

현재 Phase에서 다음 Phase 기능이 필요해 보이더라도 임의로 구현하지 말고 “다음 Phase 후보 작업”으로 기록한다.

### 4-2. Phase 시작 전 필수 확인

각 Phase 시작 전 다음을 보고하라.

```text
[Phase 시작 전 확인]

1. 현재 진행할 Phase 번호
2. 이 Phase의 목표
3. 이 Phase의 구현 또는 문서화 범위
4. 수정 가능한 파일 범위
5. 수정하면 안 되는 파일 또는 기능
6. 이전 Phase 완료 여부
7. 이전 Phase 커밋 해시
8. 현재 Git 상태
9. 사용자의 명시적 승인 여부
```

사용자 승인 없이 Phase를 시작하지 마라.

### 4-3. 분석 Phase와 구현 Phase 구분

다음 Phase는 분석/검증 Phase다.

```text
Phase 47: 기존 리포트 누락 분석
Phase 50: QA 및 배포 검증
Phase 52: 최종 승인 요청
```

분석/검증 Phase에서는 코드 기능 추가를 하지 마라.

### 4-4. 중복 Plan 파일 감지

작업 폴더 안에 다음처럼 중복 Plan 파일이 있으면 사용자에게 확인하라.

```text
workspace plan1.txt
workspace plan1(2).txt
workspace plan1(3).txt
workspace plan5.txt
workspace plan5(2).txt
```

보고 형식:

```text
[중복 Plan 파일 감지]

1. 감지한 중복 파일 목록
2. 파일별 수정일
3. 파일별 크기
4. 어떤 파일을 기준으로 사용할지 사용자 확인 필요

어떤 파일을 기준으로 진행할까요?
```

사용자가 기준 파일을 지정하기 전까지 최종 리포트 보강을 진행하지 마라.

# Phase 47 — 기존 통합 리포트 누락 분석 및 증빙 필요 항목 정리

## 목표

사용자가 제공한 `Workspace 프로젝트 통합 리포트 (Plan 1 ~ Plan 8)`을 기준으로, Plan 1~8 대비 빠진 항목과 증빙이 필요한 항목을 분석한다.

## 작업

- 기존 통합 리포트 내용 확인
- Plan 1~8 요구사항과 비교
- 구현 완료 / 설계 반영 / 추후 확장 / 검증 필요 항목 구분
- 과장되거나 증빙 없는 표현 식별
- 빠진 섹션 목록 작성
- 리포트 보강 방향 제안
- Phase 48에서 작성할 문서 구조 제안

## 완료 조건

- 기존 리포트의 누락 항목이 정리됨
- 증빙이 필요한 항목이 정리됨
- 보완할 목차가 정리됨
- 사용자에게 Phase 48 진행 승인 요청

## 자체검수 항목

- Plan 1~8의 주요 요구사항이 비교 대상에 포함되었는가?
- Plan 4의 MVP 제한이 반영되었는가?
- Plan 5의 VN Excel seed 검증이 포함되었는가?
- Plan 7의 Data Dictionary / Test Matrix가 포함되었는가?
- Plan 8의 평가방식 통합이 포함되었는가?
- 증빙 없는 완료 표현이 식별되었는가?

## Git 커밋

분석 Phase이므로 코드 변경이 없다면 커밋하지 않는다.  
문서 파일을 생성한 경우에만 커밋한다.

커밋 메시지:

```text
phase-47: analyze integrated report gaps and evidence requirements
```

## Phase 47 완료 후 출력 형식

```text
[Phase 47 완료 보고]

1. 검토한 기존 리포트
2. Plan 1~8 대비 누락 항목
3. 증빙이 필요한 항목
4. 수정이 필요한 표현
5. 추가해야 할 리포트 섹션
6. 구현 완료 / 설계 반영 / 추후 확장 / 검증 필요 구분
7. 자체검수 결과
8. Git 상태
9. 커밋 메시지 및 커밋 해시 또는 커밋 생략 사유
10. 다음 단계: Phase 48 진행 승인 요청

Phase 48을 진행해도 될까요?
```

사용자가 승인하기 전까지 Phase 48을 시작하지 마라.

# Phase 48 — 보강 통합 리포트 문서 작성

## 목표

Phase 47에서 확인한 누락 항목을 반영하여, Plan 1~8 전체를 더 정확하게 설명하는 보강 통합 리포트를 작성한다.

## 작업

- `docs/integrated-workspace-report.md` 작성 또는 제안
- 기존 리포트 내용 보존
