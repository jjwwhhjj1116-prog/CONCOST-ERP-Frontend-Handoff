# WORKSPACE PLAN 10 — 프로젝트 보드 구조 재정의, 납품일 기준 우선순위, 상세라인 6단계, 직원 월간 일정표 UI 개선 프롬프트

이 프롬프트는 기존 `workspace plan1.txt`부터 `workspace plan9.txt` 이후에 추가되는 열 번째 보강 지시사항이다.

이번 Plan 10의 목적은 현재 구현된 Workspace 화면을 실제 관리자가 더 직관적으로 사용할 수 있도록 **프로젝트 보드 구조, 납품일 기준 우선순위, 보드 단계 명칭, 직원 일정표, 사이드바/전체 UI**를 재정비하는 것이다.

사용자가 제공한 4장의 화면 기준으로 다음 문제가 확인된다.

1. 좌측 메뉴바 폭이 넓어 실제 보드 영역을 과도하게 차지한다.
2. 우선순위별 현황이 실제 납품일 기준이 아니라 단순 Priority 분류처럼 보인다.
3. 모든 카드가 `진행 중`에 몰려 있어 실제 프로세스 흐름을 판단하기 어렵다.
4. 프로젝트 보드에서 직원별 세부 업무 카드가 바로 노출되어 전체 프로젝트 관리가 어렵다.
5. `KR 기획/정리`, `VN 베트남 작업`, `QA/검수` 명칭이 현재 조직 명칭과 맞지 않는다.
6. 협업 보드 / 파이프라인 보드 / 상세라인 보드가 중복되어 보드 선택 구조가 복잡하다.
7. 상세라인 보드는 기존 5단계가 아니라 실제 업무 흐름에 맞는 6단계가 필요하다.
8. 직원 일정표가 단순 리스트 형태라 월간 스케줄을 세밀하게 보기 어렵다.
9. 작업자별 부하는 프로젝트 보드가 아니라 별도 통계 탭에서 봐야 한다.
10. 납품일은 수주 프로젝트에서 입력되고, 중간에 바뀔 수 있으므로 편집 및 변경 이력이 필요하다.

Plan 10은 위 요구사항을 Plan 1~9와 충돌하지 않도록 반영한다.

---

## 0. 핵심 목표

Antigravity는 Plan 10에서 다음 목표를 반드시 달성해야 한다.

1. 좌측 사이드바 폭을 줄이고 접기/펼치기 구조를 제공한다.
2. 우선순위 보드는 수동 Priority가 아니라 **납품일 임박도** 기준으로 재정의한다.
3. 수주 프로젝트의 `deliveryDate`를 우선순위 분류 기준으로 사용한다.
4. 납품일은 최초 입력 후에도 편집 가능해야 하며, 변경 이력이 남아야 한다.
5. 프로젝트 보드는 직원별 세부 업무가 아니라 **프로젝트 카드 중심**으로 보여준다.
6. 프로젝트 카드에는 전체 프로젝트 공정률을 표시한다.
7. 프로젝트 카드를 클릭하면 세부 직원별 공정률과 업무 상세를 확인한다.
8. 기존 `KR 기획/정리`는 `CONCOST`로 변경한다.
9. 기존 `VN 베트남 작업`은 `VIET_QS`로 변경한다.
10. 기존 `QA/검수`는 `QC/검수`로 변경한다.
11. 보드 선택 드롭다운은 `협업 보드`, `상세라인 보드` 2개로 단순화한다.
12. 상세라인 보드는 6단계로 재정의한다.
13. 직원 일정표는 월간 전체 일정과 프로젝트별 전체 일정을 우선 제공한다.
14. 작업자별 부하 정보는 프로젝트 보드가 아니라 별도 통계/리포트 영역으로 이동한다.
15. Plan 1~9의 권한, 데이터 사전, 평가방식, QA 증빙 규칙과 충돌하지 않게 구현한다.

## 1. Plan 1~9와의 무결성 검토

### 1-1. Plan 1과의 연결

Plan 1의 기본 업무 흐름은 유지한다.

```text
수주 → PM 배정 → 일정 작성 → 승인/반려 → 카드형 업무 진행 → 완료
```

Plan 10은 이 흐름을 바꾸지 않는다. 단, 프로젝트 보드의 표시 단위를 다음처럼 변경한다.

```text
기존: TaskCard 중심 보드
변경: Project 중심 요약 보드 + 클릭 시 TaskCard/직원별 상세
```

TaskCard는 사라지지 않는다. 프로젝트 보드 첫 화면에서 Project Summary Card로 묶어서 보여줄 뿐이다.

### 1-2. Plan 2와의 연결

Plan 2의 선후행 업무, 변경요청, 일정 충돌, 체크리스트, 산출물 기능은 유지한다.

- 상세라인 보드에서 TaskCard 상태 흐름을 표시한다.
- 프로젝트 상세 패널에서 선후행/충돌/체크리스트/산출물을 확인한다.
- Change Request는 납품일 변경 및 일정 변경에도 연결한다.
- 납품일 변경은 승인 절차가 필요한 경우 ApprovalRequest 또는 ChangeRequest로 확장 가능하게 둔다.

### 1-3. Plan 3과의 연결

Plan 3의 권한별 화면과 인사카드 기반 권한은 유지한다.

프로젝트 보드 노출 기준:

- SUPER_ADMIN: 전체 프로젝트 카드 조회
- DEPARTMENT_MANAGER: 본인 부서 프로젝트 카드 조회
- PM: 본인 담당 프로젝트 카드 조회
- WORKER: 본인 관련 프로젝트 카드 또는 본인 업무 카드만 제한 조회

작업자는 프로젝트 전체 공정률을 볼 수 있더라도, 타인의 상세 작업량과 평가 정보는 볼 수 없다.

### 1-4. Plan 4와의 연결

Plan 4의 MVP 제한, 운영 안정성, 변경 전후 비교, soft delete, backup 정책은 유지한다.

납품일 편집 기능은 다음 원칙을 따른다.

- 납품일 변경 시 AuditLog 생성
- 변경 전/후 납품일 비교 가능
- 변경 사유 입력 권장 또는 필수
- 필요 시 VersionSnapshot 생성
- 납품일 변경 후 우선순위 버킷 자동 재계산
- 납품일 변경은 기존 Project 업데이트로 처리

### 1-5. Plan 5와의 연결

Plan 5의 VN Excel 기반 `ScheduleAssignment`는 직원 월간 일정표와 상세라인 보드에서 계속 사용한다.

프로젝트 보드 첫 화면에서는 Excel 일자별 assignment를 그대로 카드로 나열하지 않는다.

```text
ScheduleAssignment → TaskCard 묶음 → Project Summary Card
```

### 1-6. Plan 6과의 연결

Plan 6의 보드 UI, 진행도 게이지, HealthScore, Blocker는 유지한다.

Plan 10에서는 보드 표시 단위를 보완한다.

```text
Project Board 첫 화면:
- Project Summary Card
- 전체 공정률
- 납품일 임박도
- 단계별 진행 현황

Project Detail:
- 직원별 공정률
- TaskCard
- ScheduleAssignment
- Blocker
- HealthScore
```

HealthScore는 업무 리스크 지표이며, 납품일 임박도와 혼동하지 않는다.

### 1-7. Plan 7과의 연결

Plan 7의 Data Dictionary, Status Taxonomy, Permission Scope, Selector 레이어를 업데이트한다.

추가 selector 후보:

```ts
getDeliveryUrgencyBucket(project, today)
getProjectSummaryCard(projectId)
getProjectOverallProgress(projectId)
getProjectEmployeeProgress(projectId)
getVisibleProjectSummaryCards(user)
getDetailedLineStage(task)
getMonthlyScheduleMatrix(user, month)
getProjectScheduleTimeline(projectId)
getEmployeeProjectStats(userId, period)
```

### 1-8. Plan 8과의 연결

Plan 8의 평가방식은 프로젝트 보드 첫 화면에 직접 노출하지 않는다.

평가 정보는 다음 위치에서만 제한적으로 표시한다.

- 성과평가 메뉴
- 권한 있는 사용자의 프로젝트 상세 QC/평가 탭
- 작업자의 내 평가 결과 화면

### 1-9. Plan 9와의 연결

Plan 9의 리포트/QA/Phase 통제 규칙을 유지한다.  
Plan 10에서 변경한 UI/UX도 최종 리포트와 QA 증빙 매트릭스에 반영한다.

## 2. 좌측 메뉴바 및 전체 UI 개선

### 2-1. 사이드바 폭 조정

현재 좌측 메뉴바가 지나치게 넓어 보드 영역을 압박한다.

개선 기준:

```text
Desktop 기본 사이드바 폭: 220px 이하
Compact 모드 폭: 72px
Mobile: Drawer 방식
```

권장 동작:

- 기본은 현재보다 좁은 사이드바
- 접기/펼치기 버튼 제공
- 접힌 상태에서는 아이콘만 표시
- hover 또는 클릭 시 메뉴명 표시
- 현재 선택된 메뉴는 유지
- 보드 영역은 사이드바 축소 시 자동 확장

### 2-2. 보드 상단 필터 영역 개선

- 보드 제목 왼쪽 고정
- 보드 타입 드롭다운: `협업 보드`, `상세라인 보드`
- 그룹 기준 드롭다운: `단계별`, `납품일 임박도`, `담당 PM`, `부서`
- 프로젝트 선택은 필터 드롭다운보다 검색형 입력으로 변경 고려
- `Off/Day 표시`는 직원 일정표 또는 상세라인 보드에서만 의미 있게 노출
- 필터 변경 시 현재 선택 조건을 명확히 표시

### 2-3. 전체 UI 개선 방향

- 카드 여백 축소
- 빈 컬럼 높이 과도 확장 방지
- 긴 카드 목록은 내부 스크롤 대신 페이지 전체 스크롤 또는 가상화 고려
- 카드 제목 잘림 최소화
- 직원명은 `displayName > koreanAlias > name` 순서로 표시
- 색상은 상태를 구분하되 과도하게 사용하지 않는다
- 버튼/드롭다운은 동일 높이와 동일 border radius 적용

## 3. 납품일 기준 우선순위 재정의

### 3-1. 용어 변경

기존 `우선순위별 현황`은 실제로는 납품일 기준 분류여야 한다.

최종 권장 명칭:

```text
납품 임박도 현황
```

### 3-2. 납품일 기준 버킷

기존 컬럼명은 유지할 수 있으나 의미를 다음처럼 재정의한다.

```text
긴급: 납품일 초과 또는 납품 임박
높음: 납품 1주 전
보통: 납품 2주 전
낮음: 납품 예정 3주 이상
```

실제 계산 기준:

```text
긴급: deliveryDate가 지났거나 D-3 이내
높음: D-4 ~ D-7
보통: D-8 ~ D-14
낮음: D-15 이상
```

정책화:

```ts
DeliveryUrgencyPolicy {
  urgentDays: 3
  highDays: 7
  normalDays: 14
  lowFromDays: 15
}
```

### 3-3. 수동 Priority와 납품 임박도 분리

Plan 1~9의 `priority`는 삭제하지 않는다.

```text
Project.priority
- 사용자가 직접 지정하는 업무 중요도

Project.deliveryDate
- 납품 예정일

deliveryUrgencyBucket
- deliveryDate 기준으로 자동 계산되는 납품 임박도
```

### 3-4. 납품일 데이터 구조

Project에 다음 필드를 추가 또는 확인한다.

```ts
Project {
  deliveryDate?: string
  deliveryDateStatus?: "UNSET" | "SCHEDULED" | "CHANGED" | "OVERDUE" | "DELIVERED"
  deliveryDateUpdatedAt?: string
  deliveryDateUpdatedBy?: string
  deliveryDateChangeReason?: string
}
```

납품일 변경 이력 후보:

```ts
DeliveryDateChange {
  id: string
  projectId: string
  beforeDeliveryDate?: string
  afterDeliveryDate: string
  changedBy: string
  reason: string
  createdAt: string
}
```

### 3-5. 납품일 편집 권한

- SUPER_ADMIN: 전체 프로젝트 납품일 편집 가능
- DEPARTMENT_MANAGER: 본인 부서 프로젝트 납품일 편집 가능
- PM: 본인 프로젝트 납품일 변경 요청 또는 편집 가능
- WORKER: 납품일 편집 불가

변경 시 처리:

- 변경 사유 입력
- AuditLog 생성
- VersionSnapshot 생성 고려
- 관련 PM/중간관리자에게 알림
- 납품 임박도 버킷 재계산
- 보드 컬럼 자동 이동

## 4. 프로젝트 보드 구조 재정의

### 4-1. 프로젝트 보드 첫 화면 원칙

프로젝트 보드 첫 화면에는 Project Summary Card만 표시한다.

Project Summary Card 표시 정보:

```text
프로젝트명
전체 공정률
납품일
납품 임박도
현재 단계
담당 PM
담당 부서
참여 인원 수
총 TaskCard 수
완료 TaskCard 수
진행 중 TaskCard 수
PM검토 대기 수
QC검토 대기 수
Blocker 수
지연 여부
```

### 4-2. 프로젝트 전체 공정률 계산

우선순위:

```text
1. Project.progress가 수동 확정값이면 사용
2. 연결된 TaskCard progress 평균
3. 완료 TaskCard 수 / 전체 TaskCard 수
4. ScheduleAssignment 기반 일정 진행률
```

권장 selector:

```ts
getProjectOverallProgress(projectId)
```

주의:

- 모든 TaskCard가 `IN_PROGRESS`라고 해서 100%로 보지 않는다.
- 일정 소진률과 실제 공정률은 구분한다.

### 4-3. 프로젝트 카드 클릭 시 상세 보기

프로젝트 카드를 클릭하면 상세 패널 또는 상세 페이지를 연다.

상세 표시 정보:

```text
프로젝트 기본정보
납품일 및 변경 이력
전체 공정률
직원별 공정률
TaskCard 목록
ScheduleAssignment 목록
PM 검토 대기
QC 검토 대기
Blocker
산출물
Change Request
AuditLog
```

직원별 공정률 예시:

```text
[DEMO] Viet QS Team Lead 039(퐁): 45%
[DEMO] Viet QS Deputy Lead 040(늣끄엉): 20%
[DEMO] Viet QS Team Lead 042(단): 65%
```

### 4-4. 모든 카드가 진행중으로 보이는 문제 해결

상태 자동 추론 규칙:

```text
미래 일정이며 착수 기록 없음 → 작업 착수 대기
승인 완료되었고 착수 가능 → QC/PM작업착수
progress > 0 이고 완료 요청 없음 → 진행중
작업자 완료 요청 → PM검토
PM 검토 완료 후 QC 필요 → QC검토
최종 완료 → 완료
```

Excel에서 가져온 ScheduleAssignment는 기본적으로 `진행중`이 아니라 `작업 착수 대기` 또는 날짜 기준 예정 상태로 둔다.

```text
INTAKE_WAITING → 수주/대기
CONCOST → CONCOST
VIET_QS → VIET_QS
QC_REVIEW → QC/검수
COMPLETED → 완료
```

### 5-3. QA → QC 명칭 마이그레이션

기존 코드 또는 데이터에 `QA`가 있을 수 있으므로 즉시 삭제하지 말고 alias를 둔다.

```text
legacy QA_REVIEW → QC_REVIEW로 표시
legacy QA/검수 → QC/검수로 표시
```

Data Dictionary에는 다음을 명시한다.

```text
QA는 기존 레거시 명칭이며, UI에서는 QC로 통일한다.
기존 데이터 호환을 위해 QA_REVIEW 값은 QC_REVIEW와 동일하게 처리한다.
```

## 6. 보드 선택 구조 단순화

### 6-1. 기존 보드 타입 정리

기존 드롭다운:

```text
협업 보드
파이프라인 보드
상세라인 보드
```

변경 후:

```text
협업 보드
상세라인 보드
```

`파이프라인 보드`는 별도 보드 타입으로 유지하지 않는다. 필요한 기능은 협업 보드 내부 그룹 기준으로 흡수한다.

### 6-2. 그룹 기준 드롭다운

보드 타입과 그룹 기준을 분리한다.

보드 타입:

```text
협업 보드
상세라인 보드
```

그룹 기준:

```text
단계별
납품일 임박도
담당 PM
부서
```

주의:

- 우선순위별 현황은 `납품일 임박도` 그룹으로 이동한다.
- 수동 priority 그룹은 추후 필요 시 별도 옵션으로 추가한다.

### 7-4. 단계 전환 규칙

```text
작업 착수 대기
- 일정은 있지만 아직 착수 조건이 충족되지 않음
- 미래 일정
- 승인 대기 전 또는 착수 전

- PM 또는 QC가 작업 착수를 확인해야 하는 상태

- progress > 0
- 완료 요청 전

PM검토
- 작업자가 완료 요청
- PM이 검토 중

QC검토
- PM 검토 후 QC 검수가 필요한 상태
- QC 오류 등록 가능

완료
- QC 또는 최종 승인 완료
- completionStatus = COMPLETED
```

## 8. 작업자별 부하 정보 위치 변경

### 8-1. 프로젝트 보드에서 제거

프로젝트 보드에서는 `작업자별 부하`를 주요 정보로 보여주지 않는다.

이유:

- 프로젝트 보드의 목적은 프로젝트 흐름 관리다.
- 작업자별 부하 정보는 별도 통계 화면에서 보는 것이 더 명확하다.
- 보드 카드가 과도하게 복잡해지는 것을 방지한다.

### 8-2. 별도 통계 탭 추가

새 메뉴 또는 기존 직원 일정표 내부 탭으로 다음 기능을 제공한다.

```text
직원 프로젝트 통계
```

표시 정보:

```text
직원명
본인 부서
월간 프로젝트 수
연간 프로젝트 수
월간 참여 TaskCard 수
연간 참여 TaskCard 수
평균 프로젝트 연면적
총 프로젝트 연면적
최근 참여 프로젝트
평가 대상 여부
```

### 8-3. 평균 연면적 계산

Plan 8의 `ProjectScaleFactor`와 연결한다.

```text
averageGrossAreaPy = 참여 프로젝트 grossAreaPy 합계 / 참여 프로젝트 수
```

면적 정보가 없으면 다음처럼 표시한다.

```text
면적 정보 없음
```

면적 없는 프로젝트는 평균 계산에서 제외하거나 별도 경고로 표시한다. 계산 방식은 리포트에 명시한다.

프로젝트 보드 첫 화면을 세부 TaskCard 나열 방식에서 Project Summary Card 중심으로 변경한다.

## 작업

- 현재 보드 카드 데이터 소스 확인
- Project Summary Card 타입 정의
- `getProjectOverallProgress(projectId)` 구현 또는 보완
- `getProjectSummaryCard(projectId)` 구현
- `getVisibleProjectSummaryCards(user)` 구현
- 프로젝트별 전체 공정률 표시
- 납품일 표시
- 납품 임박도 표시
- 담당 PM 표시
- 부서 표시
- 참여 인원 수 표시
- TaskCard 요약 수 표시
- PM검토 / QC검토 대기 수 표시
- Blocker 수 표시
- 프로젝트 카드 클릭 시 상세 패널 또는 상세 페이지 연결

## 완료 조건

- 프로젝트 보드 첫 화면에 Project Summary Card가 표시됨
- 세부 직원 TaskCard가 첫 화면에 과도하게 나열되지 않음
- 프로젝트 전체 공정률이 표시됨
- 프로젝트 클릭 시 직원별 공정률 상세를 볼 수 있음
- 권한별 Project Summary Card 노출이 정상 작동함
- 빌드 오류 없음

## 자체검수 항목

- 작업자가 타인 프로젝트 상세를 볼 수 없는가?
- PM은 본인 프로젝트만 보는가?
- 중간관리자는 본인 부서 프로젝트만 보는가?
- 전체 공정률 계산이 하드코딩되지 않았는가?
- TaskCard 데이터가 사라지지 않고 상세에서 확인되는가?

# Phase 57 — 상세라인 보드 6단계 업무 흐름 구현

## 목표

상세라인 보드를 실제 업무 흐름에 맞게 6단계로 재정의한다.

## 작업

- 기존 상세라인 단계 확인
- DetailedLineStage 타입 또는 label map 추가
- 6단계 컬럼 구현
- 기존 TaskCard.status와 completionStatus 연결 규칙 구현
- `getDetailedLineStage(task)` selector 구현
- 단계별 카드 이동 처리
- PM검토 → QC검토 흐름 연결
- QC검토 → 완료 흐름 연결
- 기존 완료 처리 흐름과 충돌 없는지 확인
- 컬럼별 카드 수 / 평균 진행률 / 지연 수 표시

## 6단계

```text
작업 착수 대기
QC/PM작업착수
진행중
PM검토
QC검토
완료
```

## 완료 조건

- 상세라인 보드가 6단계로 표시됨
- 기존 5단계 명칭이 새 명칭으로 변경됨
- 모든 카드가 무조건 진행중에 몰리지 않음
- 완료 요청 후 PM검토로 이동 가능
- PM검토 후 QC검토로 이동 가능
- QC검토 후 완료 가능
- 빌드 오류 없음

## 자체검수 항목

- 기존 TaskCard.status가 파괴되지 않는가?
- completionStatus와 상세라인 stage가 충돌하지 않는가?
- QC검토 단계가 평가 모듈과 혼동되지 않는가?
- 카드 이동 시 AuditLog가 남는가?
- 권한 없는 사용자가 단계 이동을 할 수 없는가?

## Plan 10 추가 무결성 검토 기준

### 프로젝트 보드 무결성

- 프로젝트 보드 첫 화면이 Project Summary Card 중심인가?
- 직원별 TaskCard가 첫 화면에 과도하게 노출되지 않는가?
- 프로젝트 카드 클릭 시 세부 직원 공정률이 보이는가?
- 프로젝트 전체 공정률이 실제 TaskCard/Assignment 기반으로 계산되는가?

### 납품일 기준 우선순위 무결성

- 긴급/높음/보통/낮음이 deliveryDate 기준으로 계산되는가?
- 수동 Priority와 deliveryUrgencyBucket이 혼동되지 않는가?
- 납품일 변경 시 이력이 남는가?
- 납품일 변경 후 버킷이 자동 갱신되는가?

### 상세라인 보드 무결성

- 6단계가 정확히 표시되는가?
- 기존 TaskCard.status가 파괴되지 않는가?
- completionStatus와 detailedLineStage가 충돌하지 않는가?
- PM검토와 QC검토가 구분되는가?

### 직원 일정표 무결성

- 월간 전체 일정이 직원별/날짜별로 표시되는가?
- 프로젝트별 전체 일정이 표시되는가?
- Off/Day가 업무와 구분되는가?
- ScheduleAssignment와 PersonalSchedule이 혼동되지 않는가?

### 권한 무결성

- 작업자는 타인 상세 공정률을 볼 수 없는가?
- PM은 본인 프로젝트만 보는가?
- 중간관리자는 본인 부서만 보는가?
- 최고관리자는 전체를 보는가?
- 통계 탭에서도 권한이 유지되는가?
