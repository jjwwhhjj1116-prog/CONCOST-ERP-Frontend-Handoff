# WORKSPACE PLAN 14 — 납품일 경과 프로젝트 자동 완료 분류, 사후 추가업무 요청, 완료/재오픈 무결성 보강 프롬프트

이 프롬프트는 기존 `workspace plan1.txt`부터 `workspace plan13.txt` 이후에 추가되는 열네 번째 보강 지시사항이다.

Plan 13에서 “작은 수정은 Patch, 구조 변경은 ADR, 완전히 새로운 대형 흐름만 Plan 14”로 관리하라고 정의했지만, 이번 요구사항은 단순 문구 수정이나 UI patch가 아니다.

이번 요구사항은 다음 영역에 동시에 영향을 준다.

- Project 상태 분류
- 납품일 기준 보드 이동
- 완료 컬럼 표시 기준
- 추가 업무 요청 흐름
- 완료 후 재오픈 정책
- 작업자/PM/중간관리자 결재 흐름
- 일정 충돌 및 납품일 재산정
- Data Quality 검사
- QA Matrix 및 최종 리포트

따라서 이번 건은 Patch가 아니라 **Plan 14로 분리할 수 있는 대형 상태/업무흐름 보강**으로 본다.

---

## 0. 현재 문제

현재 화면에서 다음 문제가 확인된다.

1. 이미 납품일이 지난 프로젝트가 `진행 중` 컬럼에 남아 있다.
2. 납품일이 2026-01-15, 2026-01-20 등 과거인데도 `납품 1주일 전` 배지가 표시된다.
3. 납품일 기준으로 보면 이미 마감된 프로젝트인데, 보드상으로는 계속 진행 프로젝트처럼 보인다.
4. 모든 프로젝트가 `진행 중`에 몰려 있어 실제 운영 상태를 판단하기 어렵다.
5. 작업 중 추가 업무가 필요한 경우에는 작업자가 업무 추가 요청을 하기로 했으므로, 납품일이 지난 프로젝트를 계속 진행중에 둘 필요가 없다.
6. 다만 납품일 경과를 이유로 TaskCard의 실제 작업 이력, QC 이력, 추가업무 요청 이력을 임의로 삭제하거나 왜곡하면 안 된다.

## 1. Plan 14의 핵심 목표

Antigravity는 Plan 14에서 다음 목표를 달성해야 한다.

1. 납품일이 지난 프로젝트는 프로젝트 보드에서 `완료` 컬럼으로 분류한다.
2. 납품일이 지난 프로젝트에 `납품 1주일 전` 같은 잘못된 배지를 표시하지 않는다.
3. 납품일 경과 프로젝트에는 `납품일 경과`, `자동 완료 분류`, `추가업무 가능` 같은 명확한 상태를 표시한다.
4. 납품일 경과에 따른 완료 분류는 Project Summary Card 기준으로 처리한다.
5. TaskCard, ScheduleAssignment, TaskWorkSegment의 실제 이력은 임의로 완료 처리하지 않는다.
6. 추가 업무가 필요한 경우 작업자가 프로젝트 카드에서 추가 업무 요청을 할 수 있어야 한다.
7. 추가 업무 요청이 승인되면 프로젝트는 다시 `진행 중` 또는 `사후 추가업무 진행` 상태로 재분류될 수 있어야 한다.
8. 추가 업무 요청이 없고 납품일이 지난 프로젝트는 기본적으로 완료 컬럼에 위치한다.
9. 자동 완료 분류, 재오픈, 추가업무 승인 과정은 AuditLog와 Notification을 남긴다.
10. Plan 1~13의 상태 체계, 권한 체계, 결재 체계와 충돌하지 않도록 구현한다.

## 2. Plan 1~13과의 무결성 검토

### 2-1. Plan 1과의 연결

Plan 1의 기본 프로젝트 흐름은 유지한다.

```text
수주 → PM 배정 → 일정 작성 → 승인/반려 → 카드형 업무 진행 → 완료
```

Plan 14는 이 흐름에서 `납품일 경과`를 프로젝트 보드의 완료 분류 기준으로 추가한다.

단, 납품일 경과가 곧바로 모든 TaskCard의 작업 완료를 의미하지는 않는다.

### 2-2. Plan 2와의 연결

Plan 2의 추가 업무, 일정 변경, Change Request 흐름과 연결한다.

납품일 이후 추가 업무가 필요하면 다음 흐름을 따른다.

```text
작업자 추가업무 요청
→ PM 검토
→ 중간관리자 검토
→ 필요 시 최고관리자 검토
→ 승인 시 PostDeliveryWork 생성
→ 프로젝트 재오픈 또는 사후 추가업무 진행
```

### 2-3. Plan 3과의 연결

Plan 3의 권한 구조를 유지한다.

권한별 원칙:

```text
SUPER_ADMIN:
- 자동 완료 분류 정책 전체 관리 가능
- 모든 프로젝트 재오픈 가능

DEPARTMENT_MANAGER:
- 본인 부서 프로젝트의 사후 추가업무 승인 가능
- 본인 부서 프로젝트 재오픈 가능

PM:
- 본인 프로젝트의 추가업무 요청 검토 가능
- 본인 프로젝트 사후 추가업무 진행 관리 가능

WORKER:
- 본인에게 배정된 프로젝트 카드에서 추가업무 요청 가능
- 프로젝트 완료 상태를 직접 해제할 수 없음
```

### 2-4. Plan 4와의 연결

Plan 4의 운영 안정성, 변경 전후 비교, AuditLog, VersionSnapshot 원칙을 유지한다.

납품일 경과로 보드 컬럼이 완료로 이동하는 경우:

- selector 기반 자동 분류면 원본 데이터 변경 없이 화면상 완료 컬럼에 표시
- 실제 Project.status를 변경하는 batch action이면 AuditLog 필수
- 재오픈 시 VersionSnapshot 또는 DeliveryLifecycleLog 생성 권장

### 2-5. Plan 5와의 연결

Plan 5의 Excel 스케줄 데이터에서 생성된 프로젝트도 납품일 기준 완료 분류를 적용한다.

Excel 기반 프로젝트는 Plan 11에서 정의한 규칙을 따른다.

```text
프로젝트 최종 작업일 + 7일 = 임시 납품일
```

이 임시 납품일이 현재 날짜보다 과거면 프로젝트 보드에서는 완료 컬럼으로 이동해야 한다.

### 2-6. Plan 6과의 연결

Plan 6의 HealthScore와 진행률은 유지한다.

주의:

```text
납품일 경과로 완료 컬럼에 이동했다고 해서 HealthScore, TaskCard progress, EvaluationScore를 임의로 100%로 만들지 마라.
```

Project Summary Card에는 다음처럼 분리 표시한다.

```text
운영 상태: 납품일 경과 완료 분류
작업 공정률: 실제 TaskCard 기반 progress
추가업무: 요청 가능
```

### 2-7. Plan 7과의 연결

Plan 7의 Status Taxonomy를 훼손하지 않기 위해, Project.status를 무조건 덮어쓰지 말고 derived lifecycle selector를 우선 사용한다.

핵심 selector:

```ts
getProjectDeliveryLifecycle(project, today)
getProjectBoardColumn(project, today)
getProjectDeliveryBadge(project, today)
getCanAutoCloseProject(project, today)
getCanRequestPostDeliveryWork(user, project)
getCanReopenProject(user, project)
```

### 2-8. Plan 8과의 연결

Plan 8의 평가 모듈과 혼동하지 않는다.

납품일 경과 완료 분류는 성과평가 완료가 아니다.

```text
Delivery Closed ≠ Evaluation Locked
Delivery Closed ≠ QC Evaluation Completed
```

평가 Lock, QC 오류, EvaluationScore는 별도 흐름을 유지한다.

### 2-9. Plan 9와의 연결

Plan 9의 QA 증빙과 Phase Lock 규칙을 유지한다.

Plan 14의 자동 완료 분류 및 재오픈 흐름도 QA Evidence Matrix에 반영해야 한다.

### 2-10. Plan 10과의 연결

Plan 10의 납품일 기준 우선순위/프리셋을 보강한다.

현재 문제:

```text
납품일이 지난 프로젝트에도 "납품 1주일 전" 표시
```

수정:

```text
납품일 경과 → "납품일 경과"
D-0 ~ D-7 → "납품 1주일 전"
D-8 ~ D-14 → "납품 2주일 전"
D-15 ~ D-30 → "납품 1달 전"
deliveryDate 없음 → "미정"
```

### 2-11. Plan 11과의 연결

Plan 11의 추가 업무, 야근, 일정 연장, 충돌 관리 흐름을 유지한다.

납품일 경과 프로젝트에서 추가 업무가 필요하면 기존 형식을 깨지 않는다.

```text
작업자가 추가업무 요청
→ 결재 라우팅
→ 승인 시 추가 TaskCard 생성
→ 필요 시 deliveryDate 재산정 또는 수동 변경
→ 프로젝트가 다시 진행중으로 재분류
```

### 2-12. Plan 12와의 연결

Plan 12의 ProjectWorkPart, 직원 일정표, 프로젝트 상세 파트 보드와 연결한다.

완료 컬럼으로 이동한 프로젝트도 클릭 시 상세 이력을 볼 수 있어야 한다.

- 파트별 진행 이력
- TaskCard 이력
- ScheduleAssignment 이력
- 추가업무 요청 이력
- 납품일 변경 이력
- AuditLog

### 2-13. Plan 13과의 연결

Plan 13의 운영자 설정, 데이터 품질 검사, 권한 시뮬레이터와 연결한다.

운영자 설정에서 다음 정책을 관리할 수 있게 한다.

```text
납품일 경과 시 자동 완료 컬럼 분류 여부
납품일 경과 후 추가업무 요청 허용 여부
자동 완료 분류 적용 기준
완료 후 재오픈 승인 라인
```

데이터 품질 대시보드에서 다음 문제를 감지한다.

```text
납품일 경과인데 진행 중 컬럼에 남아 있는 프로젝트
완료 컬럼인데 추가업무 미결재가 있는 프로젝트
납품일 경과인데 배지가 "납품 1주일 전"인 프로젝트
```

## 3. 핵심 개념 분리

Plan 14에서 가장 중요한 것은 `완료`의 의미를 분리하는 것이다.

### 3-1. 운영상 완료 분류

프로젝트 보드에서 완료 컬럼에 표시되는 상태다.

```text
납품일이 지났으므로 현재 진행 프로젝트 목록에서 제외
```

### 3-2. 작업 공정 완료

TaskCard, Checklist, Progress, QC 검토 기준의 실제 작업 완료다.

```text
모든 업무가 실제로 완료되었는지 여부
```

### 3-3. 평가 완료

Plan 8의 Evaluation Lock과 QC 평가 완료다.

```text
성과평가가 확정되었는지 여부
```

### 3-4. 분리 원칙

```text
운영상 완료 분류 ≠ 작업 공정 100%
운영상 완료 분류 ≠ 평가 완료
작업 공정 완료 ≠ 납품일 경과
평가 완료 ≠ 프로젝트 보드 완료 컬럼 이동
```

## 4. Delivery Lifecycle 정의

### 4-1. DeliveryLifecycle enum

```ts
DeliveryLifecycle =
  | "UNSCHEDULED"
  | "UPCOMING"
  | "DUE_WITHIN_1_MONTH"
  | "DUE_WITHIN_2_WEEKS"
  | "DUE_WITHIN_1_WEEK"
  | "DUE_TODAY"
  | "OVERDUE"
  | "DELIVERY_CLOSED_AUTO"
  | "DELIVERY_CLOSED_MANUAL"
  | "POST_DELIVERY_WORK_REQUESTED"
  | "POST_DELIVERY_WORK_IN_PROGRESS"
  | "REOPENED"
```

### 4-2. Board Column Classification

프로젝트 보드 컬럼은 다음 기준으로 계산한다.

```ts
ProjectBoardColumn =
  | "INTAKE_WAITING"
  | "IN_PROGRESS"
  | "COMPLETED"
```

기본 규칙:

```text
수주/대기:
- PM 미배정
- 일정 미승인
- startDate 미도래
- status가 intake/waiting 계열

진행 중:
- 납품일이 오늘 이후
- 사후 추가업무 진행 중
- 승인된 추가업무가 진행 중
- 재오픈 상태

완료:
- 납품일이 오늘보다 과거
- 추가업무 요청이 없거나 모두 처리됨
- 운영상 마감 처리된 프로젝트
```

### 4-3. 날짜 기준

```text
deliveryDate < today → 납품일 경과
deliveryDate = today → 납품 당일
deliveryDate > today → 예정
```

주의:

- timezone은 `Asia/Seoul` 또는 프로젝트 설정 기준으로 통일한다.
- 날짜 비교 시 시간까지 비교하지 말고 날짜 단위로 비교한다.
- GitHub Pages 정적 환경에서도 동일하게 작동해야 한다.

## 5. 자동 완료 분류 방식

### 5-1. 권장 방식

초기 구현은 원본 Project.status를 즉시 바꾸지 말고 selector 기반으로 보드 컬럼을 계산한다.

```ts
getProjectBoardColumn(project, today)
```

즉:

```text
Project.status는 기존 값 유지
보드 표시 컬럼만 deliveryDate 기준으로 완료 컬럼에 표시
```

이렇게 해야 기존 상태 이력과 TaskCard 상태를 훼손하지 않는다.

### 5-2. 선택적 실제 마감 처리

운영자가 원하면 `자동 완료 분류 적용` 또는 `마감 처리 반영` 버튼으로 Project에 lifecycle 상태를 기록할 수 있다.

```ts
Project {
  deliveryLifecycle?: DeliveryLifecycle
  deliveryClosedAt?: string
  deliveryClosedBy?: string
  deliveryCloseReason?: string
}
```

### 5-3. 자동 완료 분류 조건

기본 조건:

```text
deliveryDate가 있음
deliveryDate < today
postDeliveryWorkRequest가 없음
openScheduleConflict가 없음
openApprovalRequest가 없음
```

단, 사용자가 명시한 방향에 따라 기본 보드 컬럼은 완료로 이동시킨다.

미결 항목이 있는 경우 완료 컬럼에 표시하되 경고 배지를 붙인다.

```text
완료 컬럼 + "미결 요청 있음"
완료 컬럼 + "충돌 미해결"
완료 컬럼 + "추가업무 검토중"
```

이렇게 하면 납품일이 지난 프로젝트가 진행중에 남는 문제를 해결하면서도, 미결 이슈를 숨기지 않는다.

## 6. 배지 표시 규칙 수정

### 6-1. 기존 문제

과거 납품일 프로젝트가 `납품 1주일 전`으로 표시된다.

### 6-2. 수정된 배지 규칙

```text
deliveryDate 없음 → 미정
deliveryDate < today → 납품일 경과
deliveryDate = today → 납품 당일
D-1 ~ D-7 → 납품 1주일 전
D-8 ~ D-14 → 납품 2주일 전
D-15 ~ D-30 → 납품 1달 전
D-31 이상 → 납품 예정
```

### 6-3. 배지 색상 의미

```text
납품일 경과: 위험/경고
납품 당일: 위험
납품 1주일 전: 경고
납품 2주일 전: 주의
납품 1달 전: 정보
납품 예정: 중립
미정: 중립/회색
```

색상은 직접 하드코딩하지 말고 기존 디자인 토큰 또는 class map을 사용한다.

## 7. 추가 업무 요청과 완료 후 재오픈

### 7-1. 사용자 판단 반영

사용자는 다음 방향을 명시했다.

```text
작업 중 추가 업무가 필요한 경우 작업자가 업무 추가 요청을 할 것이므로,
날짜가 지난 프로젝트는 완료로 넘어가도 기존 설정 형식을 깨는 것이 아니다.
```

Plan 14는 이를 반영한다.

### 7-2. PostDeliveryWorkRequest 엔티티

추가 업무 요청을 명확히 구분한다.

```ts
PostDeliveryWorkRequest {
  id: string
  projectId: string
  taskId?: string
  requestedBy: string
  title: string
  description: string
  reason: string
  requestedStartDate?: string
  requestedEndDate?: string
  estimatedHours?: number
  impactDeliveryDate?: boolean
  newSuggestedDeliveryDate?: string
  status: "DRAFT" | "PENDING_PM" | "PENDING_MANAGER" | "PENDING_SUPER_ADMIN" | "APPROVED" | "REJECTED" | "APPLIED" | "CANCELLED"
  approvalRequestId?: string
  createdAt: string
  updatedAt: string
}
```

### 7-3. 요청 흐름

```text
작업자
→ 완료 또는 진행중 프로젝트 카드 클릭
→ 추가업무 요청
→ 사유/기간/예상시간/영향 입력
→ PM 알림
→ PM 승인 또는 반려
→ 중간관리자 승인 또는 반려
→ 필요 시 최고관리자 승인
→ 승인 시 추가 TaskCard 생성
→ 프로젝트 lifecycle = POST_DELIVERY_WORK_IN_PROGRESS 또는 REOPENED
```

### 7-4. 승인 후 처리

승인 시 선택지:

```text
1. 기존 프로젝트 재오픈
2. 사후 추가업무 TaskCard만 추가
3. 납품일 재산정
4. 별도 ChangeRequest로 전환
5. 반려 후 기존 완료 유지
```

### 7-5. 보드 이동 규칙

```text
PostDeliveryWorkRequest 승인 전:
- 프로젝트는 완료 컬럼에 유지
- 배지: 추가업무 검토중

PostDeliveryWorkRequest 승인 후:
- 프로젝트는 진행 중 컬럼으로 이동
- 배지: 사후 추가업무 진행

추가업무 완료 후:
- 프로젝트는 다시 완료 컬럼으로 이동
```

## 18. Plan 14 추가 무결성 검토 기준

### 18-1. 상태 무결성

- 납품일 경과 완료 분류와 TaskCard 실제 완료가 구분되는가?
- Project.status를 임의로 덮어쓰지 않는가?
- CompletionStatus, DeliveryLifecycle, EvaluationStatus가 혼동되지 않는가?

### 18-2. 날짜 무결성

- deliveryDate < today가 정확히 납품일 경과로 처리되는가?
- deliveryDate = today가 납품 당일로 처리되는가?
- 날짜 비교가 timezone 문제 없이 날짜 단위로 처리되는가?

### 18-3. 보드 무결성

- 납품일 경과 프로젝트가 진행 중에 남지 않는가?
- 완료 컬럼에서 미결 요청/충돌이 숨겨지지 않는가?
- 완료 프로젝트도 상세 이력을 볼 수 있는가?

### 18-4. 추가업무 무결성

- 작업자가 추가업무 요청을 할 수 있는가?
- 요청이 즉시 반영되지 않고 결재를 거치는가?
- 승인 시 프로젝트가 재오픈 또는 사후 추가업무 진행 상태가 되는가?
- 반려 시 완료 상태가 유지되는가?

### 18-5. 권한 무결성

- WORKER가 타 프로젝트를 재오픈할 수 없는가?
- PM이 본인 프로젝트만 검토하는가?
- 중간관리자가 본인 부서만 승인하는가?
- SUPER_ADMIN은 전체 관리 가능한가?

## 19. Plan 14 추가 금지사항

- 납품일 경과를 이유로 모든 TaskCard progress를 100%로 만들지 마라.
- 납품일 경과를 평가 완료로 처리하지 마라.
- Project.status를 무조건 COMPLETED로 덮어쓰지 마라.
- 과거 납품일 프로젝트에 `납품 1주일 전` 배지를 표시하지 마라.
- 미결 추가업무 요청이나 충돌을 완료 컬럼에서 숨기지 마라.
- 추가업무 요청을 승인 없이 즉시 TaskCard로 반영하지 마라.
- 재오픈 이력 없이 완료 프로젝트를 진행 중으로 되돌리지 마라.
- 운영 설정 변경 이력 없이 자동 완료 정책을 바꾸지 마라.
- 사용자 승인 없이 Phase 90으로 넘어가지 마라.
- 사용자 승인 없이 GitHub 원격 push를 하지 마라.
