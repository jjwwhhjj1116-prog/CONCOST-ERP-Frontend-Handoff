# ADDITIONAL PROMPT — 통합업무관리 시스템 고도화 기획 보강 지시서

아래 내용은 기존 MASTER PROMPT에 추가되는 고도화 지시사항이다.

기존 Phase 0~8의 기본 구조를 유지하되, 다음 항목들을 설계 단계에서 반드시 고려하고, 구현은 별도 Phase로 나누어 진행하라.

중요 원칙:

* 기존 Phase 0~8을 무너뜨리지 마라.
* 기존 핵심 흐름인 “수주 → PM 배정 → 일정 작성 → 승인/반려 → 카드형 업무진행 → 완료”를 우선 유지한다.
* 아래 기능들은 한 번에 구현하지 말고 Phase 9 이후 확장 기능으로 분리한다.
* 각 Phase마다 자체검수, 무결성 검토, 빌드 테스트, Git 커밋, 사용자 승인 대기 절차를 반드시 따른다.
* 사용자 승인 없이 다음 Phase로 넘어가지 마라.

---

## 1. 추가 기획 목표

기존 시스템에 다음 기능을 보강한다.

1. 업무 선후행 관계 관리
2. 직원별 업무 과부하 감지
3. 일정 충돌 검사
4. 변경요청 관리
5. 야근/일정연장/인력지원/우선순위 조정 신청 분리
6. 카드 내부 체크리스트
7. 알림 우선순위 체계
8. 프로젝트별 산출물 관리
9. 권한/보안 세분화
10. 실제 DB·로그인·배포 확장 준비

# Phase 9 — 업무 선후행 관계 및 일정 충돌 검사

## 목표

업무 카드 간 선후행 관계를 설정하고, 직원별 일정 충돌을 감지할 수 있게 한다.

## 추가 데이터 구조

TaskCard에 다음 필드를 추가한다.

* dependencyTaskIds: 이 업무보다 먼저 완료되어야 하는 선행 업무 ID 목록
* blockedByTaskIds: 현재 업무를 막고 있는 업무 ID 목록
* estimatedHours: 예상 소요 시간
* actualHours: 실제 소요 시간
* workloadDate: 업무량 계산 기준일
* conflictStatus: 일정 충돌 상태
* dependencyStatus: 선후행 업무 상태

## 구현 기능

* 카드 상세 화면에서 선행 업무 선택 가능
* 선행 업무가 완료되지 않으면 후행 업무 착수 시 경고 표시
* 선행 업무가 지연되면 후행 업무도 위험 표시
* 직원에게 같은 날짜에 과도한 업무가 배정되면 경고 표시
* 하루 기준 8시간 초과 시 과부하 표시
* 직원별 공정표에 업무량 합계 표시
* 일정 충돌 발생 시 PM과 중간관리자에게 알림 생성

## 완료 조건

* 선행 업무 선택 가능
* 선행 업무 미완료 시 착수 경고
* 일정 충돌 감지 가능
* 직원별 일일 공수 합계 표시
* 과부하 업무 경고 표시
* 알림과 AuditLog 생성

## 자체검수 항목

* 순환 의존성이 발생하지 않는지 확인
* 완료된 선행 업무는 경고에서 제외되는지 확인
* 같은 직원에게 같은 날짜 업무가 중복될 경우 감지되는지 확인
* 과부하 기준이 명확히 표시되는지 확인
* 일정 충돌 경고가 너무 과도하게 발생하지 않는지 확인

# Phase 10 — 변경요청 Change Request 관리

## 목표

프로젝트 진행 중 발생하는 클라이언트 요청 변경, 내부 요청 변경, 일정 변경, 범위 변경을 체계적으로 관리한다.

## 추가 데이터 구조

ChangeRequest 엔티티를 추가한다.

필드 예시:

* id
* projectId
* taskId
* requestedBy
* requestType
* title
* description
* reason
* impactScope
* impactSchedule
* impactWorkload
* impactCost
* status
* reviewedBy
* reviewComment
* createdAt
* updatedAt

requestType 예시:

* CLIENT_CHANGE
* INTERNAL_CHANGE
* SCOPE_CHANGE
* SCHEDULE_CHANGE
* DESIGN_CHANGE
* BUG_FIX
* EXTRA_WORK

status 예시:

* DRAFT
* PENDING_REVIEW
* APPROVED
* REJECTED
* APPLIED
* CANCELLED

## 구현 기능

* 프로젝트 상세 화면에서 변경요청 등록
* 카드 상세 화면에서 변경요청 등록
* 변경요청 유형 선택
* 변경 사유 입력
* 일정 영향도 입력
* 업무량 영향도 입력
* 비용 영향도 입력
* 중간관리자 승인/반려
* 승인 시 관련 카드 또는 프로젝트에 반영
* 반려 시 사유 기록
* 변경요청 이력 표시
* 변경요청 발생 시 PM과 중간관리자 알림 생성

## 완료 조건

* 변경요청 등록 가능
* 변경요청 승인/반려 가능
* 승인된 변경요청만 실제 일정/업무에 반영
* 변경 이력이 프로젝트에 남음
* 변경요청 목록 확인 가능

## 자체검수 항목

* 승인되지 않은 변경요청이 실제 업무에 반영되지 않는지 확인
* 반려 사유 없이 반려 불가
* 변경요청이 관련 프로젝트/카드와 연결되는지 확인
* 변경요청 승인 후 AuditLog가 남는지 확인
* 변경요청이 중복으로 반영되지 않는지 확인

# Phase 11 — 신청 유형 세분화 및 승인 라우팅 고도화

## 목표

기존의 야근/추가일정 신청을 더 실무적으로 분리하고, 신청 유형별 승인 흐름을 다르게 처리한다.

## 신청 유형

ApprovalRequest type을 다음과 같이 세분화한다.

* OVERTIME_REQUEST: 야근 신청
* DEADLINE_EXTENSION: 일정 연장 신청
* ADDITIONAL_TASK: 업무 추가 신청
* MANPOWER_SUPPORT: 인력 지원 요청
* PRIORITY_CHANGE: 우선순위 조정 요청
* TASK_REORDER: 업무 순서 변경 요청
* SCHEDULE_REPLAN: 일정 재수립 요청

## 구현 기능

* 카드 상세 화면에서 신청 유형별 버튼 제공
* 신청 유형별 입력 폼 분리
* 야근 신청: 야근 필요 시간, 사유 입력
* 일정 연장 신청: 기존 마감일, 요청 마감일, 연장 사유 입력
* 인력 지원 요청: 필요한 인원, 필요한 기간, 지원 사유 입력
* 우선순위 조정 요청: 기존 우선순위, 요청 우선순위, 변경 사유 입력
* 업무 순서 변경 요청: 기존 순서, 요청 순서, 변경 사유 입력
* PM과 중간관리자에게 알림 생성
* PM 승인 전에도 중간관리자는 모든 신청을 미리 볼 수 있게 구현
* 승인/반려 이력 표시
* 신청 유형별 필터 제공

## 승인 라우팅 규칙

* 직원이 신청하면 PM과 중간관리자 모두 알림을 받는다.
* PM은 1차 검토자 역할을 할 수 있다.
* 중간관리자는 PM 승인 여부와 관계없이 신청 내용을 확인할 수 있다.
* 최종 승인자는 중간관리자다.
* 중간관리자가 승인하면 실제 일정 또는 카드에 반영된다.
* 반려 시 반려 사유는 필수다.

## 완료 조건

* 신청 유형별 폼 제공
* 신청 유형별 알림 생성
* PM과 중간관리자 동시 확인 가능
* 중간관리자 최종 승인 가능
* 승인 결과가 실제 업무에 반영
* 반려 사유 기록

## 자체검수 항목

* 신청 유형이 정확히 구분되는지 확인
* 승인 전 실제 일정에 반영되지 않는지 확인
* 중간관리자가 PM 승인 전에도 신청을 볼 수 있는지 확인
* 반려 사유 없이 반려할 수 없는지 확인
* 승인 후 중복 반영되지 않는지 확인

# Phase 13 — 알림 우선순위 및 에스컬레이션

## 목표

알림이 과도하게 쌓이지 않도록 우선순위를 부여하고, 중요한 알림은 상위 관리자에게 에스컬레이션되도록 한다.

## 추가 데이터 구조

Notification에 다음 필드를 추가한다.

* priority
* category
* requiresAction
* escalationLevel
* escalatedTo
* escalatedAt
* dueAt
* actionStatus

priority 예시:

* CRITICAL
* HIGH
* NORMAL
* LOW

category 예시:

* APPROVAL
* REJECTION
* DEADLINE
* SCHEDULE_CHANGE
* COMMENT
* SYSTEM
* AUDIT

## 구현 기능

* 알림 우선순위 표시
* 긴급 알림 상단 고정
* 승인 필요 알림 별도 필터
* 오늘 처리해야 하는 알림 필터
* 지연된 승인 요청 자동 강조
* 일정 마감 임박 알림
* 일정 초과 알림
* PM이 일정 시간 동안 처리하지 않은 승인 요청을 중간관리자에게 강조 표시
* 중간관리자 미처리 건을 관리자 화면에서 확인 가능하게 설계
* 읽음/안읽음 처리
* 알림 클릭 시 관련 카드 또는 승인 요청으로 이동

## 완료 조건

* 알림 우선순위 표시 가능
* 긴급 알림 구분 가능
* 승인 필요 알림 필터 가능
* 에스컬레이션 대상 알림 표시 가능
* 관련 화면 이동 가능

# Phase 14 — 실제 DB, 로그인, 권한 인증, 배포 준비

## 목표

Mock 데이터 중심의 프로토타입을 실제 운영 가능한 구조로 전환할 수 있도록 DB, 로그인, 권한 인증, 배포 준비를 진행한다.

단, 기존 프로젝트 상황에 따라 Supabase, PostgreSQL, Prisma, Firebase, SQLite 중 가장 적합한 방식을 제안한 뒤 사용자 승인을 받고 진행한다.

## 추가 무결성 검토 기준

Phase 9 이후에는 기존 무결성 검토에 더해 아래 항목을 추가로 확인한다.

### 업무 의존성 무결성

* 순환 참조가 없는가?
* 선행 업무가 삭제되었을 때 후행 업무가 깨지지 않는가?
* 선행 업무 미완료 상태에서 후행 업무가 완료 처리되지 않는가?

### 일정 무결성

* 직원별 일정 충돌이 감지되는가?
* 하루 업무량이 과도할 때 경고되는가?
* 일정 연장 승인 전 실제 마감일이 바뀌지 않는가?
* 변경요청 승인 전 업무 범위가 바뀌지 않는가?

### 승인 무결성

* 승인 요청이 중복 생성되지 않는가?
* 반려 사유가 기록되는가?
* 승인자와 요청자가 기록되는가?
* PM 승인 전에도 중간관리자가 신청을 볼 수 있는가?
* 최종 승인자가 명확한가?

### 산출물 무결성

* 산출물이 프로젝트 또는 업무 카드에 연결되는가?
* 링크가 비어 있으면 저장되지 않는가?
* 최종 산출물이 프로젝트 상세에서 확인되는가?

### 보안 무결성

* 역할별 접근 제한이 정상인가?
* 민감정보가 GitHub에 커밋되지 않았는가?
* 환경변수가 안전하게 분리되어 있는가?
* 클라이언트에게 내부 업무정보가 노출되지 않는가?

---

## 추가 금지사항

* 업무 의존성 구현 시 순환 참조 검사를 생략하지 마라.
* 일정 충돌 기능을 단순 텍스트 표시로만 끝내지 마라.
* 변경요청 승인 전 실제 업무에 반영하지 마라.
* 야근/일정연장/인력지원/우선순위 변경 신청을 하나의 모호한 폼으로 뭉개지 마라.
* 알림을 무조건 많이 생성하지 마라. 우선순위와 필터를 반드시 고려하라.
* 실제 DB 연결 시 환경변수를 코드에 직접 작성하지 마라.
* 로그인 없이 운영 가능한 것처럼 마무리하지 마라.
* 클라이언트에게 내부 승인·반려·야근 신청 정보가 노출되지 않도록 하라.

## 기존 MASTER PROMPT와의 연결 지시

이 추가 프롬프트는 기존 MASTER PROMPT의 Phase 8 이후에 이어지는 확장 Phase다.

따라서 Antigravity는 다음 순서를 반드시 지켜야 한다.

1. 기존 MASTER PROMPT의 Phase 0부터 시작
2. Phase 0~8까지 사용자 승인하에 순차 진행
3. Phase 8 완료 후 사용자에게 Phase 9 진행 여부 확인
4. 사용자가 승인할 경우에만 이 추가 프롬프트의 Phase 9부터 진행
5. Phase 14까지 완료한 뒤 최종 배포 및 GitHub push 여부를 다시 사용자에게 확인

지금 당장 Phase 9를 시작하지 마라.
현재 진행 중인 Phase가 있다면 해당 Phase를 먼저 완료하고, 사용자 승인을 받은 뒤 다음 Phase로 넘어가라.
