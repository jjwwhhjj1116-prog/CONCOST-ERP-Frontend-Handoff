# WORKSPACE PLAN 4 — MVP 범위 제한, 운영 안정성, 예외처리, 검색/복구 정책 보강 프롬프트

이 프롬프트는 기존 `workspace plan1`, `workspace plan2`, `workspace plan3` 이후에 추가되는 네 번째 보강 지시사항이다.

기존 개발 목표인 **“Notion 스타일 카드형 통합업무관리 시스템”**은 유지하되, 이번 Plan 4의 목적은 기능을 더 많이 늘리는 것이 아니라 실제 회사에서 안정적으로 운영 가능한 시스템이 되도록 다음 항목을 보강하는 것이다.

## 핵심 목표

1. MVP 범위를 명확히 제한하여 초기 개발 실패 가능성을 낮춘다.
2. 업무 완료 기준을 강화한다.
3. 부재중, 대리 승인, 퇴사자, 업무 재배정 같은 운영 예외상황을 처리한다.
4. 일정과 업무 변경 전후 비교가 가능하게 한다.
5. 검색, 필터, 저장된 뷰를 제공한다.
6. 첨부파일, 산출물, 링크 관리 기준을 강화한다.
7. 알림 피로도를 줄이기 위한 묶음 알림과 요약 알림을 제공한다.
8. 삭제, 보관, 복구, 백업 정책을 명확히 한다.
9. 클라이언트 화면은 초기 MVP에서 제외하고 추후 확장으로 분리한다.
10. 기존 Phase 흐름을 무너뜨리지 않고 Phase 18 이후 확장 단계로 구현한다.

---

## 1. 가장 중요한 개발 원칙

Antigravity는 다음 원칙을 반드시 지켜라.

- Plan 1, 2, 3, 4를 모두 읽고 전체 구조를 이해한 뒤 Phase 0부터 시작한다.
- Phase 0에서 MVP 범위와 확장 범위를 명확히 분리해서 보고한다.
- 초기 개발에서는 핵심 업무 흐름을 우선 완성한다.
- 운영 안정화 기능은 Phase 18 이후로 분리한다.
- 사용자가 승인하기 전까지 다음 Phase로 넘어가지 않는다.
- 사용자가 승인하기 전까지 GitHub 원격 push를 하지 않는다.
- 클라이언트 접속 기능은 초기 MVP에서 구현하지 않는다.
- 클라이언트 정보는 초기에는 내부 프로젝트 메타데이터로만 관리한다.
- 내부 승인, 반려, 야근, 일정 변경, 직원 개인 일정 정보가 외부에 노출되지 않도록 설계한다.

## 2. MVP 범위 제한

현재 전체 기획은 매우 크다. 따라서 Antigravity는 반드시 MVP 범위와 확장 범위를 구분해야 한다.

### 2-1. MVP Core 범위

초기 MVP에서 반드시 구현할 기능은 다음으로 제한한다.

1. Mock 데이터 기반 사용자/부서/프로젝트/업무 카드 구조
2. 역할별 대시보드
3. 수주 프로젝트 등록
4. 중간관리자 PM 배정
5. PM 일정 작성
6. 중간관리자 일정 승인/반려
7. 승인된 업무 카드 보드 표시
8. 카드 진행률 수정
9. 카드 완료 처리
10. 기본 알림 생성
11. 기본 AuditLog 생성
12. 직원별 공정표
13. 일별/주별/월별 보기
14. 부서별 필터
15. 권한별 데이터 노출 제한

### 2-2. MVP에서 제외할 기능

다음 기능은 초기 MVP에서 구현하지 말고 확장 Phase로 분리한다.

- 실제 클라이언트 로그인
- 클라이언트 포털
- 실제 파일 업로드 스토리지
- 실시간 채팅
- 이메일/SMS/카카오톡 외부 알림 연동
- ERP/그룹웨어 연동
- 결재 문서 자동 생성
- 복잡한 비용 정산
- 급여/근태 시스템 연동
- AI 자동 일정 배정
- 캘린더 외부 연동
- 모바일 앱 별도 개발

### 2-3. MVP Gate

Antigravity는 Phase 0에서 반드시 다음 내용을 보고해야 한다.

```text
[MVP Gate 보고 필수 항목]

1. MVP Core에 포함할 기능
2. MVP에서 제외할 기능
3. Phase 0~8에서 반드시 끝낼 기능
4. Phase 9 이후로 미룰 기능
5. Phase 18 이후 운영 안정화로 미룰 기능
6. 현재 코드베이스에서 MVP 구현에 가장 위험한 부분
7. 기능 과잉 구현 방지 계획
```

## 3. 업무 완료 기준 강화

현재 업무 카드는 완료 처리 기능이 있지만, 실무에서는 단순히 작업자가 완료 버튼을 누르는 것만으로는 부족하다.

업무 완료는 다음 기준을 충족해야 한다.

### 3-1. 완료 단계

`TaskCard`에 `completionStatus`를 추가한다.

`completionStatus` 예시:

- `NOT_STARTED`
- `IN_PROGRESS`
- `WORKER_DONE`
- `PM_REVIEWING`
- `PM_APPROVED`
- `MANAGER_REVIEWING`
- `MANAGER_APPROVED`
- `COMPLETED`
- `REOPENED`
- `REJECTED`

### 3-2. 완료 처리 흐름

기본 완료 흐름:

1. 작업자가 업무 진행률을 100%로 변경
2. 작업자가 완료 요청
3. 상태는 `WORKER_DONE`으로 변경
4. PM에게 검토 알림 생성
5. PM이 검토 후 승인 또는 반려
6. PM 승인 시 업무 성격에 따라 중간관리자 검토로 이동
7. 중간관리자 최종 승인 시 `COMPLETED` 처리
8. 완료일 `completedAt` 자동 기록
9. 완료 처리 `AuditLog` 생성

간단한 업무는 PM 승인만으로 완료 가능하게 설계한다.

중요 업무는 중간관리자 최종 승인까지 요구할 수 있도록 `requiresManagerFinalReview` 필드를 준비한다.

### 3-3. 완료 시 필수 조건

업무 완료 전 다음 조건을 검증한다.

- 진행률 100%
- 완료 메모 입력
- 산출물 링크 또는 파일 등록
- 체크리스트가 있는 경우 필수 체크리스트 완료
- 미해결 변경요청이 없을 것
- 미처리 승인 요청이 없을 것
- 지연된 경우 지연 사유 입력
- 완료 처리자 기록
- 완료일 자동 기록

### 3-4. 추가 데이터 구조

`TaskCard`에 다음 필드를 추가 또는 고려한다.

- `completionStatus`
- `completionRequestedBy`
- `completionRequestedAt`
- `completionMemo`
- `pmReviewedBy`
- `pmReviewedAt`
- `pmReviewComment`
- `managerFinalReviewedBy`
- `managerFinalReviewedAt`
- `managerFinalReviewComment`
- `requiresPmReview`
- `requiresManagerFinalReview`
- `reopenedReason`
- `reopenedAt`
- `completedAt`

## 4. 부재중, 대리 승인, 업무 재배정

실제 운영에서는 담당자가 휴가, 출장, 퇴사, 부서 이동 상태일 수 있다. 따라서 부재 및 대리 승인 구조를 준비해야 한다.

### 4-4. 운영 규칙

- 부재중인 사용자에게 신규 업무 배정 시 경고 표시
- 부재중인 승인자에게 승인 요청이 들어오면 대리 승인자에게도 알림 생성
- 대리 승인자가 승인한 경우 `AuditLog`에 “대리 승인”으로 기록
- 퇴사 또는 비활성 직원에게 신규 업무 배정 금지
- 비활성 직원이 담당하던 업무는 재배정 필요 목록에 표시
- PM 부재 시 임시 PM 지정 가능
- 중간관리자 부재 시 대리 승인자 지정 가능
- 대리 권한은 기간이 지나면 자동 만료

## 5. 변경 전후 비교 및 버전 스냅샷

`AuditLog`만으로는 실무자가 변경 내용을 한눈에 보기 어렵다. 따라서 변경 전후 비교 화면을 제공해야 한다.

### 5-1. VersionSnapshot 엔티티 추가

`VersionSnapshot`:

- `id`
- `entityType`
- `entityId`
- `versionNumber`
- `snapshotData`
- `createdBy`
- `createdAt`
- `reason`

`entityType` 예시:

- `PROJECT`
- `TASK_CARD`
- `SCHEDULE_PLAN`
- `PERSONAL_SCHEDULE`
- `APPROVAL_REQUEST`
- `CHANGE_REQUEST`

### 5-2. 변경 전후 비교 기능

필수 기능:

- 변경 전 값 표시
- 변경 후 값 표시
- 변경자 표시
- 변경일 표시
- 변경 사유 표시
- 변경된 필드만 강조
- 일정 변경 시 이전 일정과 변경 일정 비교
- 담당자 변경 시 이전 담당자와 변경 담당자 비교
- 상태 변경 시 이전 상태와 변경 상태 비교
- 우선순위 변경 시 이전 우선순위와 변경 우선순위 비교

### 5-3. 복구 준비

초기 구현에서는 실제 복구까지 강제하지 말고, 복구 가능한 구조를 준비한다.

필드 및 규칙:

- `canRestore`
- `restoredFromVersionId`
- `restoredBy`
- `restoredAt`
- `restoreReason`

중요 규칙:

- 완료된 프로젝트는 복구 전 관리자 확인 필요
- 승인된 일정은 복구 시 다시 승인 요청 상태로 전환할 수 있게 설계
- 복구도 `AuditLog`에 남긴다

## 7. 첨부파일 및 산출물 관리 강화

Plan 2의 산출물 관리 기능을 보강한다.

초기 MVP에서는 실제 파일 업로드를 무리하게 구현하지 말고, 우선 URL 기반 산출물 관리로 시작한다.

실제 파일 업로드는 DB/스토리지 구조가 확정된 후 진행한다.

### 7-1. Attachment 엔티티 추가

`Attachment`:

- `id`
- `projectId`
- `taskId`
- `approvalRequestId`
- `changeRequestId`
- `uploadedBy`
- `attachmentType`
- `title`
- `fileName`
- `fileUrl`
- `mimeType`
- `fileSize`
- `storageProvider`
- `description`
- `isRequired`
- `isDeleted`
- `createdAt`
- `updatedAt`
- `deletedAt`

`attachmentType` 예시:

- `CONTRACT`
- `CLIENT_REQUEST`
- `ESTIMATE`
- `DRAWING`
- `PLANNING_DOC`
- `SCREENSHOT`
- `DESIGN_FILE`
- `QA_EVIDENCE`
- `FINAL_DELIVERABLE`
- `MEETING_NOTE`
- `GITHUB_LINK`
- `DEPLOY_URL`
- `ETC`

### 7-2. 첨부자료 운영 규칙

- 수주 프로젝트에는 최소 1개 이상의 요청 자료 또는 설명이 있어야 한다.
- 완료 업무에는 산출물 링크 또는 완료 메모가 있어야 한다.
- QA 반려 시 오류 캡처 또는 반려 메모를 남길 수 있어야 한다.
- 첨부자료 삭제는 실제 삭제가 아니라 `isDeleted` 처리한다.
- 삭제 이력은 `AuditLog`에 남긴다.
- 외부 공유 가능한 자료와 내부 전용 자료를 구분한다.

### 7-3. 보안 분류

`Attachment`에 `visibility` 필드를 추가 고려한다.

`visibility` 예시:

- `INTERNAL_ONLY`
- `PROJECT_MEMBERS`
- `DEPARTMENT_ONLY`
- `MANAGER_ONLY`
- `CLIENT_VISIBLE`
- `SUPER_ADMIN_ONLY`

초기에는 `CLIENT_VISIBLE`을 사용하지 말고, 추후 클라이언트 포털 구현 시에만 활성화한다.

## 8. 알림 피로도 방지

알림은 많아질수록 실무 피로도가 증가한다. 따라서 알림 우선순위뿐 아니라 묶음 처리와 요약 알림이 필요하다.

### 8-1. NotificationPreference 엔티티 추가

`NotificationPreference`:

- `id`
- `userId`
- `immediateCritical`
- `immediateApproval`
- `immediateRejection`
- `immediateDeadline`
- `digestComments`
- `digestProgressChanges`
- `digestReorderChanges`
- `dailyDigestEnabled`
- `weeklyDigestEnabled`
- `quietHoursStart`
- `quietHoursEnd`
- `createdAt`
- `updatedAt`

### 8-2. DigestNotification 엔티티 추가

`DigestNotification`:

- `id`
- `userId`
- `digestType`
- `title`
- `summary`
- `itemCount`
- `relatedNotificationIds`

- `periodEnd`

`digestType` 예시:

- `DAILY`

- `REORDER_SUMMARY`

### 8-3. 즉시 알림 대상

다음 알림은 즉시 표시한다.

- 승인 요청
- 반려
- 오늘 마감
- 일정 초과
- 긴급 업무 배정
- 야근/추가일정 승인 필요
- PM 일정 변경 중 중요 일정
- 업무 재배정
- 대리 승인 요청

### 8-4. 묶음 알림 대상

다음 알림은 묶음 처리할 수 있다.

- 댓글
- 진행률 변경
- 카드 순서 변경
- 일반 상태 변경
- 산출물 추가
- 체크리스트 변경

### 8-5. 알림 피로도 방지 규칙

- 같은 카드의 진행률 변경 알림은 일정 시간 내 중복 생성하지 않는다.
- 카드 순서 변경이 여러 번 발생하면 하나의 요약 알림으로 묶는다.
- 긴급/승인/반려 알림은 끌 수 없다.
- 일반 댓글/진행률/순서 변경 알림은 요약 알림으로 전환 가능하다.
- 최고관리자와 중간관리자는 부서 요약 리포트를 받을 수 있다.
- 작업자는 본인 업무 관련 알림만 받는다.

### 9-3. 복구 규칙

- 복구 후 `AuditLog` 생성

- 완료 프로젝트 복구 시 관련 업무 카드도 함께 복구할지 선택 가능해야 한다.

## 10. 클라이언트 화면 정책

초기에는 클라이언트 화면을 만들지 않는다.

클라이언트는 프로젝트의 외부 요청 주체로만 관리한다.

### 10-1. 초기 정책

- 클라이언트 로그인 없음
- 클라이언트 포털 없음
- 클라이언트에게 내부 업무정보 노출 없음
- 클라이언트명, 담당자명, 연락처, 요청사항만 내부에서 관리
- 내부 승인/반려/야근/개인 일정 정보는 절대 클라이언트 표시 대상이 아님

### 10-2. Client 엔티티 준비

`Client`:

- `id`
- `companyName`
- `contactName`
- `contactEmail`
- `contactPhone`
- `memo`
- `createdAt`
- `updatedAt`

`Project`에는 `clientId`를 연결할 수 있게 설계한다.

### 10-3. 추후 확장 가능 기능

클라이언트 포털은 추후 별도 Phase로 분리한다.

가능한 확장 기능:

- 클라이언트 프로젝트 진행률 제한 조회
- 클라이언트 변경요청 등록
- 클라이언트 검수 피드백
- 클라이언트 첨부파일 업로드
- 클라이언트용 완료 보고서 다운로드

단, 이 기능들은 사용자가 명시적으로 승인하기 전까지 구현하지 않는다.

## 기존 프롬프트와의 연결 지시

이 프롬프트는 기존 `workspace plan1`, `workspace plan2`, `workspace plan3` 이후에 추가되는 네 번째 보강 프롬프트다.

Antigravity는 다음 순서를 반드시 지켜야 한다.

1. `workspace plan1`의 MASTER PROMPT를 우선 기준으로 삼는다.
2. `workspace plan2`의 고도화 요구사항을 함께 반영한다.
3. `workspace plan3`의 권한별 화면, 인사카드, 개인 일정 요구사항을 함께 반영한다.
4. 이 `workspace plan4`의 MVP 제한, 운영 안정성, 예외처리, 검색/복구 정책도 Phase 0 분석 단계부터 함께 고려한다.
5. 단, 기능 구현은 기존 Phase 순서를 무너뜨리지 않는다.
6. Phase 0에서는 MVP 범위와 확장 범위를 반드시 분리해서 보고한다.
7. Phase 1 데이터 모델 설계 시 `completionStatus`, soft delete, basic policy fields를 선반영한다.
8. Phase 8 최종 QA에서는 완료 기준, 삭제 정책, 알림 정책이 누락되지 않았는지 확인한다.
9. Phase 14 실제 DB/로그인 설계 시 백업, soft delete, 권한별 검색 제한을 반드시 고려한다.
10. Phase 18~25는 운영 안정화 확장 구현 단계로 분리한다.
11. 사용자 승인 없이 다음 Phase로 넘어가지 않는다.
12. 사용자 승인 없이 원격 저장소에 push하지 않는다.
