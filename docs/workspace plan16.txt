# WORKSPACE PLAN 16 — 마스터 리포트 V2와 실제 화면 불일치 복구, JSON/인사카드/조직/보드/대시보드 실반영 검증 프롬프트

이 프롬프트는 기존 `workspace plan1.txt`부터 `workspace plan15.txt` 이후에 추가되는 열여섯 번째 보강 지시사항이다.

Plan 16의 목적은 새로운 기능을 무작정 늘리는 것이 아니라, Antigravity가 제출한 `workspace_master_report_v2.md`에서 “반영 완료” 또는 “구현 완료”처럼 표현된 항목이 실제 화면과 코드에서 제대로 반영되지 않은 문제를 바로잡는 것이다.

사용자가 제공한 현재 화면 기준으로 다음 문제가 다시 확인된다.

1. `납품일 임박도 현황`에서 `미정` 컬럼이 우측으로 밀려 있고, 불필요한 가로 스크롤 또는 남는 여백 문제가 남아 있다.
2. 대시보드에 아직 `진행 중 프로젝트 요약` 문구가 남아 있으며, `월별 프로젝트 요약`과 월별 드롭다운이 명확히 적용되지 않았다.
3. 더미데이터가 계속 실사용 화면에 노출되고 있다.
4. 웹에서 수정한 자료를 JSON으로 저장하고 `/json` 폴더를 통해 Antigravity가 다시 반영하는 흐름이 실제 사용 가능한 수준인지 불명확하다.
5. 인사카드 편집/저장 기능이 실제 일정표 기준 데이터로 연결되었는지 불명확하다.
6. CON-COST / Viet_QS 조직구조와 세부 부서가 실제 UI와 데이터 구조에 반영되었는지 불명확하다.
7. `수주 프로젝트` 하위의 `개발팀 작업` 카테고리가 실제로 적용되었는지 불명확하다.
8. 프로젝트 보드 컬럼의 `수주/대기 → 작업 착수 전`, `수정` 컬럼 추가가 실제 화면에 반영되었는지 불명확하다.
9. 마스터 리포트 V2는 “반영됨”이라고 말하지만, 실제 화면 스크린샷과 불일치가 있으므로 완료 증빙으로 볼 수 없다.

따라서 Plan 16은 **마스터 리포트와 실제 화면/코드 간 불일치 복구 전용 Plan**이다.

---

## 0. Plan 16의 핵심 원칙

Antigravity는 Plan 16에서 아래 원칙을 반드시 지켜야 한다.

1. `workspace_master_report_v2.md`는 완료 증빙이 아니라 점검 대상이다.
2. 실제 코드, route, store, selector, 화면 텍스트, CSS, JSON 파일 존재 여부를 확인한 뒤 완료 여부를 판단한다.
3. 화면에 반영되지 않은 항목은 리포트에 완료라고 적혀 있어도 미완료로 본다.
4. 더미데이터는 실사용 모드에서 기본 노출하지 않는다.
5. JSON 저장은 실제 GitHub Pages에서 저장소 파일을 직접 수정하는 것으로 표현하지 않는다.
6. 정적 웹 환경에서는 `JSON 내보내기/download`와 `/json` 폴더 수동 반영 흐름을 명확히 안내한다.
7. 인사카드는 단순 명단이 아니라 일정표/권한/조직/결재의 기준 데이터로 사용한다.
8. 조직구조는 CON-COST와 Viet_QS의 실제 역할 차이를 반영해야 한다.
9. 보드/대시보드의 문구, 컬럼, 필터는 실제 화면에서 확인 가능해야 한다.
10. 완료 보고에는 반드시 실제 수정 파일, 확인 화면, lint/build 결과, 남은 리스크를 포함한다.

## 1. Plan 1~15 및 마스터 리포트 V2와의 무결성 검토

### 1-1. 마스터 리포트 V2의 현재 주장

`workspace_master_report_v2.md`에는 다음과 같은 내용이 포함되어 있을 수 있다.

```text
- CON-COST 및 Viet_QS 조직 구조 반영
- 인사카드(Personnel Card) 연동
- 외부 수주와 내부 개발 프로젝트 분리
- 보드 4단 컬럼: 작업 착수 전 → 진행 중 → 수정 → 완료
- 납품일 임박도 현황 Grid 레이아웃 최적화
- JSON Handoff
```

그러나 사용자의 실제 화면에서는 위 내용이 완전히 적용되지 않은 것으로 보인다.

따라서 Plan 16에서는 다음 원칙을 적용한다.

```text
문서상 완료 ≠ 실제 완료
코드상 타입 존재 ≠ UI 반영 완료
UI 문구 변경 ≠ 데이터 흐름 완성
JSON 파일 존재 ≠ import/export 완료
```

### 1-2. Plan 13의 요구사항 관리 원칙과의 관계

Plan 13에서 작은 수정은 Patch로 처리하라고 했지만, 이번 건은 단순 patch가 아니다.

이유:

- 마스터 리포트와 실제 화면 사이에 체계적 불일치가 있다.
- JSON 저장, 인사카드, 조직구조, 프로젝트 카테고리, 보드 컬럼, 대시보드, CSS 레이아웃이 서로 연결되어 있다.
- 실사용 데이터 전환과 권한/일정표 기반 데이터에 영향을 준다.

따라서 Plan 16은 **Discrepancy Recovery Plan**, 즉 불일치 복구 Plan으로 분리한다.

## 3. 반드시 복구해야 할 항목

### 3-1. 실사용 모드 더미데이터 제거

요구사항:

```text
이제 더미데이터들은 날릴 것.
실사용 모드에서 demo/seed 프로젝트가 실제 데이터처럼 보이면 안 됨.
```

구현 원칙:

- 실사용 모드에서는 기본 데이터 소스를 `JSON 운영 데이터`로 둔다.
- JSON 운영 데이터가 없으면 빈 상태를 보여준다.
- demo/seed 데이터는 운영 검증 모드 또는 개발 모드에서만 선택 가능하게 한다.
- 현재 데이터 소스를 화면에 표시한다.

데이터 소스:

```ts
DataSourceMode =
  | "JSON_OPERATION_DATA"
  | "EXCEL_IMPORT_DATA"
  | "DEMO_SEED_DATA"
  | "EMPTY";
```

기본값:

```text
실사용 모드: JSON_OPERATION_DATA → 없으면 EMPTY
운영 검증 모드: DEMO_SEED_DATA 선택 가능
```

금지:

- JSON이 없다고 조용히 demo data로 fallback하지 마라.
- 실사용 모드에서 demo 프로젝트를 실제 프로젝트처럼 표시하지 마라.

### 3-2. JSON 저장/불러오기/Handoff 실사용 구조

요구사항:

```text
웹에서 편집한 만큼 수정한 자료를 저장할 수 있게 버튼 추가.
저장한 다음 별도 /json 폴더에 올리고 Antigravity가 읽어 반영 가능하게 구성.
```

정적 웹 환경 원칙:

```text
GitHub Pages에서는 웹에서 repo 파일을 직접 수정할 수 없다.
따라서 “저장”은 파일 다운로드/export로 구현한다.
사용자가 해당 JSON을 /json 폴더에 복사하고,
Antigravity가 이를 import script로 읽어 반영한다.
```

필수 UI:

```text
JSON으로 내보내기
JSON 불러오기 미리보기
적용 전 검증
현재 데이터 소스 표시
/json 폴더 반영 안내
```

필수 파일 구조:

```text
json/
  organization.json
  personnel-cards.json
  projects.json
  project-categories.json
  revision-requests.json
  workspace-settings.json
  schedule-visibility-rules.json
  approval-workflow-templates.json
  README.md
```

필수 script:

```text
scripts/validate-json-data.ts
scripts/import-json-data.ts
scripts/export-current-state.ts
```

필수 안내 문구:

```text
현재 정적 배포 환경에서는 웹에서 수정한 데이터를 JSON 파일로 내보낸 뒤,
프로젝트의 /json 폴더에 저장하고 Antigravity에게 반영을 요청해야 합니다.
```

### 3-3. 인사카드 웹 편집 및 일정표 기준 데이터 연결

요구사항:

```text
인사카드를 웹에서 수정 가능하게 한다.
인사카드를 JSON으로 저장한다.
해당 인사카드를 기반으로 일정표를 짠다.
```

필수 구현:

- 인사카드 관리 화면
- 직원 추가/수정/비활성화
- 회사/부서/세부부서/팀 선택
- 직급/직책/역할 선택
- 일정 조회 권한 설정
- 결재 상위자 연결
- JSON export/import
- 직원 일정표가 PersonnelCard 기준으로 행 생성

PersonnelCard canonical field:

```ts
PersonnelCard {
  id: string
  employeeNumber?: string
  companyId: "con-cost" | "viet-qs"
  companyName: "CON-COST" | "Viet_QS"
  departmentId: "finishing" | "structure" | "civil" | "develop"
  departmentName: "마감" | "구조" | "토목" | "개발"
  subDepartmentId?: string
  subDepartmentName?: string
  teamId?: string
  teamName?: string
  name: string
  displayName: string
  koreanAlias?: string
  vietnameseName?: string
  email?: string
  systemRole: "SUPER_ADMIN" | "DEPARTMENT_MANAGER" | "PM" | "WORKER"
  organizationRank: "CEO" | "VICE_PRESIDENT" | "MANAGER" | "PM" | "TEAM_LEADER" | "DEPUTY_TEAM_LEADER" | "STAFF" | "TRAINEE"
  jobTitle?: string
  managerId?: string
  pmId?: string
  employmentStatus: "ACTIVE" | "INACTIVE" | "ON_LEAVE" | "RESIGNED"
  canDirectEstimate?: boolean
```

주의:

- Viet_QS 팀장은 PM 역할이 아니라 현장/부서 실행 리더일 수 있다.

### 3-5. `수주 프로젝트` 하위 `개발팀 작업` 카테고리

요구사항:

```text
수주프로젝트 하단에 개발팀 작업 카테고리 추가.
개발팀 작업은 수주 받은 프로젝트가 아니라 내부 진행 업무.
```

Canonical enum:

```ts
ProjectSourceType = "CLIENT_ORDER" | "INTERNAL_DEVELOPMENT";
```

Legacy alias 처리:

```text
CLIENT_PROJECT → CLIENT_ORDER
DEVELOPMENT_WORK → INTERNAL_DEVELOPMENT
```

UI 구조:

```text
수주 프로젝트
  - 외부 수주 프로젝트
  - 개발팀 작업
```

원칙:

- 내부 개발팀 작업은 수주 실적에 포함하지 않는다.
- 내부 개발팀 작업도 일정표, 결재, 알림, 진행률, 담당자 배정은 사용할 수 있다.
- 내부 개발팀 작업은 deliveryDate 대신 targetReleaseDate를 사용할 수 있다.

### 3-7. 납품일 임박도 현황 레이아웃 실수정

현재 문제:

```text
미정 컬럼이 화면 오른쪽으로 밀리고, 좌우 공간이 남는데도 스크롤이 필요해 보임.
```

수정 원칙:

- 4개 컬럼은 컨테이너 안에서 균등 배치한다.
- 전체 보드에 불필요한 horizontal scroll을 넣지 않는다.
- 각 컬럼 내부 카드 리스트만 세로 스크롤한다.
- 1440px 이상 desktop 화면에서는 4개 컬럼이 한 화면에 보여야 한다.
- 사이드바 너비와 함께 계산한다.

권장 CSS:

```css
.delivery-board-grid {
  display: grid;
  grid-template-columns: repeat(4, minmax(0, 1fr));
  gap: 16px;
  width: 100%;
  max-width: 100%;
  overflow-x: hidden;
}

.delivery-board-column {
  min-width: 0;
  overflow: hidden;
}

.delivery-board-card-list {
  overflow-y: auto;
  overflow-x: hidden;
}
```

반응형:

```text
>= 1280px: 4열
768px ~ 1279px: 2열
< 768px: 1열
```

금지:

- column에 `min-width: 300px` 이상을 고정해서 전체 overflow를 만들지 마라.
- wrapper에 불필요한 `overflow-x: auto`를 넣지 마라.
- 오른쪽 빈 공간을 방치하지 마라.

### 3-8. 대시보드 `월별 프로젝트 요약` 실반영

현재 화면 문제:

```text
진행 중 프로젝트 요약 문구가 남아 있음.
```

변경:

```text
진행 중 프로젝트 요약 → 월별 프로젝트 요약
```

## 13. Plan 16 추가 금지사항

- 마스터 리포트에 적혀 있다는 이유만으로 완료 처리하지 마라.
- 실제 화면에서 확인하지 않고 완료라고 보고하지 마라.
- 실사용 모드에서 demo data를 실제 데이터처럼 보여주지 마라.
- JSON 저장 기능을 실제 서버 저장처럼 오해하게 만들지 마라.
- GitHub Pages에서 웹이 repo 파일을 직접 수정할 수 있다고 가정하지 마라.
- 인사카드를 일정표와 연결하지 않은 채 UI만 만들지 마라.
- 조직구조 없이 role 문자열만으로 권한을 처리하지 마라.
- 개발팀 작업을 수주 실적에 섞지 마라.
- RevisionRequest와 PostDeliveryWorkRequest를 혼동하지 마라.
- `수주/대기` 문구를 남기지 마라.
- `진행 중 프로젝트 요약` 문구를 남기지 마라.
- 납품일 임박도 현황에서 `미정` 컬럼이 화면 밖으로 밀리게 하지 마라.
- 사용자 승인 없이 Phase 115로 넘어가지 마라.
- 사용자 승인 없이 GitHub 원격 push를 하지 마라.
