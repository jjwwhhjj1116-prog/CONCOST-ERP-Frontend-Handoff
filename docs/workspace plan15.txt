# WORKSPACE PLAN 15 — Dummy Data 제거, JSON 저장/반영 체계, 인사카드 편집, 조직/프로젝트 분류, 보드/대시보드 UI 보강 프롬프트

이 프롬프트는 기존 `workspace plan1.txt`부터 `workspace plan14.txt` 이후에 추가되는 열다섯 번째 보강 지시사항이다.

Plan 15의 목적은 현재까지 만든 Workspace를 실제 테스트 가능한 운영형 구조로 전환하는 것이다.

이번 Plan 15에서는 기존 더미데이터 중심 구조를 정리하고, 웹 화면에서 수정한 자료를 JSON으로 저장/export한 뒤 Antigravity가 해당 JSON을 읽어 코드/데이터에 반영할 수 있는 구조를 만든다.

또한 인사카드 편집, CON-COST / Viet_QS 조직 구조, 개발팀 작업 카테고리, 프로젝트 보드 컬럼명 변경, 수정 작업 컬럼, 월별 프로젝트 요약, 보드 가로 스크롤 문제를 함께 보강한다.

---

## 0. 현재 문제와 요구사항

현재 화면 기준으로 다음 문제가 확인된다.

1. 더미데이터 프로젝트가 많이 쌓여 있고, 실제 테스트 전에는 제거 또는 비활성화가 필요하다.
2. GitHub Pages 또는 정적 저장소에서는 사용자가 웹에서 수정한 내용이 자동으로 GitHub 저장소에 저장되지 않는다.
3. 웹에서 수정한 인사카드, 프로젝트, 설정, 조직구조를 JSON으로 export한 뒤 Antigravity가 읽어서 반영할 수 있어야 한다.
4. 인사카드를 임시로 웹에서 수정 가능하게 하고, 해당 인사카드 기반으로 일정표를 구성해야 한다.
5. `수주 프로젝트` 하단에 내부 업무 성격의 `개발팀 작업` 카테고리를 추가해야 한다.
6. 프로젝트 보드의 `수주/대기` 문구를 `작업 착수 전`으로 변경해야 한다.
7. `완료` 옆에 `수정` 카드 영역을 추가해야 한다.
8. `수정`은 기존 납품/완료 프로젝트가 클라이언트 요청으로 재작업되는 상태를 의미한다.
9. `납품일 임박도 현황`에서 `미정` 컬럼이 스크롤을 넘겨야 보이는 문제가 있다. 좌우 공간이 남는 경우에는 스크롤 없이 한 화면에 보이도록 해야 한다.
10. 대시보드의 `진행 중 프로젝트 요약` 문구를 `월별 프로젝트 요약`으로 바꾸고 월별 드롭다운을 추가해야 한다.
11. 회사 조직 구조를 실제 CON-COST / Viet_QS 구조에 맞게 반영해야 한다.
12. Plan 1~14와 충돌하지 않도록 데이터 모델, 권한, 보드, 일정표, JSON 저장 체계를 정리해야 한다.

## 1. 중요한 기술 전제 — 정적 웹에서 직접 GitHub 저장은 불가능

Antigravity는 다음 전제를 반드시 이해하고 구현해야 한다.

GitHub Pages처럼 정적 배포된 웹은 브라우저에서 사용자가 수정한 내용을 GitHub 저장소 파일에 직접 저장할 수 없다.

따라서 `저장` 버튼은 다음 중 하나로 동작해야 한다.

```text
1. 브라우저 localStorage / IndexedDB에 임시 저장
2. JSON 파일로 다운로드
3. 사용자가 다운로드한 JSON을 repo의 /json 폴더에 넣음
4. Antigravity가 /json 폴더의 JSON을 읽고 코드/seed/runtime data에 반영
```

로컬 개발 환경에서는 File System Access API를 사용할 수 있으면 사용자가 `F:\workspace\json` 폴더를 직접 선택하여 저장할 수 있게 해도 된다.

단, 이 기능은 브라우저와 환경에 따라 제한될 수 있으므로 반드시 fallback을 둔다.

Fallback:

```text
JSON 파일 다운로드
→ 사용자가 직접 /json 폴더에 복사
→ Antigravity에게 “json 폴더 읽고 반영” 요청
```

## 2. Plan 15의 핵심 목표

Antigravity는 Plan 15에서 다음 목표를 달성해야 한다.

1. 기존 더미데이터를 기본 화면에서 제거하거나 비활성화한다.
2. 웹 화면에서 수정한 데이터를 JSON으로 export할 수 있게 한다.
3. JSON export/import 버튼을 제공한다.
4. 인사카드를 웹에서 생성/수정/비활성화할 수 있게 한다.
5. 인사카드 데이터를 JSON으로 저장/export할 수 있게 한다.
6. 일정표와 프로젝트 보드가 인사카드 JSON 데이터를 기준으로 동작하도록 준비한다.
7. CON-COST / Viet_QS 조직 구조를 반영한다.
8. `개발팀 작업` 카테고리를 추가한다.
9. 프로젝트 보드의 `수주/대기`를 `작업 착수 전`으로 변경한다.
10. 프로젝트 보드에 `수정` 컬럼을 추가한다.
11. 클라이언트 재작업 요청은 `수정` 컬럼으로 이동한다.
12. `납품일 임박도 현황`의 가로 스크롤 문제를 해결한다.
13. 대시보드의 `진행 중 프로젝트 요약`을 `월별 프로젝트 요약`으로 변경하고 월별 드롭다운을 추가한다.
14. Plan 1~14의 권한, 결재, 납품일, 재오픈, 성과평가, 데이터 품질 구조와 충돌하지 않게 한다.
15. JSON handoff 방식으로 향후 Antigravity가 사용자 편집 데이터를 읽어 반영할 수 있게 한다.

## 3. Plan 1~14와의 무결성 검토

### 3-1. Plan 1과의 연결

Plan 1의 기본 업무 흐름은 유지한다.

```text
수주 → PM 배정 → 일정 작성 → 승인/반려 → 카드형 업무 진행 → 완료
```

Plan 15는 이 흐름에 다음을 추가한다.

```text
인사카드 기반 사용자/역할 구성
JSON 기반 수동 편집 데이터 반영
내부 개발팀 작업 카테고리
수정/재작업 컬럼
```

### 3-2. Plan 2와의 연결

Plan 2의 Change Request, 추가 업무, 일정 충돌, 승인 라우팅과 연결한다.

`수정` 컬럼은 단순 상태명이 아니라 다음 흐름과 연결된다.

```text
클라이언트 수정 요청
→ ChangeRequest 또는 RevisionRequest 생성
→ PM/중간관리자 승인
→ 수정 TaskCard 생성
→ 수정 컬럼 표시
→ 수정 완료 후 완료 컬럼 복귀
```

### 3-3. Plan 3과의 연결

Plan 3의 PersonnelCard 구조를 Plan 15에서 실제 편집 가능한 인사카드로 확장한다.

기존 `role`과 실제 조직 직급을 혼동하지 않는다.

```text
systemRole: SUPER_ADMIN / DEPARTMENT_MANAGER / PM / WORKER
organizationRank: CEO / VICE_PRESIDENT / MANAGER / PM / TEAM_LEADER / DEPUTY_TEAM_LEADER / STAFF
```

### 3-4. Plan 4와의 연결

Plan 4의 MVP/운영 안정성 원칙을 유지한다.

JSON 저장/export는 실제 DB가 생기기 전까지의 운영 준비 단계다.

삭제는 실제 삭제가 아니라 `isActive=false`, `archivedAt`, `deletedAt` 형태로 soft delete한다.

### 3-5. Plan 5와의 연결

Plan 5의 Excel 기반 직원/프로젝트/스케줄 데이터는 Plan 15의 JSON 구조와 충돌하지 않아야 한다.

Excel import 결과와 수동 편집 JSON은 다음 원칙으로 합친다.

```text
Base seed data
+ Excel import preview/apply data
+ JSON manual edits
= runtime workspace data
```

우선순위:

```text
manual JSON override > imported Excel data > base seed/default
```

### 3-6. Plan 6과의 연결

Plan 6의 보드 UI, Progress, HealthScore, Blocker는 유지한다.

`수정` 컬럼은 HealthScore와 별개다.

`수정` 컬럼에 있는 프로젝트도 Project Summary Card, TaskCard, 상세라인, QC/검수 이력을 가져야 한다.

### 3-7. Plan 7과의 연결

Plan 7의 Data Dictionary, Permission Scope, Selector Layer를 반드시 업데이트한다.

Plan 15에서 추가되는 selector:

```ts
loadWorkspaceRuntimeJson()
mergeRuntimeJsonWithSeedData()
exportWorkspaceJsonSnapshot()
validateWorkspaceJsonSnapshot()
getOrganizationTree()
getPersonnelCardsFromRuntimeData()
getProjectSourceType(project)
getBoardColumnLabel(column)
getRevisionProjects(user, filters)
getMonthlyProjectSummary(month, filters)
```

### 3-8. Plan 8과의 연결

Plan 8의 성과평가 구조와 인사카드는 연결된다.

단, 인사카드 수정이 곧바로 평가 결과를 수정하면 안 된다.

평가 Lock 이후 인사카드 변경은 다음처럼 처리한다.

```text
인사카드 현재값 변경 가능
평가 당시 snapshot은 보존
평가 결과는 당시 PersonnelCardSnapshot 기준 유지
```

### 3-9. Plan 9와의 연결

Plan 9의 QA 증빙/최종 리포트/Phase Lock 원칙을 유지한다.

JSON 저장/export/import, 인사카드 수정, 수동 편집 데이터 반영도 QA Matrix에 포함해야 한다.

### 3-10. Plan 10과의 연결

Plan 10의 Project Summary Card 중심 보드 구조를 유지한다.

보드 컬럼명 변경:

```text
수주/대기 → 작업 착수 전
진행 중 → 진행 중
완료 → 완료
신규 추가 → 수정
```

### 3-11. Plan 11과의 연결

Plan 11의 인사카드 기반 일정표, 권한, 결재, 추가업무, 충돌 관리와 연결한다.

인사카드 JSON은 직원 일정표의 기준 데이터가 된다.

### 3-12. Plan 12와의 연결

Plan 12의 ProjectWorkPart, Scope 정규화, 일정표 UI, 권한 제한은 유지한다.

부서/파트 구조는 Plan 15의 조직 구조를 기준으로 보완한다.

### 3-13. Plan 13과의 연결

Plan 13의 Excel Import Preview, Data Quality Dashboard, Permission Simulator, Admin Settings와 연결한다.

Plan 15의 JSON 저장/export/import는 운영 검증 모드에서 관리한다.

### 3-14. Plan 14와의 연결

Plan 14의 납품일 경과 완료 분류, 사후 추가업무, 재오픈 흐름과 연결한다.

`수정` 컬럼은 Plan 14의 PostDeliveryWorkRequest와 유사하지만 구분한다.

```text
PostDeliveryWorkRequest:
- 내부적으로 추가 업무가 필요할 때
- 작업자 또는 PM이 요청

RevisionRequest:
- 클라이언트 요청으로 기존 납품물을 수정해야 할 때
- 완료 프로젝트가 수정 컬럼으로 이동
```

## 4. Dummy Data 제거 및 Runtime JSON Data 전환

### 4-1. 원칙

더미데이터는 기본 실사용 화면에서 제거한다.

단, 개발/검증 목적의 sample data는 완전히 삭제하지 않고 별도 dev-only fixture로 격리한다.

```text
실사용 모드: runtime JSON data 사용
운영 검증 모드: sample fixture 선택 가능
개발 모드: dev fixture 선택 가능
```

### 4-2. 데이터 로딩 우선순위

```text
1. /json/workspace-export.json 또는 /json/export-manifest.json 기반 runtime data
2. /json/*.json 개별 파일
3. localStorage draft
4. empty state
5. dev fixture는 명시적으로 켠 경우에만 사용
```

### 4-3. 금지사항

- 더미데이터를 실사용 모드에 기본 노출하지 마라.
- 더미데이터가 없다고 화면이 깨지게 하지 마라.
- 데이터가 없으면 명확한 empty state를 보여줘라.
- dev fixture와 runtime JSON을 섞어 실제 운영 데이터처럼 보이게 하지 마라.

## 5. JSON 저장/export/import 체계

### 5-1. JSON 폴더 구조

프로젝트 루트에 다음 폴더를 만든다.

```text
json/
  README.md
  export-manifest.json
  workspace-export.json
  org-structure.json
  personnel-cards.json
  client-projects.json
  internal-projects.json
  schedule-overrides.json
  approval-workflows.json
  workspace-settings.json
  revision-requests.json
  import-notes.json
```

### 5-2. Export Manifest

```ts
ExportManifest {
  schemaVersion: string
  exportedAt: string
  exportedBy: string
  source: "WEB_EXPORT" | "LOCAL_DEV" | "ANTIGRAVITY_GENERATED"
  files: {
    orgStructure: string
    personnelCards: string
    clientProjects: string
    internalProjects: string
    scheduleOverrides: string
    approvalWorkflows: string
    workspaceSettings: string
    revisionRequests: string
  }
  checksum?: string
}
```

### 5-3. 웹 버튼

운영 검증 모드 또는 관리자 설정에 다음 버튼을 추가한다.

```text
임시 저장
JSON 내보내기
JSON 불러오기
Antigravity 반영용 패키지 생성
```

### 5-4. 버튼 동작

```text
임시 저장:
- localStorage 또는 IndexedDB에 저장

JSON 내보내기:
- workspace-export.json 다운로드
- 가능하면 분할 JSON zip 또는 여러 파일 export 지원

JSON 불러오기:
- 사용자가 선택한 JSON을 읽어 화면에 preview
- validation 후 적용

Antigravity 반영용 패키지 생성:
- export-manifest.json + workspace-export.json 생성
- 사용자가 /json 폴더에 복사할 수 있게 안내
```

### 5-5. 브라우저 저장 한계 안내

UI에는 다음 안내를 표시한다.

```text
GitHub Pages에서는 브라우저가 저장소 파일을 직접 수정할 수 없습니다.
JSON을 다운로드한 뒤 프로젝트의 /json 폴더에 복사하고 Antigravity에게 반영을 요청하세요.
```

### 5-6. Antigravity 반영 지시

`json/README.md`에 다음 지시를 포함한다.

```text
Antigravity는 이 폴더의 export-manifest.json을 먼저 읽고,
각 JSON 파일의 schemaVersion을 확인한 뒤,
현재 src/data 또는 runtime data 구조에 맞게 반영하라.

기존 코드와 충돌할 경우 임의로 덮어쓰지 말고 diff report를 먼저 작성하라.
```

## 6. 인사카드 웹 편집 및 JSON 저장

### 6-1. 인사카드 목적

인사카드는 일정표, 권한, 결재 라우팅, 프로젝트 배정, 평가 대상의 기준 데이터다.

### 6-2. PersonnelCard 확장 필드

```ts
PersonnelCard {
  id: string
  employeeNumber?: string
  displayName: string
  koreanAlias?: string
  vietnameseName?: string
  email?: string
  companyId: "CON_COST" | "VIET_QS"
  companyName: "CON-COST" | "Viet_QS"
  departmentId: "FINISH" | "STRUCTURE" | "CIVIL" | "DEVELOP"
  departmentName: "마감" | "구조" | "토목" | "개발"
  subDepartmentId?: string
  subDepartmentName?: string
```

### 6-3. 인사카드 화면 기능

메뉴 위치:

```text
내 설정 또는 운영 검증 모드 > 인사카드 관리
```

기능:

```text
인사카드 목록
인사카드 생성
인사카드 수정
인사카드 비활성화
회사/부서/파트 필터
역할 필터
JSON 저장/export
권한 시뮬레이터로 보기
일정표 기준 적용
```

### 6-4. 일정표 연결

직원 일정표는 인사카드의 다음 필드를 기준으로 필터링한다.

```text
companyId
departmentId
subDepartmentId
teamId
systemRole
organizationRank
```

## 8. 수주 프로젝트 하단 `개발팀 작업` 카테고리 추가

### 8-1. 목적

`개발팀 작업`은 외부 수주 프로젝트가 아니라 내부에서 진행 중인 업무다.

```text

- 외부 수주 프로젝트
- 개발팀 작업
```

또는 사이드 메뉴 구조가 복잡하면 수주 프로젝트 화면 내부 탭으로 구현한다.

```ts
  pmId?: string

  deliveryDate?: string
  status: ProjectStatus
  description?: string
```

## 10. 납품일 임박도 현황 가로 스크롤 문제 해결

### 10-1. 문제

현재 `미정` 컬럼이 화면 우측에 잘려 보이고, 좌우 공간이 남는데도 가로 스크롤이 생긴다.

### 10-2. 개선 원칙

- 4개 컬럼 이하이면 화면 너비 안에 모두 표시한다.
- 컬럼 폭을 고정 과대값으로 두지 않는다.
- 컨테이너 max-width가 과도하게 좁으면 제거 또는 완화한다.
- grid layout은 `minmax`를 사용한다.

권장 CSS 구조:

```css
.board-columns {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(240px, 1fr));
  gap: 16px;
  width: 100%;
  overflow-x: visible;
}
```

단, 컬럼이 5개 이상이고 최소폭 이하로 줄어들 경우에만 horizontal scroll을 허용한다.

### 10-3. 보드 컨테이너 체크

Antigravity는 다음을 확인하라.

```text
상위 container max-width
sidebar width
content padding
board wrapper overflow-x
column min-width
filter bar width
```

### 10-4. 완료 조건

- 납품일 임박도 4개 컬럼이 한 화면에 표시된다.
- `미정` 컬럼을 보기 위해 불필요한 가로 스크롤이 필요하지 않다.
- 사이드바 Mini 모드에서 보드가 더 넓게 표시된다.
