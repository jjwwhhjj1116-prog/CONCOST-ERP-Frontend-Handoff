# WORKSPACE PLAN 13 — 운영자 설정, Excel Import 검증, 권한 시뮬레이터, 데이터 품질 대시보드, 추가 요구사항 관리 체계 프롬프트

이 프롬프트는 기존 `workspace plan1.txt`부터 `workspace plan12.txt` 이후에 추가되는 열세 번째 보강 지시사항이다.

Plan 13의 목적은 새로운 업무 기능을 무작정 추가하는 것이 아니라, 지금까지 쌓아온 Plan 1~12의 시스템이 실제 회사 운영에서 안정적으로 돌아가도록 **운영자 설정, Excel Import 검증, 권한 시뮬레이터, 데이터 품질 검사, 대량 수정, 실사용/검증 모드 분리, 향후 요구사항 관리 체계**를 추가하는 것이다.

Plan 13 이후에는 기능 기획을 계속 `plan14`, `plan15`처럼 늘리는 방식은 가급적 피한다.  
대신 Plan 13에서 정의하는 **Change Intake / RFC / 운영 백로그 / 릴리즈 패치 방식**으로 추가 요구사항을 관리한다.

---

## 0. Plan 13의 핵심 목적

Antigravity는 Plan 13을 통해 다음 문제를 해결해야 한다.

1. Excel Import 전에 데이터가 제대로 읽혔는지 미리 확인할 수 있어야 한다.
2. 직원명, 프로젝트명, Scope, Off/Day, 납품일, 파트가 잘못 매핑되면 화면 반영 전에 잡아야 한다.
3. 권한 설정이 실제로 의도대로 작동하는지 관리자 화면에서 시뮬레이션할 수 있어야 한다.
4. 직원별 일정 조회 권한이 복잡해졌으므로, “이 사용자가 무엇을 볼 수 있는지”를 사전에 검증해야 한다.
5. 데이터 품질 문제를 관리자 대시보드에서 한 번에 확인해야 한다.
6. Excel import 후 프로젝트명, PM, 부서, Scope, 납품일을 대량 수정할 수 있어야 한다.
7. 운영 기준값을 코드 수정 없이 관리자 설정에서 조정할 수 있어야 한다.
8. 일반 작업자가 보는 실사용 화면과 최고관리자/개발자가 보는 검증 화면을 분리해야 한다.
9. Plan 1~12에 추가 요구사항이 생길 경우 무조건 Plan 14를 만들지 않고, 변경요청 방식으로 흡수해야 한다.
10. QA Evidence Matrix와 최종 리포트에 Plan 13 변경사항을 반영해야 한다.

## 1. Plan 1~12와의 무결성 검토

### 1-1. Plan 1과의 연결

Plan 1의 기본 업무 흐름은 유지한다.

```text
수주 → PM 배정 → 일정 작성 → 승인/반려 → 카드형 업무 진행 → 완료
```

Plan 13은 이 흐름에 직접 업무 기능을 추가하는 것이 아니라, 운영자가 이 흐름을 안정적으로 관리할 수 있게 하는 설정/검증 계층이다.

### 1-2. Plan 2와의 연결

Plan 2의 선후행, 변경요청, 체크리스트, 알림, 실제 DB/로그인 확장과 연결된다.

Plan 13에서 추가되는 운영 설정은 다음 기능을 조정할 수 있어야 한다.

- 일정 충돌 허용 기준
- 승인 라우팅 기준
- 알림 묶음 기준
- Change Request 유형
- 체크리스트 기본 템플릿
- 산출물 필수 여부

### 1-3. Plan 3과의 연결

Plan 3의 인사카드 기반 권한과 강하게 연결된다.

Plan 13의 권한 시뮬레이터는 PersonnelCard, Department, Role, ScheduleVisibilityRule, Permission Scope Function을 모두 사용해야 한다.

### 1-4. Plan 4와의 연결

Plan 4의 MVP 제한, 운영 안정성, soft delete, archive, backup 원칙을 유지한다.

Plan 13의 데이터 품질 대시보드는 다음 운영 문제를 감지해야 한다.

- 삭제된 직원에게 업무 배정
- 납품일 없는 프로젝트
- PM 미배정 프로젝트
- 부서 미배정 프로젝트
- 복구 필요한 데이터
- 백업 필요 상태

### 1-5. Plan 5와의 연결

Plan 5의 VN Excel 기반 샘플 데이터 구조를 Plan 13의 Excel Import Preview로 확장한다.

기존에는 Excel을 읽어 seed/dummy data를 만드는 방향이었다.  
Plan 13부터는 다음 흐름을 권장한다.

```text
Excel 감지
→ 구조 분석
→ 미리보기
→ 오류/경고 확인
→ 매핑 수정
→ 사용자 승인
→ seed/dummy data 반영
```

### 1-6. Plan 6과의 연결

Plan 6의 보드 UI, 진행도 게이지, HealthScore, Blocker는 데이터 품질 검사의 대상이 된다.

예시:

- progress가 0%인데 완료 상태인 카드
- Blocker가 있는데 HealthScore가 정상인 카드
- 일정 소진률과 작업 진행률 차이가 큰 카드
- 진행률 변경 메모 누락

### 1-7. Plan 7과의 연결

Plan 7의 Data Dictionary, Permission Scope Function, Selector Layer, Test Matrix가 Plan 13의 기반이다.

Plan 13에서 추가되는 검증 기능은 반드시 selector와 permission function 결과를 사용해야 한다.

### 1-8. Plan 8과의 연결

Plan 8의 평가방식은 데이터 품질과 밀접하게 연결된다.

평가 전에는 다음 품질 문제가 없어야 한다.

- 평가 대상자 미매칭
- 작업량 0인데 QC 오류 존재
- ProjectScaleFactor 누락
- QC Issue weightPercent 범위 오류
- EvaluationScore와 HealthScore 혼동

### 1-9. Plan 9와의 연결

Plan 9의 최종 리포트/QA 증빙/Phase Lock 규칙을 유지한다.

Plan 13은 QA Evidence Matrix에 다음 카테고리를 추가한다.

- Import Preview Tests
- Data Quality Tests
- Permission Simulator Tests
- Admin Settings Tests
- Bulk Edit Tests
- Mode Separation Tests
- Change Intake Tests

### 1-10. Plan 10과의 연결

Plan 10의 납품일 기준 보드, Project Summary Card, 상세라인 6단계, 직원 일정표 방향과 연결된다.

Plan 13의 운영자 설정에서 다음 기준을 수정할 수 있어야 한다.

- 납품일 기준 버킷
- 상세라인 단계 표시명
- 파트 열 접힘 기준
- Off/Day 표시 기본값
- 보드 기본 뷰

### 1-11. Plan 11과의 연결

Plan 11의 1월~7월 Excel 전체 import, 납품일 자동 지정, 휴가/권한/결재/충돌 기능과 연결된다.

Plan 13에서는 import 결과를 바로 반영하지 않고 검증 후 승인하는 구조를 추가한다.

### 1-12. Plan 12와의 연결

Plan 12의 ProjectWorkPart derived data, Scope 정규화, PM 일정 권한, 직원 일정표 고도화와 연결된다.

Plan 13의 데이터 품질 검사는 다음을 검증해야 한다.

- 동일 Scope가 여러 파트로 쪼개지지 않았는가
- ProjectWorkPartOverride가 자동 파트를 훼손하지 않는가
- PM이 작업자 개인 일정 상세를 볼 수 없는가
- 직원 일정표와 프로젝트 파트 보드가 같은 selector 결과를 쓰는가

## 2. Excel Import Preview / Validation

### 2-1. 목적

Excel import는 시스템에 대량 데이터를 넣는 가장 위험한 단계다.  
따라서 실제 seed 반영 전 반드시 미리보기와 검증 단계를 거친다.

### 2-2. Import 흐름

```text
1. Excel 파일 감지
2. 시트 목록 확인
3. 월별 섹션 감지
4. 직원명 추출
5. Project / Scope 쌍 추출
6. Off/Day/HALF Day 분리
7. 프로젝트명 정규화
8. Scope 정규화
9. PersonnelCard 매칭
10. Project 매칭
11. ScheduleAssignment 미리보기
12. TaskCard 묶음 미리보기
13. LeaveSchedule 미리보기
14. 오류/경고 목록 확인
15. 사용자 승인
16. seed/dummy data 반영
```

### 2-3. ImportPreviewSession 엔티티

```ts
ImportPreviewSession {
  id: string
```

### 2-5. Import Preview 화면

메뉴명:

```text

```

탭:


### 2-6. 금지사항

- Excel을 읽자마자 바로 seed data에 반영하지 마라.
- 오류/경고가 BLOCKER 상태인데 적용하지 마라.
- 직원 미매칭을 무시하지 마라.
- Project/Scope 원본값을 덮어쓰지 마라.
- 사용자가 승인하기 전 import 결과를 적용하지 마라.

## 3. 데이터 품질 검사 대시보드

### 3-1. 목적

실제 운영에서는 데이터가 누적되면서 누락, 중복, 충돌, 권한 오류가 생길 수 있다.  
데이터 품질 대시보드는 이런 문제를 한 번에 보여주는 관리자용 화면이다.

### 3-2. 메뉴명

```text
데이터 품질 검사
```

### 3-3. 검사 항목

필수 검사:

```text
직원명 매칭 실패
프로젝트명 중복
Scope 미정규화
납품일 없음
자동 납품일과 수동 납품일 충돌
PM 미배정
부서 미배정
동일 직원 동일 날짜 중복 일정
Off/Day와 업무 일정 충돌
TaskCard 없는 ScheduleAssignment
Project 없는 TaskCard
PersonnelCard 없는 ScheduleAssignment
ProjectWorkPart 중복
권한 없는 일정 노출 가능성
평가 대상자 미매칭
QC Issue weightPercent 오류
HealthScore/EvaluationScore 혼동 가능성
```

### 3-4. DataQualityCheck 엔티티

## 4. 권한 시뮬레이터

### 4-1. 목적

권한은 이 시스템에서 가장 민감한 영역이다.  
관리자가 특정 사용자로 로그인했을 때 실제로 어떤 화면과 데이터를 볼 수 있는지 미리 확인할 수 있어야 한다.

### 4-2. 메뉴명

```text
권한 시뮬레이터
```

### 4-3. 기본 흐름

```text
사용자 선택
→ 화면 선택
→ 프로젝트/월/부서 조건 선택
→ 볼 수 있는 데이터 미리보기
→ 볼 수 없는 데이터 목록 확인
→ 권한 문제 감지
```

### 4-4. PermissionSimulationResult 엔티티

```ts
PermissionSimulationResult {
  id: string
  simulatedUserId: string
  simulatedBy: string
  targetScreen: string
  targetProjectId?: string
  targetMonth?: string
  visibleProjects: string[]
  hiddenProjects: string[]
  visibleEmployees: string[]
  hiddenEmployees: string[]
  visibleSchedules: string[]
  hiddenSchedules: string[]
  warnings: string[]
  createdAt: string
}
```

### 4-5. 예시

```text
시뮬레이션 사용자: [DEMO] Viet QS Team Lead 039(퐁)
화면: 직원 일정표
결과:
- 볼 수 있음: 본인 일정, Slab Team 일정
- 볼 수 없음: PM 일정, 중간관리자 일정, Wall Team 일정, 타 프로젝트 작업자 일정
```

### 4-6. 필수 기능

- 사용자 선택
- 화면 선택
- 월 선택
- 프로젝트 선택
- visible/hidden 목록
- 권한 사유 표시
- permission selector 결과 표시
- 권한 문제 감지 시 DataQualityCheck 생성 가능

### 4-7. 금지사항

- 시뮬레이터가 실제 권한을 변경하지 마라.
- 시뮬레이션 중 권한 없는 상세 데이터 원문을 노출하지 마라.
- 숨김 데이터는 이름 또는 요약만 보여주고 민감 내용은 노출하지 마라.

## 6. 대량 수정 기능

### 6-1. 목적

Excel import 후 프로젝트명, 납품일, PM, 부서, Scope를 하나씩 수정하는 것은 비효율적이다.  
운영자는 대량 수정 기능으로 빠르게 정리할 수 있어야 한다.

### 6-2. 메뉴명

```text
대량 수정
```

### 6-3. 대상

```text
프로젝트명
프로젝트 PM
부서
납품일
Scope 정규화명
직원 매칭
파트명
ProjectScaleFactor
```

### 6-4. BulkEditSession 엔티티

```ts
BulkEditSession {
  id: string
  targetEntityType: string
  totalItems: number
  changedItems: number
  status: "DRAFT" | "PREVIEW" | "APPLIED" | "CANCELLED"
  createdBy: string
  createdAt: string
  appliedAt?: string
}
```

### 6-5. 대량 수정 흐름

```text
대상 선택
→ 수정값 입력
→ 변경 전/후 미리보기
→ 영향 범위 확인
→ 사용자 승인
→ 적용
→ AuditLog 생성
```

### 6-6. 금지사항

- 미리보기 없이 대량 수정하지 마라.
- 적용 후 변경 전/후 기록 없이 수정하지 마라.
- 권한 없는 사용자가 대량 수정하지 못하게 하라.
- 평가 Lock된 데이터는 일반 대량 수정 대상에서 제외하라.

## 8. 향후 추가 요구사항 관리 방식

### 8-1. 문제

Plan 1~13까지 늘어난 상태에서 계속 Plan 14, Plan 15를 추가하면 Antigravity가 요구사항의 우선순위를 잃을 수 있다.

따라서 Plan 13 이후에는 다음 방식을 따른다.

### 8-2. 원칙

새 요구사항이 생기면 즉시 새 Plan 파일을 만들지 않는다.

먼저 다음 중 하나로 분류한다.

```text
A. 기존 Phase 안에서 처리 가능한 세부 수정
B. 운영 설정으로 처리 가능한 기준 변경
C. QA/버그 수정
D. UI 문구/레이아웃 수정
E. 데이터 매핑 수정
F. 아키텍처 변경이 필요한 대형 기능
```

### 8-3. Change Intake 문서

새 요구사항은 먼저 다음 문서에 등록한다.

```text
docs/change-intake.md
```

항목:

```text
요청일
요청자
요구사항 제목
상세 설명
관련 화면
관련 Plan
영향 범위
우선순위
위험도
처리 방식
담당 Phase
상태
```

### 8-4. Architecture Decision Record

아키텍처 변경이 필요한 경우에만 ADR을 작성한다.

```text
docs/adr/
  ADR-001-title.md
  ADR-002-title.md
```

ADR 필수 항목:

```text
배경
문제
선택지
결정
영향 범위
되돌릴 수 있는지 여부
적용 Phase
```

### 8-5. Plan 14를 만들어도 되는 경우

Plan 14는 아래 조건을 만족할 때만 만든다.

```text
1. 기존 Plan 1~13의 어느 Phase에도 넣기 어렵다.
2. 데이터 모델 또는 권한 구조가 크게 바뀐다.
3. 독립된 업무 도메인이 추가된다.
4. 최소 5개 이상의 Phase가 필요한 수준이다.
5. MVP Freeze 이후 별도 Release로 관리해야 한다.
```

### 8-6. Plan 14를 만들지 말아야 하는 경우

다음은 Plan 14가 아니라 Change Intake 또는 Patch로 처리한다.

```text
버튼 위치 변경
문구 변경
필터 옵션 추가
테이블 컬럼 추가

디자인 여백 조정
```

```text
docs/release-patches/

  patch-002.md
```

Patch 문서 항목:


일반 업무 사용자가 보는 화면과 관리자/검증자가 보는 화면을 분리하여 시스템 복잡도를 줄인다.

## 작업

- AppMode 타입 추가
- 실사용 모드 메뉴 구성
- 관리자 검증 모드 메뉴 구성
- SUPER_ADMIN 모드 전환 기능
- PM/WORKER 관리자 검증 모드 접근 제한
- 중간관리자 일부 검증 기능 제한 접근
- 현재 모드 표시
- 모드별 메뉴/라우트 제한

## 완료 조건

- 실사용 모드와 관리자 검증 모드 구분
- 역할별 접근 제한
- 일반 사용자가 검증 메뉴를 보지 않음
- SUPER_ADMIN은 전환 가능
- 빌드 오류 없음

## 자체검수 항목

- WORKER에게 관리자 검증 메뉴가 보이지 않는가?
- PM에게 데이터 품질 검사 전체가 보이지 않는가?
- SUPER_ADMIN은 모드 전환 가능한가?
- 모드 변경이 권한 우회를 만들지 않는가?

## Plan 13 추가 무결성 검토 기준

### Import 무결성

- Excel import 전에 미리보기가 있는가?
- BLOCKER 이슈가 있으면 적용이 차단되는가?
- sourceRow/sourceColumn 추적이 유지되는가?
- 직원/프로젝트/Scope 매칭이 확인되는가?

### 데이터 품질 무결성

- 중복/누락/충돌/권한 위험을 감지하는가?
- 해결/무시 처리 이력이 남는가?
- DataQualityCheck가 실제 데이터와 연결되는가?

### 권한 무결성

- 권한 시뮬레이터가 실제 permission selector와 같은 결과를 사용하는가?
- 시뮬레이터가 민감 데이터를 노출하지 않는가?
- 모드 전환이 권한 우회를 만들지 않는가?

### 설정 무결성

- 운영 기준이 하드코딩에서 분리되는가?
- 설정 변경 이력이 남는가?
- 위험 설정 변경에 확인 절차가 있는가?

### 요구사항 관리 무결성

- 작은 변경이 Plan 14로 과잉 분리되지 않는가?
- 아키텍처 변경만 ADR로 분리되는가?
- Patch 문서가 테스트 항목을 포함하는가?
