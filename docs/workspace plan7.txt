# WORKSPACE PLAN 7 — Plan 1~6 통합 연결성 보강, 데이터 사전, 라우팅/권한/테스트 매트릭스 정리 프롬프트

이 프롬프트는 기존 `workspace plan1.txt`, `workspace plan2.txt`, `workspace plan3.txt`, `workspace plan4.txt`, `workspace plan5.txt`, `workspace plan6.txt` 이후에 추가되는 일곱 번째 보강 지시사항이다.

Plan 1~6은 각각 다음 영역을 정의한다.

- Plan 1: 기본 통합업무관리 시스템, Phase 0~8
- Plan 2: 선후행 업무, 변경요청, 체크리스트, 알림, 실제 DB/로그인 확장, Phase 9~14
- Plan 3: 권한별 화면, 인사카드 기반 권한, PM/중간관리자 개인 일정, Phase 15~17
- Plan 4: MVP 제한, 운영 안정화, 완료 기준, 부재/대리승인/복구/검색 정책, Phase 18~25
- Plan 5: VN 월별 스케줄표 Excel 기반 샘플 데이터 검증, Phase 26~29
- Plan 6: 카드형 프로젝트 보드 UI/UX, 진행도 게이지, HealthScore, Blocker, Phase 30~34

Plan 7의 목적은 새로운 기능을 무작정 추가하는 것이 아니라, Plan 1~6 사이의 연결이 끊기지 않도록 **통합 설계 기준, 데이터 사전, 권한 매트릭스, 라우팅 구조, 테스트 시나리오, 개발 우선순위**를 고정하는 것이다.

## 0. Plan 7의 핵심 목적

Antigravity는 Plan 1~6을 모두 읽은 후, 실제 구현 전에 다음 문제를 반드시 해결해야 한다.

1. 엔티티가 너무 많아져 데이터 모델이 중복되거나 충돌할 수 있다.
2. `status`, `approvalStatus`, `completionStatus`가 혼동될 수 있다.
3. `TaskCard`, `ScheduleAssignment`, `PersonalSchedule`이 모두 일정처럼 보일 수 있다.
4. 권한별 화면과 데이터 필터가 UI에서만 처리되고 로직에서는 누락될 위험이 있다.
5. Excel 기반 샘플 데이터가 기존 Mock 데이터와 분리되어 따로 놀 수 있다.
6. 보드 UI는 좋아졌지만 실제 승인/완료/일정/권한 흐름과 연결되지 않을 수 있다.
7. Phase가 34까지 늘어나면서 구현 순서, 의존성, 완료 기준이 불명확해질 수 있다.
8. GitHub Pages 배포 구조에서 라우팅, base path, 새로고침 404 문제가 발생할 수 있다.
9. 한국어/영어/베트남어 이름과 업무명이 섞여 검색/필터/정렬 문제가 생길 수 있다.
10. 개발자가 임의로 기능을 앞당겨 구현하면서 MVP 경계가 무너질 수 있다.

따라서 Plan 7은 다음을 강제한다.

- 통합 데이터 사전 작성
- 상태값 표준화
- 일정 데이터 구분 규칙 확정
- 권한 스코프 함수 우선 구현
- 라우팅/화면 구조 명세
- Phase 의존성 매트릭스 작성
- 테스트 시나리오 매트릭스 작성
- 샘플 데이터와 UI 연결 규칙 확정
- GitHub Pages 배포 조건 검증
- 다국어/이름/검색 정규화 기준 확정
- MVP와 확장 기능 경계 재확인

## 1. 절대 원칙

Antigravity는 다음 원칙을 반드시 지켜라.

- Plan 7은 Plan 1~6을 대체하지 않는다.
- Plan 7은 Plan 1~6의 연결성을 보강하는 통합 설계 프롬프트다.
- Plan 1의 Phase 0~8 기본 흐름을 가장 우선한다.
- Plan 4의 MVP 범위 제한을 반드시 지킨다.
- Plan 5의 VN Excel 샘플 데이터는 실제 업무 검증용 seed로 연결한다.
- Plan 6의 보드 UI는 실제 데이터와 권한 로직 위에서만 구현한다.
- 데이터 모델을 추가하기 전에 기존 엔티티로 표현 가능한지 먼저 검토한다.
- status 계열 필드는 통합 규칙 없이 임의로 추가하지 않는다.
- UI에서 숨기는 것만으로 권한을 처리하지 않는다. 데이터 필터링 로직을 반드시 분리한다.
- 사용자가 승인하기 전까지 다음 Phase로 넘어가지 않는다.
- 사용자가 승인하기 전까지 GitHub 원격 push를 하지 않는다.


이 엔티티들을 모두 무작정 생성하면 구조가 과도하게 복잡해진다.

따라서 Antigravity는 다음 원칙을 지켜라.

- MVP에서는 핵심 엔티티만 먼저 구현한다.
- 확장 Phase에서는 기존 엔티티를 재사용할 수 있는지 먼저 검토한다.
- 같은 목적의 엔티티가 있으면 병합 가능성을 검토한다.
- 데이터 모델은 `types`, `schemas`, `mock data`, `UI selectors`가 같은 기준을 사용해야 한다.

### 2-2. status 혼동 위험

다음 status들은 서로 역할이 다르다.

```text
Project.status
TaskCard.status
TaskCard.approvalStatus
TaskCard.completionStatus
SchedulePlan.status
ApprovalRequest.status
PersonalSchedule.status
ChangeRequest.status
AbsenceSchedule.status
DelegationRule.status
ReassignmentRequest.status
```

Antigravity는 Phase 0에서 반드시 status taxonomy를 작성해야 한다.

### 2-3. 일정 데이터 혼동 위험

일정 관련 데이터는 최소 4종류로 구분한다.

```text
Project schedule
TaskCard schedule
ScheduleAssignment
PersonalSchedule
```

구분 기준:

- `Project schedule`: 프로젝트 전체 시작일/종료일
- `TaskCard schedule`: 업무 카드 단위 일정
- `ScheduleAssignment`: Excel 또는 월별 스케줄표에서 추출한 일자별 배정 데이터
- `PersonalSchedule`: PM/중간관리자/작업자의 개인 일정, Off, Day, 회의, 교육 등

이 네 가지를 UI에서 함께 보여줄 수는 있지만, 데이터 모델에서는 반드시 구분해야 한다.

### 2-4. 이력 데이터 혼동 위험

이력 관련 데이터는 다음처럼 역할을 분리한다.

```text
AuditLog
- 누가, 언제, 무엇을 바꿨는지 기록

VersionSnapshot
- 변경 전후 비교와 복구 준비용 스냅샷

ProgressUpdate
- 업무 진행률과 진행 내용 변경 이력

Notification
- 사용자에게 알려야 하는 사건

DigestNotification
- 여러 알림을 묶은 요약 알림
```

절대 모든 이력을 `AuditLog` 하나에 몰아넣지 마라.

### 5-7. 상태값 연결 규칙

상태값은 서로 자동으로 연결될 수 있지만 동일한 의미로 취급하지 않는다.

예시:

- `TaskCard.status = DONE` 이라고 해서 무조건 `completionStatus = COMPLETED`는 아니다.
- 작업자가 완료 요청한 상태는 `TaskCard.status = REVIEW`, `completionStatus = WORKER_DONE`으로 표현할 수 있다.
- 중간관리자 최종 승인 후에만 `completionStatus = COMPLETED`로 변경한다.
- 프로젝트 전체 완료는 모든 필수 TaskCard가 완료되고, 미해결 ApprovalRequest가 없을 때만 가능하다.

## 8. GitHub Pages 배포 안정화 지시

프로젝트의 GitHub 저장소와 배포 URL이 다음과 같다면:

```text
Repository: https://github.com/eumditravel-oss/workspace
Pages URL: https://eumditravel-oss.github.io/workspace/
```

Antigravity는 다음을 확인해야 한다.

### 8-1. base path 확인

- Vite라면 `base: "/workspace/"` 필요 여부 확인
- Next.js라면 `basePath` 또는 `assetPrefix` 필요 여부 확인
- React Router라면 `basename="/workspace"` 필요 여부 확인

### 8-2. 새로고침 404 대응

GitHub Pages에서 SPA 라우팅을 사용할 경우 새로고침 시 404가 발생할 수 있다.

해결 후보:

- HashRouter 사용
- 404.html fallback 구성
- GitHub Pages용 SPA redirect 스크립트 적용
- 라우트 수를 줄이고 query/hash 기반으로 관리

임의로 적용하지 말고 Phase 0에서 현재 프로젝트 구조를 확인한 뒤 제안하라.

### 8-3. 배포 검증 항목

- 메인 페이지 로딩
- `/workspace/` 하위 경로 로딩
- 새로고침 시 404 여부
- 정적 asset 경로 정상 여부
- 모바일 화면 기본 표시
- GitHub Pages 배포 반영 지연 안내

## 9. Mock 데이터와 VN Excel seed 데이터 통합 방식

Plan 5의 VN Excel 기반 데이터는 기존 Mock 데이터와 분리되어 따로 존재하면 안 된다.

### 9-1. 통합 원칙

- `samplePersonnelCards`는 Plan 3의 `PersonnelCard` 구조와 연결한다.
- `sampleProjects`는 Plan 1의 `Project` 구조와 연결한다.
- `sampleScheduleAssignments`는 Plan 5의 Excel 일자별 배정 데이터로 유지한다.
- `sampleTaskCards`는 연속 일정 묶음 단위로 생성한다.
- `samplePersonalSchedules`는 Off/Day/HALF Day 등 개인 일정으로 유지한다.
- 보드와 공정표는 같은 seed 데이터를 바라봐야 한다.

### 9-2. 권장 파일 구조

```text
src/data/
  seed/
    departments.ts
    personnel.ts
    projects.ts
    taskCards.ts
    scheduleAssignments.ts
    personalSchedules.ts
    approvals.ts
    notifications.ts
    auditLogs.ts
  index.ts
```

또는 기존 프로젝트 구조에 맞게 다음처럼 둘 수 있다.

```text
src/mocks/workspace/
```

중요한 것은 seed 데이터가 화면마다 따로 복사되지 않는 것이다.

## 추가 무결성 검토 기준

Phase 35 이후에는 다음 항목을 반드시 추가 검토한다.

### 데이터 모델 무결성

- 같은 의미의 엔티티가 중복 생성되지 않았는가?
- `TaskArtifact`와 `Attachment`의 역할이 충돌하지 않는가?
- `ScheduleAssignment`와 `TaskCard`의 역할이 분리되었는가?
- `PersonalSchedule`이 업무 카드처럼 잘못 처리되지 않는가?

### 상태값 무결성

- `TaskCard.status`와 `TaskCard.completionStatus`가 혼동되지 않는가?
- `ApprovalRequest.status`와 `SchedulePlan.status`가 혼동되지 않는가?
- `Project.status`가 개별 카드 상태로 오염되지 않는가?

### 권한 무결성

- 권한 필터가 UI가 아니라 공통 함수에서 처리되는가?
- 검색 결과에도 권한 필터가 적용되는가?
- 카드 상세 URL 직접 접근 시에도 권한이 적용되는가?
- selector 결과가 권한 범위를 벗어나지 않는가?

### 데이터 연결 무결성

- VN Excel seed 데이터가 별도 더미 화면에만 쓰이지 않는가?
- 보드, 공정표, 대시보드가 같은 seed 데이터를 바라보는가?
- Excel source 추적 정보가 유지되는가?

### 배포 무결성

- GitHub Pages base path가 반영되었는가?
- 정적 asset 경로가 깨지지 않는가?
- 새로고침 404 문제가 확인되었는가?
