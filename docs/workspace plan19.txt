# WORKSPACE PLAN 19 — KOR/VIET 다국어 전환, 업무카드 자동 번역, 번역 API 어댑터, 이중언어 UI/검수 워크플로우 프롬프트

이 프롬프트는 기존 `workspace plan1.txt`부터 `workspace plan18.txt` 이후에 추가되는 열아홉 번째 보강 지시사항이다.

Plan 19의 목적은 Workspace 시스템에 **한국어/베트남어 전환**, **업무카드 입력값의 양방향 자동 번역**, **번역 결과 검수**, **이중언어 UI 표시 전략**, **JSON Handoff와 다국어 데이터 연동**을 추가하는 것이다.

중요 전제:

- Plan 단계는 뒤로 갈수록 최신 요구사항이 우선이다.
- Plan 19는 Plan 18의 검증 중심 원칙을 유지한다.
- Plan 19는 무작정 기능을 추가하는 작업이 아니다.
- 먼저 현재 코드, 라우트, 스토어, JSON 구조, 실제 화면을 분석한 뒤 다국어 기능을 최소 침습 방식으로 설계한다.
- 사용자 승인 없이 다음 Phase로 넘어가지 않는다.
- 사용자 승인 없이 GitHub 원격 push를 하지 않는다.
- 사용자 승인 없이 API Key, Secret, Service Account 파일, `.env` 값을 코드에 하드코딩하지 않는다.
- Google Cloud Translation API, LibreTranslate, 자체 번역 Proxy 등은 모두 교체 가능한 Provider Adapter 구조로 만든다.

## 0. 현재 추가 요구사항

사용자는 다음 기능을 추가로 원한다.

1. Workspace 전체를 **VIET 언어 버전**으로 변경할 수 있어야 한다.
2. 한국 직원이 CON-COST에서 업무카드를 한글로 작성하면 VN 번역이 자동 생성되어야 한다.
3. 베트남 직원이 업무카드를 베트남어로 작성하면 KOR 번역이 자동 생성되어야 한다.
4. Google Antigravity가 무료 번역 API 연결 구조를 준비하되, API Key를 임의로 생성하거나 외부에서 무단 수집하면 안 된다.
5. 무료 API 또는 무료 구간이 있는 API는 사용자가 키를 제공하면 `.env` 또는 안전한 설정 경로를 통해 연결한다.
6. 한국어로 작성된 내용을 베트남어로 표시할 때, UI 가독성 측면에서 가장 적합한 배치를 설계해야 한다.
7. 세부 Phase를 나눠 정확도가 100%에 수렴하도록 검증 중심 workflow를 구성해야 한다.

## 1. 절대 금지 사항

Antigravity는 다음을 절대 하지 마라.

```text
- 인터넷에서 임의의 무료 Google Translate API Key를 검색하거나 가져오지 마라.
- 비공식 Google Translate endpoint를 크롤링하거나 우회 호출하지 마라.
- API Key를 Git 저장소에 커밋하지 마라.
- 브라우저 번들 안에 Secret Key를 하드코딩하지 마라.
- 번역 API가 연결되지 않았는데 “자동번역 완료”라고 보고하지 마라.
- 테스트하지 않은 번역 결과를 공식 업무 원문처럼 덮어쓰지 마라.
- 한국어 원문을 번역문으로 대체하지 마라.
- 베트남어 원문을 한국어 번역문으로 대체하지 마라.
- 기존 JSON Handoff 구조를 깨지 마라.
- 기존 권한, 결재, AuditLog, Notification 구조를 우회하지 마라.
```

API Key는 사용자의 Google Cloud Console, 또는 사용자가 직접 준비한 무료/로컬 번역 서버에서 제공되어야 한다. Antigravity는 키를 “자동 확보”하는 것이 아니라, **키가 있을 때 안전하게 연결되는 구조**를 구현해야 한다.

## 2. 권장 번역 Provider 전략

Plan 19에서는 번역 기능을 특정 업체 API에 종속시키지 말고 다음 Provider Adapter 구조로 만든다.

```ts
type TranslationProvider =
  | 'DISABLED'
  | 'GOOGLE_CLOUD_TRANSLATION'
  | 'LIBRETRANSLATE'
  | 'LOCAL_PROXY'
  | 'MANUAL_ONLY';
```

### 2-1. Provider 우선순위

초기 개발 기준 권장 순서는 다음이다.

```text
1순위: MANUAL_ONLY / DISABLED
- API Key 없이 UI와 데이터 구조를 먼저 검증
- 번역 버튼, 번역 상태, 수동 번역 입력칸, JSON 저장 구조부터 구현

2순위: LOCAL_PROXY
- 로컬 개발 환경에서만 `.env.local`의 API Key를 사용
- 프론트엔드는 `/api/translate` 같은 내부 proxy만 호출
- 실제 Key는 서버/로컬 환경 변수에만 존재

3순위: GOOGLE_CLOUD_TRANSLATION
- 사용자가 Google Cloud API Key 또는 Service Account를 제공한 경우만 연결
- 무료 구간이 있어도 결제 설정과 quota 관리가 필요하므로 비용 방어 UI를 둔다

4순위: LIBRETRANSLATE
- 사용자가 직접 운영하거나 신뢰 가능한 서버 URL을 제공한 경우 사용
- 공개 무료 서버는 장애/제한/보안 이슈가 있으므로 기본값으로 고정하지 않는다
```

### 2-2. 정적 GitHub Pages 환경 주의

현재 Workspace는 GitHub Pages 정적 배포 구조를 고려한다.

정적 배포에서는 서버 환경변수 기반 Secret 보호가 어렵다. 따라서 다음 원칙을 따른다.

```text
- 프로덕션 GitHub Pages에서는 기본값을 DISABLED 또는 MANUAL_ONLY로 둔다.
- API 번역은 로컬 개발 환경, 사내망 proxy, Cloud Function/Cloud Run/API Route가 준비된 환경에서만 활성화한다.
- 프론트엔드에서 직접 API Key를 쓰는 방식은 프로토타입 옵션으로만 허용하고, 반드시 도메인 제한/쿼터 제한/경고 문구를 둔다.
```

## 3. 다국어 데이터 모델

기존 Project, TaskCard, ScheduleAssignment, ApprovalRequest, Notification, AuditLog 구조를 무너뜨리지 말고, 번역 필드는 보조 메타데이터로 확장한다.

### 3-1. 공통 다국어 텍스트 구조

```ts
type LanguageCode = 'ko' | 'vi' | 'en';

type TranslationStatus =
  | 'NONE'
  | 'NEEDS_TRANSLATION'
  | 'AUTO_TRANSLATED'
  | 'HUMAN_REVIEW_REQUIRED'
  | 'HUMAN_APPROVED'
  | 'TRANSLATION_FAILED';

type LocalizedText = {
  sourceLanguage: LanguageCode;
  original: string;
  translations: Partial<Record<LanguageCode, string>>;
  translationStatus: Partial<Record<LanguageCode, TranslationStatus>>;
  translatedAt?: string;
  translatedByProvider?: TranslationProvider;
  reviewedAt?: string;
  reviewedByUserId?: string;
  glossaryVersion?: string;
};
```

### 3-2. TaskCard 적용 필드

업무카드는 최소 다음 필드에 LocalizedText 적용을 검토한다.

```text
- title
- summary
- description
- scopeMemo
- workerInstruction
- qcMemo
- blockerReason
- revisionReason
- completionNote
```

초기 Phase에서는 모든 필드에 한 번에 적용하지 말고 다음 순서로 적용한다.

```text
1차: title, description, workerInstruction
2차: qcMemo, revisionReason, completionNote
3차: Notification, ApprovalRequest comment, AuditLog summary
```

### 3-3. 원문 보존 원칙

```text
- 사용자가 직접 작성한 언어가 항상 original이다.
- 자동 번역문은 original을 대체하지 않는다.
- 자동 번역 결과는 draft로 취급한다.
- 중요한 업무 지시는 HUMAN_APPROVED 전까지 “자동번역/검토필요” 배지를 표시한다.
- AuditLog에는 원문 변경과 번역문 변경을 구분해 기록한다.
```

## 4. 언어 감지 정책

자동 감지는 보조 기능이며, 최종 sourceLanguage는 사용자가 수정할 수 있어야 한다.

### 4-1. 기본 감지 규칙

```text
- 한글 자모/완성형 문자가 포함되면 ko 후보
- 베트남어 특수문자/성조가 다수 포함되면 vi 후보
- 베트남어가 무성조로 입력될 수 있으므로 100% 자동 확정하지 않는다
- 한글과 베트남어가 섞이면 MIXED로 보고 사용자가 sourceLanguage를 선택하게 한다
```

### 4-2. 입력 UX

업무카드 작성 화면에는 다음 요소를 둔다.

```text
[작성 언어] 자동 감지: 한국어 / 베트남어 / 직접 선택
[자동 번역] 켜기 / 끄기
[번역 대상] 한국어 → 베트남어 또는 베트남어 → 한국어
[번역 상태] 대기 / 자동번역 / 검토필요 / 승인됨 / 실패
```

자동 번역은 타이핑마다 호출하지 말고 다음 조건에서만 실행한다.

```text
- 저장 버튼 클릭 시
- 번역 버튼 클릭 시
- 입력 후 debounce 1.5초 이상 + 사용자가 자동번역을 켠 경우
- 동일 텍스트 hash가 이미 번역 cache에 있으면 API를 호출하지 않음
```

## 5. UI 표시 전략 — 한국어 원문 기준 베트남어 표시 방식

업무자는 한국어/베트남어를 동시에 봐야 할 수 있지만, 모든 문장을 항상 2개 언어로 같은 크기로 보여주면 카드가 지나치게 길어지고 가독성이 떨어진다.

Plan 19의 기본 UI 원칙은 다음이다.

```text
- 카드 목록/보드에서는 “주 언어 1줄 + 보조 언어 1줄 축약”만 표시한다.
- 상세 패널에서는 원문과 번역문을 나란히 또는 위아래로 확장 표시한다.
- 번역문은 원문보다 작은 크기와 낮은 시각 강도로 표시한다.
- 자동번역은 반드시 Auto 또는 검토필요 배지를 붙인다.
- 사용자가 선택한 UI 언어가 ko이면 한국어를 우선 표시하고 베트남어를 보조 표시한다.
- 사용자가 선택한 UI 언어가 vi이면 베트남어를 우선 표시하고 한국어를 보조 표시한다.
```

### 5-1. 카드 목록/보드 Compact 표시

권장 표시 방식:

```text
[업무 제목 한국어]
VI · [베트남어 번역 1줄 축약]  Auto / 검토필요

담당자 · 일정 · 진행률 · 상태 배지
```

예시:

```text
슬라브 물량 산출 1차 검토
VI · Kiểm tra lần 1 khối lượng sàn  Auto

Nguyen Van A · 07/10~07/12 · 40% · 진행 중
```

반대로 베트남어 UI에서는 다음처럼 표시한다.

```text
Kiểm tra lần 1 khối lượng sàn
KO · 슬라브 물량 산출 1차 검토  Auto

Nguyen Van A · 07/10~07/12 · 40% · Đang tiến hành
```

### 5-2. 카드 상세 패널 표시

상세 패널에서는 다음 배치를 권장한다.

```text
[원문]
- 작성자
- 작성 언어
- 작성일
- 원문 내용

[번역]
- 대상 언어
- Provider
- 번역 상태
- 번역 내용
- 다시 번역
- 수동 수정
- 검토 승인
```

모바일 또는 좁은 화면에서는 나란히 2열 대신 위아래 accordion으로 표시한다.

### 5-3. 긴 설명 필드 표시

`description`, `workerInstruction`, `qcMemo`처럼 긴 문장은 카드 본문에 전부 표시하지 않는다.

```text
- 보드 카드: 첫 1~2줄만 표시
- 상세 패널: 원문/번역 탭 또는 접기/펼치기 표시
- 번역문은 “VI 보기”, “KO 보기”, “둘 다 보기” 토글 제공
```

### 5-4. 언어 전환 토글

상단 헤더 또는 설정에 다음 토글을 둔다.

```text
표시 언어: 한국어 / Tiếng Việt / 이중언어

한국어:
- UI 메뉴, 버튼, 상태값을 한국어로 표시
- 업무 원문이 베트남어면 한국어 번역을 보조 표시

Tiếng Việt:
- UI 메뉴, 버튼, 상태값을 베트남어로 표시
- 업무 원문이 한국어면 베트남어 번역을 보조 표시

이중언어:
- 업무 관련 핵심 텍스트는 원문 + 번역 동시 표시
- 메뉴/버튼은 사용자의 기본 언어 기준으로 유지
```

## 6. 용어집/번역 품질 관리

업무카드에는 건축, 구조, 수량산출, QC, 납품, 수정, 승인 용어가 많으므로 일반 번역만으로는 품질이 불안정할 수 있다.

Plan 19에서는 Glossary 구조를 반드시 설계한다.

```ts
type TranslationGlossaryEntry = {
  id: string;
  ko: string;
  vi: string;
  category: 'STRUCTURE' | 'ARCHITECTURE' | 'CIVIL' | 'QC' | 'APPROVAL' | 'SCHEDULE' | 'COMMON';
  aliases?: string[];
  locked: boolean;
  updatedAt: string;
  updatedByUserId: string;
};
```

초기 용어 예시:

```text
수주 프로젝트 → Dự án nhận từ khách hàng
개발팀 작업 → Công việc đội phát triển
작업 착수 전 → Chưa bắt đầu
진행 중 → Đang tiến hành
완료 → Hoàn thành
수정 → Chỉnh sửa / Revision
결재 대기 → Chờ phê duyệt
반려 → Từ chối
일정 연장 요청 → Yêu cầu gia hạn lịch
추가 일정 요청 → Yêu cầu thêm lịch làm việc
업무 하달 → Giao việc
검토 필요 → Cần kiểm tra
자동 번역 → Dịch tự động
검토 승인 → Đã duyệt bản dịch
```

Antigravity는 번역 API 결과를 그대로 신뢰하지 말고, glossary가 있으면 후처리 또는 provider glossary 기능으로 반영할 수 있게 구조화한다.

# Phase 147 — i18n 데이터 모델 및 번역 상태 모델 설계

## 목표

업무카드 자동 번역과 UI 언어 전환을 위한 타입/스토어/JSON 구조를 설계한다.

## 작업 지시

1. `LanguageCode`, `LocalizedText`, `TranslationStatus`, `TranslationProvider` 타입을 추가 설계한다.
2. TaskCard에 바로 적용할 필드를 1차/2차/3차로 나눈다.

# Phase 149 — 번역 Provider Adapter 및 API Key 안전 연결 구조

## 목표

자동 번역을 위한 Provider Adapter를 만들되, API Key 보안과 비용 리스크를 통제한다.

## 작업 지시

1. `translationProvider.ts` 또는 유사 모듈을 만든다.
2. Provider는 `DISABLED`, `MANUAL_ONLY`, `GOOGLE_CLOUD_TRANSLATION`, `LIBRETRANSLATE`, `LOCAL_PROXY`를 지원한다.
3. 기본값은 `DISABLED` 또는 `MANUAL_ONLY`로 둔다.
4. `.env.example`에 필요한 환경변수 예시만 추가한다.
5. 실제 API Key는 `.env.local` 또는 사용자의 환경에서만 읽는다.
6. API Key가 없으면 자동번역 버튼은 비활성화하거나 “설정 필요” 상태로 표시한다.
7. 브라우저 번들에 Secret이 들어가지 않도록 확인한다.
8. GitHub Pages 정적 배포에서는 자동 API 번역이 제한될 수 있음을 UI와 문서에 명확히 표시한다.
9. 번역 실패 시 원문은 절대 훼손하지 않고 TranslationStatus만 `TRANSLATION_FAILED`로 바꾼다.
10. 동일 텍스트 반복 번역 방지를 위해 hash 기반 cache 구조를 설계한다.

## 환경변수 예시

```env
# Do not commit real values
NEXT_PUBLIC_WORKSPACE_TRANSLATION_MODE=MANUAL_ONLY
WORKSPACE_TRANSLATION_PROVIDER=GOOGLE_CLOUD_TRANSLATION
GOOGLE_CLOUD_TRANSLATION_API_KEY=
GOOGLE_CLOUD_PROJECT_ID=
LIBRETRANSLATE_ENDPOINT=
LIBRETRANSLATE_API_KEY=
WORKSPACE_TRANSLATION_DAILY_CHAR_LIMIT=50000
```

주의:

```text
NEXT_PUBLIC_ prefix에 실제 Secret을 넣지 마라.
프론트엔드 직접 호출용 키를 사용할 경우에는 도메인 제한과 quota 제한을 걸고, 프로토타입 모드로만 표시하라.
```

## 완료 조건

```text
- Provider Adapter 구조 존재
- API Key가 없어도 앱이 정상 동작
- API Key가 없으면 자동번역 불가 상태를 명확히 표시
- 실제 Secret이 코드에 포함되지 않음
- build 통과
```

## 보고 형식

```text
[Phase 149 보고]
1. Provider 구조
2. API Key 처리 방식
3. GitHub Pages 제한사항
4. .env.example 변경사항
5. 자동번역 비활성 상태 UX
6. 보안 검토 결과
```

```text
현재 F:\workspace 프로젝트의 Plan 19 작업을 시작한다.

중요 전제:
- Plan 단계는 뒤로 갈수록 최신 요구사항이 우선이다.

- API Key, Secret, Service Account 파일을 코드나 저장소에 하드코딩하지 마라.
- 인터넷에서 무료 Google Translate API Key를 임의로 검색하거나 가져오지 마라.
- Google Cloud Translation API는 사용자가 제공한 키 또는 환경변수가 있을 때만 연결하라.
- API Key가 없으면 MANUAL_ONLY 또는 DISABLED 모드로 UI/데이터 구조부터 검증하라.
- 정적 GitHub Pages 환경에서는 Secret 보호가 어렵다는 점을 반영해, 자동번역은 Local Proxy 또는 별도 서버/Cloud Function 구조를 우선 설계하라.
- 한국어 원문과 베트남어 번역문은 절대 서로 덮어쓰지 말고, LocalizedText 구조로 분리 보관하라.

현재 언어 구조, 하드코딩 UI 텍스트, 번역 대상 필드, JSON 영향 범위, API/Secret 존재 여부, MVP/확장 범위를 조사해 보고하고, Phase 147 진행 승인을 요청하라.
```
